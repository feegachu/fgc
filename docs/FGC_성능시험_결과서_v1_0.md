원문에 없는 기준으로 합격을 선언하지 않는다. 10만 건에 못 미치는 측정은 외삽하지 않고 "미검증"으로 적는다(#673).

### 신한 compose와 다른 점

힙과 메모리는 `infra/shinhan/compose.yaml`과 같다: API `-Xms256m -Xmx1024m -XX:MaxMetaspaceSize=384m`, `mem_limit 2g`, DB `postgres:17-alpine`, `mem_limit 1g`, `TZ=Asia/Seoul`, API 프로필 `prod`. 다른 점은 아래뿐이다.

| 항목 | compose | 이 측정 | 이유 |
|---|---|---|---|
| Flyway 위치 | `db/migration`, `db/demo`, `db/demo-agent` | `db/migration`, `db/demo` | 생성기 DB는 `db/demo-agent`를 읽지 않는다 [시드 명세 §50]. `agent01`은 격리 DB에서만 스크립트가 켠다 |
| 웹 계층 | nginx(web) 앞단 | 없음 | API 처리 시간만 잰다. 정적 파일과 프록시 지연은 포함하지 않는다 |
| 앱 형태 | RC 이미지(Tomcat WAR) | 사전 측정은 bootJar(내장 Tomcat), RC는 이미지 | 게시 이미지 `sha-2c460fd3`로 같은 스크립트의 smoke, dashboard를 돌려 동작을 확인했다 |
| 생성기 실행 | 없음 | `generateDar012`와 같은 진입점(`dar012` 프로필)을 API와 같은 컨테이너로 | 메모리 한도와 DB 경로를 API와 맞춘다 |
| JVM 옵션 | 위 3개 | 위 3개 + `-Xlog:gc:file=/tmp/gc.log` | 힙 표본 |
| PostgreSQL | 기본값 | 기본값 + `pg_stat_statements`, `track_io_timing`, `track_wal_io_timing`, trust 인증 | DB 병목 지표. 포트를 열지 않아 trust로 둔다 |
| 일 배치 | 02:00 켜짐 | 꺼짐 | 측정 중 끼어들지 않게 한다 |
| AI 키, 파일 볼륨 | 있음 | 없음 | 대상 API에 쓰이지 않는다 |

**병목 관찰.** `pg_stat_statements`는 적재와 검증 조회를 포함한 누계다.

- **시간의 절반 넘게 SQL 실행 밖에 있다 (측정 B).** SQL 실행 합계 221.9초는 배치 538.8초의 41%다. 나머지는 앱 코드, JDBC 왕복, 커밋 대기다. CPU 표본에서 앱과 DB가 각각 코어 1개 미만으로 교대한다. Step이 건별로 왕복하는 단일 흐름이라는 코드 구조와 맞는다.
- **분개 Step이 가장 크다.** 측정 B에서 254.6초(47%). `journal_line` INSERT 30,572회 27.4초, `journal_header` UPDATE 15,286회 13.0초, INSERT 15,286회 11.8초. 분개 건마다 커밋해 fsync가 쌓인다(커밋 누계 30,820, fsync 합계 103.1초). 채번은 PR #873 뒤 상위권 밖이다(측정 A 4,378회 0.3초).
- **`reconciliation_match` INSERT가 건당 블록을 많이 읽는다.** 측정 B에서 15,288회 24.2초, 건당 블록 약 553개. `reconciliation_result` 순차 스캔 횟수(15,290)가 INSERT 횟수와 거의 같고 읽은 행은 9,507만 행이다(측정 A는 396만 행). `guard_finalized_reconciliation_result` 트리거(V31)의 `= ANY(...)` 조회가 표가 작을 때 세운 계획을 재사용하는 것으로 추정한다(원인 미확인). 데이터가 늘면 제곱으로 늘 수 있는 항목이다.
- 스케줄 `schedule_line` INSERT 두 형태 합계 23.2초, 대사 예외 집계 1회 10.3초, `cap_check_detail` INSERT 두 형태 합계 13.4초.
- 메모리는 병목이 아니다. 힙이 `-Xms`(256MB) 안에서 움직였고 OOM이 없다.

전문은 `build/performance/<시각>-batch-<N>/report.txt` 형식으로 스크립트가 남긴다.

DB 메모리 최대 309MiB, CPU 평균 132%(최대 761%). 힙 최대 247MiB, Full GC 0. 무거운 SQL: 실행 상세의 대상 집계 1,094회 137.4초(평균 126ms), 예외 목록 1,048회 125.2초(평균 120ms), 1,200% 목록의 `ranked_cap_check` 여러 형태, `vw_journal_imbalance` 1,055회 73.1초(평균 69ms). 부하가 DB에 몰린다. API별 최대값이 1.3~1.8초로 비슷한 것은 호스트 겹침으로 함께 밀린 순간이 있다는 뜻으로 보고, 원인은 확인하지 않았다.

### 4-3. 한계

- **읽기 API만 잰다.** PER-001 세부내용의 "등록·수정"은 측정하지 않았다. 쓰기는 PER-007 재실행 1건뿐이다.
- 계정은 내부 1개(`settle01`), 설계사 1개(`agent01`)를 VU가 나눠 쓴다. 토큰은 `setup()`에서 계정당 1회 발급한다. 로그인 부하는 재지 않는다.
- 사용자 구성(내부 9 : 설계사 1), 생각 시간 1~3초, 대시보드 VU 5는 원문에 없는 값이다. 업무 규칙 아님, 가상 GA 정책으로 정함(합격 기준이 아니라 조건). 실제 사용 패턴 자료가 나오면 다시 정한다.
- DAR-012 데이터는 GA→설계사 지급을 대표 계약 4건만 만들어 설계사 명세 행이 적고 그 단계 대사가 대부분 `ACTUAL_MISSING`이다 [시드 명세 §50]. 예외와 위반 건수는 데이터 구성에서 나온 값이고 업무 사례가 아니다.
- PC 값이다. 신한 서버 성능으로 인용하지 않는다.

## 6. 목표 초과 항목, 원인, 개선안

측정한 범위에서 목표를 넘은 항목은 없다(#673 시나리오 4). 다만 측정 B의 538.8초는 목표 600초와 가까워 RC에서 넘을 수 있다. 넘으면 아래 순서로 고친다. 아직 시도하지 않은 개선안이라 효과는 재 봐야 안다.
