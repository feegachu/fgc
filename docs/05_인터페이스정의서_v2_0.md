## 0. 이 문서를 읽는 법 (5분)

### 0-1. 이 문서는 무엇인가

화면과 서버가 **어떤 주소로 · 무엇을 주고받는지**를 적은 약속입니다.
화면정의서가 "무엇을 보여줄지"를 정한다면, 이 문서는 "그 값을 어디서 가져올지"를 정합니다.

| 이런 걸 알고 싶으면 | 이 절을 보세요 |
|---|---|
| API 주소를 어떻게 짓나 | 2장 |
| 서버가 400·409를 주는데 화면에 뭐라고 띄우나 | **3장** + 부록 A |
| 내가 만들 화면이 부를 API가 뭔가 | 4장 · 5장 |
| 이 검증은 언제 도나? 버튼? 밤에? 월말? | **6장** · 7장 |
| 왜 날짜가 세 개나 되나 | **9장** |
| 파일 업로드 화면은 왜 없나 | **10장** |
| 2차에 React로 바꾸면 서버도 다시 만드나 | 11장 |

### 0-2. 어려운 말은 괄호로 풉니다 (문서 규칙)

이 문서는 보험·정산을 처음 보는 팀원이 읽습니다. 그래서 다음 규칙을 지킵니다.

1. 처음 나오는 어려운 말은 반드시 `용어(한 줄 설명)` 형태로 씁니다.
   예) `멱등키(같은 작업을 두 번 해도 결과가 하나만 남게 해 주는 열쇠)`
2. 두 번째부터는 괄호를 생략하고, 대신 **부록 B 용어 사전**을 봅니다.
3. 영문 약어도 첫 등장 시 풉니다.
   예) `Spring Batch(정해진 작업을 단계별로 나눠 대량 처리하는 스프링 기능)`

### 0-3. 이 문서가 정하는 것 / 정하지 않는 것

| 정한다 | 정하지 않는다 (다른 문서 소관) |
|---|---|
| API 주소 · Method · 요청/응답 필드 · 상태코드 | 화면 배치 · 색상 → 화면정의서 v2.0 |
| 오류코드와 화면 문구의 짝 | 계산식 자체 → 운영정책서 v1.0 |
| 배치 Job 이름 · 트리거 · 파라미터 · 멱등키 | 테이블 컬럼 정의 → 스키마 v2.1.7 |
| 검증이 **언제** 실행되는지 (4가지 모드) | 규제 해석 → 규제조문표 v0.2.1 |

## 2. 공통 API 규약

### 2-1. Base path와 인증

| 항목 | 1차 (2026-08-24) | 2차 (2026-11-17) |
|---|---|---|
| 화면 라우트 | `/`, `/contracts`, `/cap-checks` … (Thymeleaf MPA) | React Router (같은 경로 유지) |
| 데이터 API | `/api/v1/**` | **동일** |
| 인증 | Spring Security **폼 로그인**, `POST /login` → 세션 쿠키 `JSESSIONID` | **JWT**(Access + Refresh). 같은 `/api/v1/**` 경로를 그대로 쓴다 |
| 인가 | `@PreAuthorize` + 역할 4종 | 동일 |
| CSRF | 상태를 바꾸는 요청(POST·PUT·DELETE)에 `X-CSRF-TOKEN` 헤더 필수 | 동일 |

역할 4종 — `SYSTEM_ADMIN`(전부) / `GA_ADMIN`(정책·조직 조회, 검증 확정) / `SETTLEMENT`(계약·지급 등록, 검증 실행, 예외 처리) / `COMPLIANCE`(조회만). `SYSTEM_ADMIN`은 "전부"라 §4-2 역할 열에는 따로 적지 않는다 — 역할 열의 `SETTLEMENT`는 SETTLEMENT + SYSTEM_ADMIN을 뜻한다.

> **주의 1**: 로그인 API만 `/api/v1` 밑에 있지 않습니다. Spring Security의 기본 폼 로그인 경로를 그대로 쓰기 때문입니다.
>
> **주의 2 — 왜 처음부터 `/api/v1` 인가**
> 나중에 붙이려면 이미 만들어 둔 화면·문서·테스트의 주소를 전부 고쳐야 합니다.
> 지금 한 글자 더 쓰는 비용이 나중에 52개 경로를 고치는 비용보다 훨씬 쌉니다.
> 2차에서 응답 모양이 바뀌는 API가 생기면 그때 `/api/v2`를 **함께 띄워 두고**
> 1차 화면이 죽지 않게 한 뒤 옮깁니다. 이것이 버전 프리픽스를 두는 이유입니다.

### 2-1-1. 인증 방식 — 1차 세션 / 2차 JWT

| 구분 | 1차 (Thymeleaf MPA) | 2차 (React SPA) |
|---|---|---|
| 방식 | **세션 쿠키** (`JSESSIONID`) | **JWT**(로그인하면 받는 서명된 출입증) |
| 발급 | `POST /login` → 서버 세션 생성 | `POST /api/v1/auth/login` → `accessToken` + `refreshToken` |
| 전달 | 쿠키 자동 전송 | `Authorization: Bearer {accessToken}` 헤더 |
| 만료 | 세션 타임아웃 30분 | Access 30분 / Refresh 14일 |
| 갱신 | 재로그인 | `POST /api/v1/auth/refresh` |
| 로그아웃 | `POST /logout` (세션 삭제) | `POST /api/v1/auth/logout` (Refresh 무효화 목록에 등록) |
| CSRF | **필요** (쿠키를 쓰므로) | 불필요 (헤더 방식) |
| 역할 정보 | 세션에 보관 | JWT `claims.roles` |

**왜 1차는 세션인가** — Thymeleaf는 서버가 화면을 그리므로 세션이 가장 단순하고, 로그아웃 즉시 무효화가 됩니다.
**왜 2차는 JWT인가** — React 앱과 API 서버를 따로 배포하면(ECR-005) 쿠키 도메인·CORS 처리가 번거로워지고, 서버가 세션을 들고 있지 않아야 확장이 쉽습니다.

> **전환 안전장치**: 인증 방식이 바뀌어도 **`/api/v1/**` 경로와 응답 봉투는 그대로**입니다.
> 바뀌는 것은 "누구인지 알아내는 방법" 하나뿐이고, `@PreAuthorize` 인가 규칙은 손대지 않습니다.
> 그래서 1차에 `SecurityConfig`를 만들 때 **인증 필터만 갈아 끼울 수 있게** 분리해 두세요.

### 2-2. 응답 봉투(Envelope)

**봉투**란 실제 내용물을 감싸는 공통 껍데기입니다. 성공이든 실패든 모양이 같아야 화면이 한 가지 방법으로 처리할 수 있습니다.

```jsonc
// 성공 (단건)
{ "data": { ... }, "error": null, "requestId": "20260803-7f3a1c" }

// 성공 (목록)
{ "data": { "content": [ ... ],
            "page": 1, "size": 20, "totalElements": 137, "totalPages": 7,
            "sort": "asOfDate,desc" },
  "error": null, "requestId": "20260803-7f3a1c" }

// 실패
{ "data": null,
  "error": { "code": "FGC-CAP-001",
             "message": "지급 확정 불가 — 1,200% 한도 초과(사용률 104.166667%). 예외함에서 정정·감액·취소를 선택하세요.",
             "field": null,
             "params": { "usagePct": "104.166667", "capCheckId": 4102 },
             "detail": null },
  "requestId": "20260803-7f3a1c" }
```

| 필드 | 뜻 | 규칙 |
|---|---|---|
| `data` | 성공 결과 | 실패 시 항상 `null` |
| `error.code` | 3장 오류코드 | **화면은 코드로 분기한다. 문구로 분기하면 안 된다** |
| `error.message` | **부록 A 표준 문구 그대로** | 서버가 완성해서 보낸다. 화면에서 조립 금지 |
| `error.field` | 입력 항목 오류일 때 필드명 | 폼에서 빨갛게 표시할 칸 |
| `error.params` | 문구의 `{n}` `{a}` `{b}` `{c}` 치환값 | 로그·재현용 |
| `error.detail` | 개발용 상세 | **운영 프로파일에서는 항상 `null`** (내부 구조를 밖으로 흘리지 않는다) |
| `requestId` | 요청추적ID | 로그·감사로그·화면에 같은 값이 찍힌다 |

### 2-3. 페이징 · 정렬 · 검색

| 파라미터 | 기본값 | 규칙 |
|---|---|---|
| `page` | `1` | **1부터 시작.** Spring Data는 0부터라 컨트롤러에서 −1 변환한다 |
| `size` | `20` | 화면 공통규칙과 같다. 최대 100 |
| `sort` | 화면별 기본값 | `필드명,asc\|desc`. 다중 정렬은 `sort` 반복 |
| 검색조건 | — | 전부 쿼리스트링. URL에 남아야 뒤로가기·공유가 된다 |

**목록이 0건인 것은 오류가 아닙니다.** `404`가 아니라 `200 + 빈 배열`로 주고, 화면에서 "조건에 맞는 자료가 없습니다"를 띄웁니다.

### 2-4. 표시 형식 표준 (SIR-008)

| 종류 | API가 보내는 형식 | 화면 표시 | 누가 하나 |
|---|---|---|---|
| 금액 | JSON 숫자, **원 단위 정수** (서버가 이미 `HALF_UP`으로 반올림) | `1,517,944` / 음수 `(1,517,944)` 빨강 | 반올림=서버, 콤마=화면 |
| 요율·사용률 | **문자열** `"104.166667"` | 요율 소수점 4자리, 사용률 6자리 | 서버가 문자열로, 화면은 자르기만 |
| 날짜 | `"2026-07-01"` (`YYYY-MM-DD`) | 동일 | — |
| 일시 | `"2026-08-03T14:05:22+09:00"` (ISO-8601, 오프셋 포함) | `2026-08-03 14:05` | 서버 `Asia/Seoul` 고정 |
| 정산월·귀속월 | `"2026-07-01"` (**항상 그 달 1일**) | `2026-07` | DB CHECK가 강제 |
| 코드값 | 영문 코드(`VIOLATION`) + 한글 라벨(`violationLabel: "위반"`) 동봉 | 배지는 색+글자 | **한글 라벨은 서버가 만든다** |
| 개인정보 | **계약자 개인정보는 응답에 없습니다.** 계약 식별은 `contractNo` | 계약번호로 표시 | 이름·주민번호 모두 저장·전송 없음 (SRC-027 D-05) |

> **요율을 왜 문자열로 보내나요?**
> JSON 숫자는 소수를 정확히 담지 못할 때가 있습니다(`0.1 + 0.2 = 0.30000000000000004`).
> 1,200% 사용률은 소수점 6자리까지 판정에 쓰이므로 문자열로 보내 오차를 없앱니다.

### 2-5. 공통 헤더

| 헤더 | 방향 | 용도 |
|---|---|---|
| `X-CSRF-TOKEN` | 요청 | 상태를 바꾸는 요청에 필수 |
| `X-Request-Id` | 요청(선택) / 응답(항상) | 없으면 서버가 만든다. 감사로그·배치로그와 같은 값 |
| `Idempotency-Key` | 요청(선택) | 되돌릴 수 없는 작업(확정·검증 확정)에 권장 |

## 3. 오류코드 표준 ★ 이 문서의 핵심

### 3-1. HTTP 상태코드 사용 규칙

| 코드 | 언제 |
|---|---|
| `400` | 입력값 자체가 잘못됨 (필수값 누락, 형식 오류) |
| `401` | 로그인 안 됨 / 세션 만료 |
| `403` | 로그인은 됐는데 역할이 부족함 |
| `404` | 그 ID의 자료가 없음. **목록 0건은 404가 아니다** |
| `409` | 이미 있음 / 상태가 안 맞음 (중복키, 확정된 자료 수정) |
| `422` | 형식은 맞지만 **업무 규칙 위반** (한도 초과, 귀속합계 불일치, 확정조건 미충족) |
| `500` | 서버 오류. 사용자에게는 `requestId`만 보여준다 |

### 3-2. 오류코드 × 표준문구 × DB 제약 대조표

**이 표가 곧 `@RestControllerAdvice` 한 클래스의 설계도입니다.**
DB가 던진 제약 이름(`uq_contract_no` 등)을 오류코드로 바꾸는 매핑 테이블로 그대로 쓰세요.

| 오류코드 | HTTP | 발생 API | 무엇이 막나 | 화면 문구 (부록 A 그대로) | 사용자가 할 일 |
|---|---|---|---|---|---|
| `FGC-CAP-001` | 422 | IF-API-25 | 앱 (`cap_check.result_status='VIOLATION'`) | 지급 확정 불가 — 1,200% 한도 초과(사용률 {n}%). 예외함에서 정정·감액·취소를 선택하세요. | 예외함으로 이동 |

### 3-3. 구현 규칙 (SIR-007)

| # | 규칙 |
|---|---|
| 1 | 전부 `@RestControllerAdvice` **한 클래스**에서 처리한다. 컨트롤러 안에 `try-catch`를 쓰지 않는다 |
| 2 | `DataIntegrityViolationException`의 **제약 이름**으로 오류코드를 찾는 매핑을 하나 둔다 → 위 표가 그 매핑이다 |
| 3 | MPA 화면(Thymeleaf)은 같은 예외를 잡아 오류 페이지·토스트로, Ajax는 JSON 봉투로 내보낸다. **코드와 문구는 같아야 한다** |
| 4 | 문구는 `messages_ko.properties`에 키로 두고 코드에 문자열을 직접 쓰지 않는다 |
| 5 | `error.detail`은 운영 프로파일에서 항상 `null`로 만든다 |

## 5. 화면 ↔ API 매핑 (MPA / Ajax) — SIR-006

### 5-1. 왜 나누나

> **MPA**(Multi Page Application: 서버가 HTML 페이지를 통째로 그려서 주는 방식)는 주소를 누를 때마다 화면 전체가 새로 그려집니다.

## 6. 검증 실행 시점 아키텍처 ★ 신설

### 6-1. 왜 이 장이 필요한가

같은 "1,200% 검증"이라도 **언제 도느냐**가 4가지입니다.
이걸 안 정해두면 같은 계산기를 네 번 따로 만들게 되고, 네 개의 답이 서로 달라집니다.

> **FGC는 계산 엔진을 하나만 만들고, 부르는 시점만 4가지로 나눕니다.**

### 6-2. 4가지 실행 모드

| 모드 | 이름 | 언제 | 무엇을 | 누가 부르나 | 결과가 남는 곳 |
|---|---|---|---|---|---|
| ① | **즉시 재계산** | 데이터가 새로 들어오거나 바뀐 직후 | 그 계약만 | 내부 도메인 이벤트(8장) 리스너 | `cap_check(check_kind='REALTIME')`, `schedule_header` 새 버전 |
| ② | **확정 전 차단 검증** | 설계사에게 돈을 확정하기 **직전** | 그 지급 건 + 관련 계약 | `POST /api/v1/transactions/{id}/confirm` (IF-API-25) | `cap_check(check_kind='PRE_CONFIRM')`, `exception_case` |
| ③ | **일일 변경분 보정 배치** | 매일 밤 (프로젝트 운영 가정) | **어제 이후 바뀐 계약만** | `DailyChangedContractJob` (IF-BAT-02) | 각 검증 테이블 + `exception_case` |
| ④ | **월 전체 검증·대사 배치** | 월 정산자료가 모두 들어온 뒤 | 대상월 전 계약 | `MonthlyValidationJob` (IF-BAT-01) | `validation_run` 하위 전부 |

```
데이터 변경 ──────────────► ① 즉시 재계산
                                │
설계사 지급 확정 버튼 ────────► ② 확정 게이트 (막히면 예외 생성)
                                │
매일 밤 (변경분만) ──────────► ③ 일일 보정 배치
                                │
월 자료 도착 후 ─────────────► ④ 월 전체 배치 → 사람 검토 → 확정(FINALIZED)
```

### 6-3. 절대 규칙

| # | 규칙 | 왜 |
|---|---|---|
| 1 | **모든 계약을 매일 전부 재검사하지 않는다.** 일일 배치는 `updated_at > last_processed_at` 인 변경분만 본다 | 계약이 늘어나면 밤에 안 끝난다 |
| 2 | **원수사 데이터 도착 주기를 코드·문서에 고정하지 않는다.** 보험회사와 자료 종류마다 다르고 법정 표준이 아니다 | 이 문서에 적는 "매일 02:00"은 **프로젝트 운영 가정**일 뿐이다 |
| 3 | **상태가 바뀌었다고 전부 재검증하지 않는다. 영향받는 검증만 실행한다** | 6-4 매트릭스의 "즉시" 열이 그 목록이다 |
| 4 | **계산 엔진은 하나다.** `CapValidator` · `ArbitrageValidator` · `ScheduleGenerator`. 모드는 호출자만 다르다 | 즉시 결과와 월 결과가 달라지면 안 된다 |
| 5 | **FINALIZED된 `validation_run`의 결과는 어떤 모드로도 덮어쓰지 않는다.** 새 실행을 만든다 | DB 트리거가 물리적으로 막는다 |

## 7. 배치 인터페이스 (Spring Batch) — 1차부터 사용

### 7-1. 왜 1차부터 Spring Batch인가

월 통합검증은 10단계를 순서대로 돌리고, 중간에 실패하면 **실패한 단계부터** 다시 시작해야 합니다.
이걸 직접 만들면 "어디까지 갔는지" 기록하는 코드를 우리가 짜야 합니다.
**Spring Batch**(정해진 작업을 단계별로 나눠 대량 처리하는 스프링 기능)는 그 기록을 대신 해 줍니다.

1차에서는 Job 2개만 씁니다. 화려한 기능은 쓰지 않습니다.

### 7-2. Job 목록

|---|---|---|---|---|
| **IF-BAT-01** | `MonthlyValidationJob` | **1차** | ④ 월 전체 | `POST /api/v1/validation-runs/{id}/execute` (VRUN-W02 버튼) |
| **IF-BAT-02** | `DailyChangedContractJob` | **1차** | ③ 일일 변경분 | Spring `@Scheduled` (운영 가정: 매일 02:00 KST) + 수동 재실행 |
| IF-BAT-03 | `ScheduleEligibilityJob` | 2차 | ③④ | 월 배치 + 상태 변경 이벤트 |
| IF-BAT-04 | `ReconciliationJob` | 2차 | ④ | 명세 적재 완료 후 |
| IF-BAT-05 | `ArbitrageRecheckJob` | 2차 | ①③ | 실효·해지 이벤트 누적분 |

### 7-3. IF-BAT-01 `MonthlyValidationJob` — Step 정의

제43조 10단계를 **순서대로** 수행합니다. 다만 **Step 과 단계는 1:1이 아닙니다.**

- 6단계는 Step 2개(`journalPostingStep` → `imbalanceCheckStep`)
- 4단계는 partition 2개, 7단계는 지급단계별 2회 실행
- **9·10단계는 Job 이 아닙니다** (사람이 수행)

그래서 **진행률을 `batch_step_execution` 에서 역산하지 마세요.** 매핑이 성립하지 않고,
9·10단계는 Spring Batch 에 Step 자체가 없습니다.
각 Step 은 자기 일을 마치면 **`validation_run.current_step` 을 제43조 단계번호로 갱신**하고,
화면은 그 값만 읽습니다(IF-API-49). 단계 이름은 화면 상수입니다.

| # | 제43조 단계 | Step 이름 | 입력 → 출력 | 멱등키 (중복을 막는 열쇠) | 실패 시 |
|---|---|---|---|---|---|
| 1 | ①대상월 실행 생성 | `createRunStep` | JobParameter → `validation_run` | `uq_validation_run (validation_month, run_no)` + 부분 UNIQUE(진행중 1건) | 즉시 FAILED |
| 2 | ②계약·상품버전·환급률표 선별 | `selectTargetStep` | `insurance_contract`, `product_offering`, `refund_rate_table` → `validation_target` | `uq_validation_target (validation_run_id, contract_id)` | 재시작 시 이 Step부터 |
| 3 | ③현행 예상 스케줄 생성·재검증 | `regenerateScheduleStep` | `validation_target` → `schedule_header/line` | 활성 OPERATIONAL 부분 UNIQUE + `uq_schedule_line_business` | 계약 단위 skip → `exception_case(DATA_QUALITY)` |
| 4 | ④지급단계별 1,200% 검증 | `capCheckStep` (**partition 2개**: `INSURER_TO_GA` / `GA_TO_FC`) | `transaction_attribution`, `cap_rule_set` → `cap_check`, `cap_check_detail` | `uq_cap_check_monthly (validation_run_id, contract_id, payment_stage)` | skip 한도 100건 |
| 5 | ⑤차익거래 검증 | `arbitrageCheckStep` | `contract_financial_snapshot`, `contract_status_event`(**effective_at 기준**) → `arbitrage_check` | `uq_arbitrage_check (validation_run_id, contract_id, payment_stage, as_of_date)` | skip |
| 6 | ⑥검증원장 기표·균형검사 | `journalPostingStep` → `imbalanceCheckStep` | `schedule_line`, `commission_transaction` → `journal_header/line` | `(journal_type, source_entity_type, source_entity_id) WHERE status='POSTED'` | **불균형이 1건이라도 있으면 Step 실패** |
| 7 | ⑦양방향 대사 | `reconciliationStep` (**지급단계 2회**) | `schedule_line` ↔ `transaction_attribution` → `reconciliation_run/result/match` | `uq_reconciliation_result (reconciliation_run_id, match_group_key)` | skip |
| 8 | ⑧예외 생성 | `exceptionGenerationStep` | 위 결과 전부 → `exception_case`, `exception_action` | **`uq_exception_key (exception_key)`** | — |
| — | ⑨담당자 검토 | **Job 아님** | 사람이 EXCP-W01 · VRUN-W02에서 처리 | — | — |
| — | ⑩확정 | **Job 아님** | `POST /api/v1/validation-runs/{id}/finalize` (IF-API-51) | — | — |

> ## ★ 10단계 중 ⑨담당자 검토와 ⑩확정은 배치가 하지 않습니다.
> **사람이 검토하고 사람이 확정합니다.**
> 배치가 자동으로 확정해 버리면, 규제 검증 시스템을 만든 이유 자체가 사라집니다.

**`exception_key` 조립 규칙** (동결 대상):

```
{exceptionType}:{validationRunId}:{sourceEntityType}:{sourceEntityId}:{paymentStage?}

예) CAP_VIOLATION:118:cap_check:4104:GA_TO_FC
    RECONCILIATION_MISMATCH:118:reconciliation_result:7002
```

이 키에 UNIQUE 제약이 걸려 있어서, 배치를 몇 번 다시 돌려도 **예외는 1건만** 생깁니다.

### 7-4. IF-BAT-01 JobParameters

| 파라미터 | 타입 | 필수 | 예시 | 비고 |
|---|---|---|---|---|
| `validationMonth` | String `yyyy-MM` | O | `2026-07` | 내부에서 그 달 1일 date로 변환 |
| `runNo` | Long | O | `1` | `uq_validation_run`의 두 번째 열쇠 |
| `runType` | String | O | `MONTHLY` | `MONTHLY` / `MANUAL_CONTRACT` / `PRE_CONFIRM` |
| `triggeredBy` | Long | O | `12` (`app_user.user_id`) | 감사로그용 |
| `requestId` | String | O | `20260803-7f3a1c` | 2-5절 헤더와 같은 값 |

> **주의**: Spring Batch는 "같은 JobParameters면 같은 Job 인스턴스"로 봅니다.
> `runNo`를 파라미터에 넣어야 같은 달 2회차 실행이 새 인스턴스가 됩니다.

### 7-5. IF-BAT-02 `DailyChangedContractJob`

| 항목 | 내용 |
|---|---|
| 목적 | 어제 밤 이후 **바뀐 계약만** 다시 확인 (모드 ③) |
| Reader | `JdbcPagingItemReader` — `WHERE c.updated_at > :lastProcessedAt` **OR** `EXISTS (SELECT 1 FROM contract_status_event e WHERE e.contract_id = c.contract_id AND NOT EXISTS (SELECT 1 FROM contract_status_event_processing p WHERE p.contract_status_event_id = e.contract_status_event_id AND p.processing_job = :jobName AND p.processing_status = 'SUCCEEDED'))` — **`e.processed_at IS NULL` 금지.** 처리 여부는 Job별로 판단한다 |
| 대상 검증 | 6-4 매트릭스의 "일일 변경분 = O" 행만. **1차**: 1,200% 누적 · 차익거래 · 원장 불균형 재검사 |
| Writer | 해당 검증 테이블 + `exception_case` |
| 워터마크 | **`batch_watermark` 테이블** (스키마 v2.1.3에서 신설) + **`contract_status_event_processing`**의 Job별 처리이력 |
| 멱등성 | `run_type='MANUAL_CONTRACT'`인 `validation_run`을 하루 1건 만들어 그 밑에 결과를 붙인다 → 기존 UNIQUE 제약이 그대로 작동 |
| 실패·재시작 | **워터마크는 Step이 성공한 뒤에만 전진**시킨다. 실패하면 다음 날 같은 구간을 다시 읽지만 UNIQUE가 중복을 막는다 |
| 처리량 가정 | 1차 시연 시드 기준 수백 건. chunk size 100 |

**워터마크(watermark)란** — "여기까지는 처리했다"고 표시해 두는 기준선입니다.
강물에 남은 물자국처럼, 다음에는 그 위(그 이후)만 보면 됩니다.

### 7-6. 배치 공통 규칙

| # | 규칙 |
|---|---|
| 1 | 모든 Writer는 **UPSERT 또는 `ON CONFLICT DO NOTHING`**. "지웠다 다시 넣기" 금지 |
| 2 | Job 실행 이력은 Spring Batch 메타테이블에, **업무 결과는 `validation_run`에** 남긴다. 화면은 `validation_run`만 본다 |
| 3 | 재시작은 실패한 Step부터. 앞 Step 결과는 UNIQUE 덕분에 그대로 살아있다 |
| 4 | **1차에서는 자동 재시작을 만들지 않는다** (FUN-045는 2차). 실패하면 사람이 VRUN-W02에서 새 실행을 만든다 |
| 5 | 배치가 남기는 감사로그의 `user_id`는 `triggeredBy`, `request_id`는 JobParameter 값 |
| 6 | **배치는 자금이체를 하지 않는다** (COR-001). 배치의 출력물은 검증 결과·분개·예외뿐이다 |
| 7 | 배치가 도는 시각("매일 02:00")은 **프로젝트 운영 가정**이다. 법정 기준이 아니므로 설정값으로 둔다 |

## 8. 내부 도메인 이벤트 계약

### 8-1. 전제

> **Kafka도 MSA도 없습니다** (COR-006).
> 전부 **한 애플리케이션 안**의 Spring `ApplicationEvent`입니다.
> 이벤트는 "다른 모듈에 알려주는 메모"일 뿐, 네트워크를 타지 않습니다.

### 8-2. 이벤트 표

| IF ID | 이벤트 | 발행 시점 | 발행 → 구독 | 페이로드 핵심 | 모드 | 트랜잭션 |
|---|---|---|---|---|---|---|
| IF-EVT-01 | `ContractIssued` | `POST /api/v1/contracts` 커밋 후 | 계약 → 스케줄·한도 | `contractId`, `productOfferingId`, `monthlyEquivalentFirstPremium`, `contractDate` | ① | AFTER_COMMIT |
| IF-EVT-02 | `CommissionAccrued` | 지급 건 확정 시 | 지급 → 원장·한도 | `commissionTransactionId`, `attributionIds[]`, `amount`, `paymentStage`, `ruleRef` | ①② | **같은 트랜잭션** |
| IF-EVT-03 | `ContractStatusChanged` **(신규)** | `contract_status_event` 적재 후 | 계약 → 차익거래·스케줄·(2차)환수 | `contractId`, `previousStatus`, `newStatus`, **`effectiveAt`, `receivedAt`**, `sourceSystem`, `sourceEventKey` | ① | AFTER_COMMIT |
| IF-EVT-04 | `PolicyLapsed` → `ClawbackTriggered` | 실효·해지 확정 시 | 계약 → 수수료·(2차)환수 | `contractId`, `lapseEffectiveAt`, `reasonCode` | ① | AFTER_COMMIT |
| IF-EVT-05 | `CapExceeded` | `cap_check.result_status='VIOLATION'` 저장 시 | 한도 → 예외·대시보드 | `capCheckId`, `contractId`, `paymentStage`, `usagePct`, `limitAmount`, `includedAmount` | ①② | **같은 트랜잭션** |
| IF-EVT-06 | `SettlementPosted` | 월 배치 Step6 완료 시 | 원장 → 대시보드 | `validationRunId`, `journalCount`, `imbalanceCount` | ④ | AFTER_COMMIT |
| IF-EVT-07 | `ValidationRunFinalized` **(신규)** | `POST /.../finalize` 성공 시 | 검증 → 전 화면 잠금·감사로그 | `validationRunId`, `validationMonth`, `finalizedBy`, `finalizedAt` | ④ | AFTER_COMMIT |

### 8-3. 이벤트 설계 규칙

| # | 규칙 | 왜 |
|---|---|---|
| 1 | 이벤트에 **금액 계산 결과를 담지 않는다.** ID만 담고 구독자가 다시 읽는다 | 같은 계산을 두 곳에서 하면 값이 갈라진다 |
| 2 | 확정 게이트에 관여하는 이벤트(`CommissionAccrued`, `CapExceeded`)는 **같은 트랜잭션**. 나머지는 `AFTER_COMMIT` | 차단됐는데 예외가 안 만들어지면 안 된다 |
| 3 | `AFTER_COMMIT` 리스너에서 예외가 나면 **로그 + `exception_case(DATA_QUALITY)`**. 원 요청을 되돌리지 않는다 | 이미 커밋된 계약 등록을 취소할 수는 없다 |
| 4 | 2차에도 이 계약을 유지한다 | 나중에 메시지 큐로 바꿀 때 payload가 그대로 메시지가 되도록 |

## 9. 세 날짜 규약과 지연도착 처리 ★ 신설

### 9-1. 세 날짜

계약 상태를 그냥 "2026-08-16에 입력됨" 정도로만 저장하면 안 됩니다. 세 시점을 나눠야 합니다.

| 날짜 | 컬럼 | 한 줄 뜻 | 반드시 이걸로 판단하는 것 | 절대 이걸로 판단하면 안 되는 것 |
|---|---|---|---|---|
| **효력 발생** | `contract_status_event.effective_at` | 실제로 그 일이 일어난 날 (해지된 날) | **수수료 자격 · 차익거래 판정 · 초년도 구간 · 계약 이력 재구성 순서** | — |
| **수신** | `contract_status_event.received_at` | FGC DB가 그 사실을 받은 날 | 지연 모니터링, "왜 어제 결과와 다른가" 설명 | 수수료 자격 판단 |
| **처리** | `contract_status_event_processing.processed_at` (**Job별**) | 특정 Job이 그 사건을 처리한 날 | **재처리 대상 선별**(해당 Job의 성공행이 없으면 아직 안 봄), 감사 | 수수료 자격 판단, **다른 Job의 처리 완료 여부** |

```
9/01 계약 해지 발생 ─────────► 9/02 FGC DB 수신 ─────────► 9/03 02:00 배치 처리
   effective_at                   received_at        contract_status_event_processing
                                                       .processed_at (processing_job별)
   └─ 차익거래·수수료 자격은 이 날짜로 판단한다 ─┘
```

> ⚠️ **`contract_status_event.processed_at`은 v2.1.6부터 폐기 예정 호환 컬럼이다.**
> 신규 코드에서 읽거나 쓰지 않는다. 처리 여부는 사건 하나에 하나가 아니라
> **`processing_job`별로** 따로 존재하므로, 한 Job의 성공을 다른 Job의 처리완료로
> 간주하면 안 된다. 실패는 재시도마다 새 행으로 남고 사건×Job의 성공행은 최대 1건이다.
> (운영정책서 제7장 · 시드데이터명세서 §33)

### 9-2. API 노출 규칙

| 규칙 |
|---|
| 상태 이력을 주는 모든 API(IF-API-16 · IF-API-12)는 **세 날짜를 전부 내보낸다.** 하나만 주면 화면에서 잘못 쓴다 |
| 처리일은 **단일 필드가 아니라 `processings[]` 배열**이다. 사건 하나가 Job마다 따로 처리되므로 `processedAt` 하나만 주면 한 Job의 성공을 전체 처리완료로 오인한다 |
| 아직 어떤 Job도 처리하지 않았으면 `processings`는 **빈 배열**이다. `null`이 아니다 |
| 화면 표기: `효력 2026-09-01 · 수신 2026-09-02 · 처리 DailyChangedContractJob 2026-09-03` (미처리 Job은 "대기") |
| 이력 정렬 기본값은 **`effectiveAt,asc`**. `receivedAt` 정렬은 "도착 순서 보기" 토글로만 |

### 9-3. 순서역전 · 지연도착 처리

| 상황 | 규칙 |
|---|---|
| 수신 순서가 효력 순서와 다름 (8/16에 8/14 실효, 8/17에 8/12 미납 수신) | 계약 이력 재구성은 **`effective_at ASC, event_seq ASC`** 로 정렬해서 다시 만든다. **수신순 절대 금지** |
| 같은 `effective_at`에 두 건 | `source_version`이 큰 것을 최신으로. 없으면 `event_seq`가 큰 것 |
| 같은 사건이 두 번 수신 | `UNIQUE(source_system, source_event_key)`가 물리적으로 차단 → API는 `409`가 아니라 **`200 + "이미 반영됨"`**으로 응답한다 (재전송은 정상 상황이다) |
| 이미 검증이 끝난 달에 늦게 도착 | ① 그 사건에 **해당 Job의 성공 처리행을 남기지 않아** 다음 일일 배치가 잡게 한다 ② 결과는 **새 `validation_run`**에 남긴다 ③ **FINALIZED된 run은 절대 수정하지 않는다** |
| 원수사 도착 주기 | **고정하지 않는다.** 문서에 적는 "매일 02:00", "월말 후 5영업일"은 전부 *프로젝트 운영 가정*이다 |

### 9-4. 미납과 실효는 다릅니다 (자주 틀리는 부분)

| 상태 | 뜻 | 지급 처리 |
|---|---|---|
| **미납**(UNPAID) | 보험료를 아직 안 냈다. 계약이 끝난 것은 아니다 | 회사 정책에 따라 **보류**할 수 있다. 미래 수수료를 곧바로 영구 중단하면 안 된다 |
| **실효**(LAPSED) | 미납 등으로 계약의 효력이 실제로 정지됐다 | 미래 지급회차 보류·중단. 차익거래 즉시 실행 |
| **부활**(REVIVED) | 실효된 계약이 다시 살아났다 | 미래 회차 재개 여부를 정책으로 판단 |
| **해지**(TERMINATED) | 계약이 끝났다 | 미래 유지관리 회차 중단. 환수 후보 생성 |

> **미래 회차를 안 주는 것**과 **이미 준 돈을 되받는 것(환수)**은 다릅니다(REG-13).

### 9-5. 월중 실효·부활 시 그 달 수수료 처리 — `STATUS_MONTH_RULE`

**문제**: 9월 1일에 실효된 계약의 9월분 유지관리수수료를 줘야 할까요, 말아야 할까요?
9월 15일에 부활했다면 9월분을 다시 줘야 할까요?

법정 확정 기준을 아직 확보하지 못했습니다. 그래서 **파라미터로 두고 기본값을 정합니다.**
이 값은 `policy_version.source_class = 'PROJECT_ASSUMPTION'`으로 저장되어
화면에 <strong>주황색 "프로젝트 가정" 배지</strong>가 붙습니다. 법정 기준이 아니라는 뜻입니다.

#### 채택한 기본값 (3개 파라미터)

| 파라미터 | 채택값 | 뜻 |
|---|---|---|
| `STATUS_MONTH_RULE` | **`PAY_IF_ACTIVE_ON_DUE_DATE`** | 그 회차의 **지급예정일(`schedule_line.due_date`) 시점**에 계약이 유효했으면 그 회차를 지급한다 |
| `PRORATION_RULE` | **`NO_PRORATION`** | 일할계산하지 않는다. 주거나 안 주거나 둘 중 하나다 |
| `REVIVAL_BACKFILL_RULE` | **`NO_RETROACTIVE`** | 부활해도 실효 기간에 건너뛴 회차를 소급해 주지 않는다. 부활일 이후 회차부터 재개한다 |

#### 왜 이 값들인가

| # | 근거 |
|---|---|
| 1 | **`NO_PRORATION`이 규제와 맞습니다.** 유지관리수수료는 "**매월 동일 금액**"이어야 합니다(REG-03). 일할계산을 하면 어떤 달만 금액이 달라져 이 요건과 정면으로 충돌합니다 |
| 2 | **`due_date` 기준이 데이터로 명확합니다.** 스케줄에 이미 지급예정일이 있고, 대사(reconciliation)의 매칭키도 회차+지급예정일입니다. **검증과 대사가 같은 기준을 쓰면 결과가 갈라지지 않습니다** |
| 3 | **`END_OF_MONTH_STATUS`(월말 상태로 판단)를 쓰지 않은 이유** — 월말 하루의 상태로 한 달 전체를 판단하면, 9/2 실효 → 9/28 부활한 계약과 9/28 실효한 계약이 정반대 결과가 됩니다. 사람이 설명하기 어렵습니다 |
| 4 | **`FULL_MONTH_REQUIRED`(그 달 내내 유지)를 쓰지 않은 이유** — 가장 보수적이지만, 월중 부활한 계약은 영원히 그 달을 못 받습니다. 부활 제도의 취지와 맞지 않습니다 |
| 5 | **`NO_RETROACTIVE`인 이유** — 실효 기간에는 **실제로 유지관리 서비스가 없었습니다.** 유지관리수수료는 "계약 유지기간에 한정"됩니다(REG-03). 안 한 일에 대가를 주면 그 자체가 규제 위반 소지입니다 |
| 6 | **미납(UNPAID)은 중단이 아니라 보류입니다.** 미납만으로 미래 수수료를 영구 중단하지 않습니다. `HOLD`로 두었다가 실효되면 중단, 납입이 재개되면 그대로 지급합니다 |

#### 상태별 처리표

| 그 회차 지급예정일 시점의 계약 상태 | 그 회차 처리 | `schedule_line.line_status` |
|---|---|---|
| 정상(ACTIVE) · 부활(REVIVED) | **지급** | `PLANNED` → `CONFIRMED` |
| 미납(UNPAID) | **보류** (납입 재개 시 그대로 지급) | `HOLD` |
| 실효(LAPSED) | **미지급** (소급하지 않음) | `CANCELLED` |
| 해지(TERMINATED) · 만기(MATURED) | **미지급**, 이후 회차 전부 중단 | `CANCELLED` |
| 청약철회(CANCELLED) | **미지급** + 기지급분은 환수 후보 | `CANCELLED` |

#### 예시

```
계약 C-1001 · 유지관리수수료 지급예정일 = 매월 25일

 9월분 (예정일 9/25):  9/01 실효 → 9/25 시점 실효   → 미지급 (CANCELLED)
10월분 (예정일 10/25): 10/15 부활 → 10/25 시점 정상  → 지급   (CONFIRMED)
 9월분 소급 지급?      → 하지 않음 (NO_RETROACTIVE)
```

| 화면 표시 | POL-W01 정책 버전 탭에 **주황색 "프로젝트 가정" 배지**로 노출 |

## 10. 외부 인터페이스 — **없음** (COR-010)

### 10-1. 선언

> ## FGC는 1차·2차 모두 외부 시스템과 연결되는 인터페이스가 **0개**입니다.

## 부록 B. 이 문서에만 나오는 용어 한 줄 사전

화면정의서 부록 B와 겹치지 않는 것만 적었습니다.

| 용어 | 한 줄 설명 |
|---|---|
| **API** | 화면이 서버에 "이 자료 주세요"라고 부르는 주소와 약속 |
| **REST** | 주소와 HTTP 동사(GET·POST 등)로 자원을 다루는 API 설계 방식 |
| **MPA** | 서버가 HTML 페이지를 통째로 그려서 주는 방식. 주소를 누르면 화면 전체가 새로 그려진다 |
| **SPA** | 첫 화면만 받아 두고 그 뒤엔 데이터만 받아 화면을 바꾸는 방식 (2차 React) |
| **Ajax** | 페이지는 그대로 두고 화면 일부만 서버에서 값을 받아 다시 그리는 것 |
| **응답 봉투(Envelope)** | 성공이든 실패든 똑같은 모양으로 감싸는 공통 껍데기 (`data` / `error` / `requestId`) |
| **요청추적ID(requestId)** | 이 요청 하나에 붙는 번호. 로그·감사로그·화면에 같은 값이 찍혀 나중에 되짚을 수 있다 |
| **멱등키(Idempotency Key)** | 같은 작업을 두 번 해도 결과가 하나만 남게 해 주는 열쇠 |
| **멱등성** | 같은 작업을 여러 번 해도 결과가 한 번 한 것과 같은 성질 |
| **워터마크** | "여기까지 처리했다"고 표시해 두는 기준선. 다음엔 그 이후만 읽는다 |
| **부분 UNIQUE 인덱스** | 특정 조건을 만족하는 행들 사이에서만 중복을 막는 제약 |
| **트리거** | DB가 어떤 일이 생기면 자동으로 실행하는 검사·동작 |
| **UPSERT** | 있으면 고치고 없으면 넣는 저장 방식 |
| **Spring Batch** | 정해진 작업을 단계별로 나눠 대량 처리하는 스프링 기능 |
| **Job / Step** | 배치의 전체 작업 단위(Job)와 그 안의 한 단계(Step) |
| **JobParameter** | 배치를 돌릴 때 넘기는 값. 같은 값이면 같은 실행으로 본다 |
| **chunk** | 배치가 한 번에 읽고 쓰는 묶음 크기 |
| **AFTER_COMMIT** | DB 저장이 확정된 뒤에 실행하라는 표시 |
| **CSRF** | 사용자가 모르는 사이에 다른 사이트가 요청을 보내는 공격. 토큰으로 막는다 |
| **폴링(polling)** | 화면이 몇 초마다 서버에 "끝났나요?" 물어보는 방식 |
| **스테이징** | 정식 테이블에 넣기 전에 임시로 담아 두는 자리 (FGC에는 없다) |
| **순서역전** | 나중에 일어난 일이 먼저 도착하는 상황 |
| **효력일 / 수신일 / 처리일** | 9장 참조. 각각 실제로 일어난 날 / DB가 받은 날 / 검증을 돌린 날 |
