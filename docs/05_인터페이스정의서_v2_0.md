## 0. 이 문서를 읽는 법 (5분)

### 0-1. 이 문서는 무엇인가

화면과 서버가 **어떤 주소로 · 무엇을 주고받는지**를 적은 약속입니다.
화면정의서가 "무엇을 보여줄지"를 정한다면, 이 문서는 "그 값을 어디서 가져올지"를 정합니다.

| 이런 걸 알고 싶으면 | 이 절을 보세요 |
|---|---|
| API 주소를 어떻게 짓나 | 2장 |
| 서버가 400·409를 주는데 화면에 뭐라고 띄우나 | **3장** + 부록 A |
| 내가 만들 화면이 부를 API가 뭔가 | 4장 · 5장 |
| 이 검증은 언제 도나? 버튼? 밤에? 월말? | **6장** · 7장 |
| 왜 날짜가 세 개나 되나 | **9장** |
| 파일 업로드 화면은 왜 없나 | **10장** |
| 2차에 React로 바꾸면 서버도 다시 만드나 | 11장 |

### 0-2. 어려운 말은 괄호로 풉니다 (문서 규칙)

이 문서는 보험·정산을 처음 보는 팀원이 읽습니다. 그래서 다음 규칙을 지킵니다.

1. 처음 나오는 어려운 말은 반드시 `용어(한 줄 설명)` 형태로 씁니다.
   예) `멱등키(같은 작업을 두 번 해도 결과가 하나만 남게 해 주는 열쇠)`
2. 두 번째부터는 괄호를 생략하고, 대신 **부록 B 용어 사전**을 봅니다.
3. 영문 약어도 첫 등장 시 풉니다.
   예) `Spring Batch(정해진 작업을 단계별로 나눠 대량 처리하는 스프링 기능)`

### 0-3. 이 문서가 정하는 것 / 정하지 않는 것

| 정한다 | 정하지 않는다 (다른 문서 소관) |
|---|---|
| API 주소 · Method · 요청/응답 필드 · 상태코드 | 화면 배치 · 색상 → 화면정의서 v2.0 |
| 오류코드와 화면 문구의 짝 | 계산식 자체 → 운영정책서 v1.0 |

## 2. 공통 API 규약

### 2-1. Base path와 인증

| 항목 | 1차 (2026-08-24) | 2차 (2026-11-17) |
|---|---|---|
| 화면 라우트 | `/`, `/contracts`, `/cap-checks` … (Thymeleaf MPA) | React Router (같은 경로 유지) |
| 데이터 API | `/api/v1/**` | **동일** |
| 인증 | Spring Security **폼 로그인**, `POST /login` → 세션 쿠키 `JSESSIONID` | **JWT**(Access + Refresh). 같은 `/api/v1/**` 경로를 그대로 쓴다 |
| 인가 | `@PreAuthorize` + 역할 4종 | 동일 |
| CSRF | 상태를 바꾸는 요청(POST·PUT·DELETE)에 `X-CSRF-TOKEN` 헤더 필수 | Bearer 요청은 **불필요**. Refresh 쿠키를 쓰는 `/api/v1/auth/**`만 별도 방어 — §2-1-1 "CSRF 판정" |

역할 4종 — `SYSTEM_ADMIN`(전부) / `GA_ADMIN`(정책·조직 조회, 검증 확정) / `SETTLEMENT`(계약·지급 등록, 검증 실행, 예외 처리) / `COMPLIANCE`(조회만). `SYSTEM_ADMIN`은 "전부"라 §4-2 역할 열에는 따로 적지 않는다 — 역할 열의 `SETTLEMENT`는 SETTLEMENT + SYSTEM_ADMIN을 뜻한다.

> **주의 1**: 1차에서는 로그인 API만 `/api/v1` 밑에 있지 않습니다. Spring Security의 기본 폼 로그인 경로를 그대로 쓰기 때문입니다. 2차 로그인은 `POST /api/v1/auth/login`입니다(§2-1-1).
>
> **주의 2 — 왜 처음부터 `/api/v1` 인가**
> 나중에 붙이려면 이미 만들어 둔 화면·문서·테스트의 주소를 전부 고쳐야 합니다.
> 지금 한 글자 더 쓰는 비용이 나중에 52개 경로를 고치는 비용보다 훨씬 쌉니다.
> 2차에서 응답 모양이 바뀌는 API가 생기면 그때 `/api/v2`를 **함께 띄워 두고**
> 1차 화면이 죽지 않게 한 뒤 옮깁니다. 이것이 버전 프리픽스를 두는 이유입니다.

### 2-1-1. 인증 방식 — 1차 세션 / 2차 JWT

| 구분 | 1차 (Thymeleaf MPA) | 2차 (React SPA) |
|---|---|---|
| 방식 | **세션 쿠키** (`JSESSIONID`) | **JWT**(로그인하면 받는 서명된 출입증) |
| 발급 | `POST /login` → 서버 세션 생성 | `POST /api/v1/auth/login` → 응답 본문 `accessToken`, Refresh는 `Set-Cookie`(`HttpOnly; Secure; SameSite=Strict; Path=/api/v1/auth`) |
| 보관 | 브라우저 쿠키 | Access는 **메모리만**(localStorage·sessionStorage 금지), Refresh는 HttpOnly 쿠키라 스크립트가 읽을 수 없음 |
| 전달 | 쿠키 자동 전송 | `Authorization: Bearer {accessToken}` 헤더 |
| 만료 | 세션 타임아웃 30분 | Access 30분 / Refresh 14일 |
| 갱신 | 재로그인 | `POST /api/v1/auth/refresh` (Refresh 쿠키로 새 Access 발급, Refresh는 회전·재사용 시 무효화) |
| 로그아웃 | `POST /logout` (세션 삭제) | `POST /api/v1/auth/logout` (서버 `auth_refresh_token`에서 무효화 + 쿠키 삭제) |
| CSRF | **필요** (쿠키를 쓰므로) | Bearer로 인증하는 `/api/v1/**`는 **불필요**. Refresh 쿠키를 쓰는 `/api/v1/auth/{login,refresh,logout}`은 아래 방어 적용 |
| 동시 로그인 | 제한 없음 | **계정당 1곳만**. 새로 로그인하면 그 계정의 이전 Refresh를 전부 무효화하고, 이전 Access도 다음 요청에서 `401 FGC-AUTH-004`로 끊는다(Access의 `sid`가 무효화된 로그인을 가리키면 거절) |
| 역할 정보 | 세션에 보관 | JWT `claims.roles`는 화면 표시용. **권한 판정은 요청마다 DB에서 다시 읽은 역할**로 한다(역할 회수 즉시 반영) |

**CSRF 판정 (2026-10-05, GitHub 이슈 #400, SRC-028)**

CSRF는 브라우저가 **자동으로 붙이는 자격증명**(쿠키)을 노린 공격입니다. 그래서 자격증명이 무엇이냐에 따라 나눕니다.

| 요청 | 자격증명 | CSRF 방어 | 이유 |
|---|---|---|---|
| `/api/v1/**` 업무 API (Bearer) | `Authorization` 헤더 — 스크립트가 직접 붙여야 함 | **불필요** | 다른 사이트는 메모리의 Access 토큰을 모르고, 브라우저가 이 헤더를 자동으로 붙이지 않는다 |
| `/api/v1/auth/login·refresh·logout` | Refresh 쿠키(자동 전송됨) | **필요** — ① `SameSite=Strict` ② `Origin` 헤더가 서비스 출처와 같아야 함(없거나 `null`이면 거절) ③ 사용자 지정 헤더 `X-FGC-Client: web` 필수(없으면 403) | 쿠키가 자동으로 실리는 유일한 경로. ③은 OWASP CSRF Cheat Sheet "Employing Custom Request Headers for AJAX/API"(사용자 지정 헤더는 교차 출처에서 preflight 없이 못 붙임), ①은 같은 문서 "Defense In Depth — SameSite"(단독 방어로 쓰지 않음), ②는 같은 문서 "Using Standard Headers to Verify Origin" (2026-10-05 확인) |
| 공존기(웨이브 C 전) 세션 요청 — Thymeleaf 화면의 Ajax | `JSESSIONID` 쿠키 | **1차와 동일하게 `X-CSRF-TOKEN` 유지** | 세션이 살아 있는 동안 CSRF를 끄면 위조 요청이 통한다. 공존기에는 Bearer 요청만 CSRF에서 면제한다 |

> 웨이브 C(Thymeleaf·세션 제거)에서 `/api/v1/**` 체인은 `STATELESS` + `csrf.disable()`로 정리하고, `/api/v1/auth/**`의 ①②③ 방어는 남긴다.
> **왜 Refresh를 응답 본문이 아니라 쿠키로 주나** — 본문으로 받으면 스크립트가 어딘가에 저장해야 하고, XSS 한 번에 14일짜리 토큰이 빠져나간다. HttpOnly 쿠키는 스크립트가 못 읽는다. 대신 쿠키라서 CSRF 방어가 필요하므로, 그 범위를 `/api/v1/auth/**` 세 개로 좁혔다.

**왜 1차는 세션인가** — Thymeleaf는 서버가 화면을 그리므로 세션이 가장 단순하고, 로그아웃 즉시 무효화가 됩니다.
**왜 2차는 JWT인가** — React 앱과 API 서버를 따로 배포하면(ECR-005) 쿠키 도메인·CORS 처리가 번거로워지고, 서버가 세션을 들고 있지 않아야 확장이 쉽습니다.

> **전환 안전장치**: 인증 방식이 바뀌어도 **`/api/v1/**` 경로와 응답 봉투는 그대로**입니다.
> 바뀌는 것은 "누구인지 알아내는 방법" 하나뿐이고, `@PreAuthorize` 인가 규칙은 손대지 않습니다.
> 그래서 1차에 `SecurityConfig`를 만들 때 **인증 필터만 갈아 끼울 수 있게** 분리해 두세요.

### 2-2. 응답 봉투(Envelope)

**봉투**란 실제 내용물을 감싸는 공통 껍데기입니다. 성공이든 실패든 모양이 같아야 화면이 한 가지 방법으로 처리할 수 있습니다.

```jsonc
// 성공 (단건)
{ "data": { ... }, "error": null, "requestId": "20260803-7f3a1c" }

// 성공 (목록)
{ "data": { "content": [ ... ],
            "page": 1, "size": 20, "totalElements": 137, "totalPages": 7,
            "sort": "asOfDate,desc" },
  "error": null, "requestId": "20260803-7f3a1c" }

// 실패
{ "data": null,
  "error": { "code": "FGC-CAP-001",
             "message": "지급 확정 불가 — 1,200% 한도 초과(사용률 104.166667%). 예외함에서 정정·감액·취소를 선택하세요.",
             "field": null,
             "params": { "usagePct": "104.166667", "capCheckId": 4102 },
             "detail": null },
  "requestId": "20260803-7f3a1c" }
```

| 필드 | 뜻 | 규칙 |
|---|---|---|
| `data` | 성공 결과 | 실패 시 항상 `null` |
| `error.code` | 3장 오류코드 | **화면은 코드로 분기한다. 문구로 분기하면 안 된다** |
| `error.message` | **부록 A 표준 문구 그대로** | 서버가 완성해서 보낸다. 화면에서 조립 금지 |
| `error.field` | 입력 항목 오류일 때 필드명 | 폼에서 빨갛게 표시할 칸 |
| `error.params` | 문구의 `{n}` `{a}` `{b}` `{c}` 치환값 | 로그·재현용 |
| `error.detail` | 개발용 상세 | **운영 프로파일에서는 항상 `null`** (내부 구조를 밖으로 흘리지 않는다) |
| `requestId` | 요청추적ID | 로그·감사로그·화면에 같은 값이 찍힌다 |

### 2-3. 페이징 · 정렬 · 검색

| 파라미터 | 기본값 | 규칙 |
|---|---|---|
| `page` | `1` | **1부터 시작.** Spring Data는 0부터라 컨트롤러에서 −1 변환한다 |
| `size` | `20` | 화면 공통규칙과 같다. 최대 100 |
| `sort` | 화면별 기본값 | `key,asc\|desc` 한 개(#604). 목록마다 **허용 key가 정해져 있고**(§2-3A) 그 밖의 key·방향·형식은 `400 FGC-COMMON-002`(`field=sort`)다. 다중 정렬은 지원하지 않는다. 응답의 `sort`는 실제 적용한 정렬(`key,asc\|desc`)이다 |
| 검색조건 | — | 전부 쿼리스트링. URL에 남아야 뒤로가기·공유가 된다 |

**목록이 0건인 것은 오류가 아닙니다.** `404`가 아니라 `200 + 빈 배열`로 주고, 화면에서 "조건에 맞는 자료가 없습니다"를 띄웁니다.

#### 2-3A. 목록 컬럼별 정렬 허용 key (#604)

공통 규칙: ① 검색된 **전체 데이터**를 정렬한 뒤 `page`·`size`로 자른다(현재 페이지만 정렬하지 않는다). ② 숫자·금액·날짜는 표시 문자열이 아니라 **실제 값**으로 비교한다. ③ 값이 `NULL`인 행은 `asc`·`desc` 모두 **맨 뒤**에 둔다. ④ 값이 같은 행은 각 목록의 기존 기본 순서로 고정해 같은 요청이 항상 같은 순서가 되게 한다. ⑤ `sort`를 주지 않으면 아래 "기본"을 그대로 쓰며 응답이 달라지지 않는다. ⑥ 지급단계·상태·판정·유형·출처처럼 순서 기준이 정해지지 않은 코드 컬럼은 허용하지 않는다(예외함 `severity`만 `CRITICAL > HIGH > WARNING > 그 밖` 순서를 정의한다 — `desc`가 심각한 순).

> **요율을 왜 문자열로 보내나요?**
> JSON 숫자는 소수를 정확히 담지 못할 때가 있습니다(`0.1 + 0.2 = 0.30000000000000004`).
> 1,200% 사용률은 소수점 6자리까지 판정에 쓰이므로 문자열로 보내 오차를 없앱니다.

## 4. 내부 REST API 목록 (1차 21개 화면 전부)

### 4-1. 표 보는 법

- `구분` 열의 **MPA**는 페이지가 통째로 새로 그려지는 것, **Ajax**는 화면 일부만 서버에서 값을 받아 바꾸는 것입니다 (SIR-006).
- 2차에 React로 바꿀 때는 **Ajax 표시된 것부터** 옮기면 됩니다. 이미 JSON을 쓰고 있기 때문입니다.
- `구분`은 **1차 화면이 그 API를 어떻게 쓰는지**만 적습니다. `MPA`로 적혀 있어도 응답이 JSON이면 API 자체는 그대로 살아 있고 2차 React가 바로 씁니다 (예: IF-API-03 — 5-1 참조).
- **`다운로드`** 는 화면이 값을 받아 다시 그리는 것이 아니라 브라우저가 파일을 통째로 내려받는 것입니다. Ajax가 아닙니다 (예: IF-API-11A·27A·28B — `<a href>` 또는 `location.assign`).
- `화면` 열은 **대표 화면**입니다. IF-API-04~08(기준정보)처럼 여러 화면이 공유하는 API는 대표 화면만 적습니다 — 어느 화면이 어떤 API를 부르는지는 5-2·5-3이 기준입니다.

## 5. 화면 ↔ API 매핑 (MPA / Ajax) — SIR-006

### 5-1. 왜 나누나

> **MPA**(Multi Page Application: 서버가 HTML 페이지를 통째로 그려서 주는 방식)는 주소를 누를 때마다 화면 전체가 새로 그려집니다.
> **Ajax**(화면 일부만 서버에서 값을 받아 다시 그리는 방식)는 페이지는 그대로 두고 숫자만 바꿉니다.
>
> 1차에서는 **입력·목록·대시보드는 MPA**, **한도게이지·검증실행·대사상세는 Ajax**로 만듭니다.

> 전체 리로드하는 공통 셸 동작을 그대로 따르고, 화면은 IF-API-03을 HTTP로 다시 부르지 않고 같은 `DashboardService`를
> 서버에서 직접 씁니다. IF-API-03은 4-2에 그대로 남아 2차 React가 씁니다 (SRC-028 · 2026-08-19 결정).

## 6. 검증 실행 시점 아키텍처 ★ 신설

### 6-1. 왜 이 장이 필요한가

같은 "1,200% 검증"이라도 **언제 도느냐**가 5가지입니다.
이걸 안 정해두면 같은 계산기를 다섯 번 따로 만들게 되고, 다섯 개의 답이 서로 달라집니다.

> **FGC는 계산 엔진을 하나만 만들고, 부르는 시점만 5가지로 나눕니다.**

### 6-2. 5가지 실행 모드

| 모드 | 이름 | 언제 | 무엇을 | 누가 부르나 | 결과가 남는 곳 |
|---|---|---|---|---|---|
| ① | **즉시 재계산** | 데이터가 새로 들어오거나 바뀐 직후 | 그 계약만 | 내부 도메인 이벤트(8장) 리스너 | `cap_check(check_kind='REALTIME')`, `schedule_header` 새 버전 |
| ② | **확정 전 차단 검증** | 설계사에게 돈을 확정하기 **직전** | 그 지급 건 + 관련 계약 | `POST /api/v1/transactions/{id}/confirm` (IF-API-25) | `cap_check(check_kind='PRE_CONFIRM')`, `exception_case` |
| ③ | **일일 변경분 보정 배치** | 매일 밤 (프로젝트 운영 가정) | **어제 이후 바뀐 계약만** | `DailyChangedContractJob` (IF-BAT-02) | 각 검증 테이블 + `exception_case` |
| ④ | **월 전체 검증·대사 배치** | 월 정산자료가 모두 들어온 뒤 | 대상월 전 계약 | `MonthlyValidationJob` (IF-BAT-01) | `validation_run` 하위 전부 |
| ⑤ | **수동 한도 재검증** | 운영자가 계약 상세에서 요청할 때 | 그 계약의 운영 중인 지급단계 | `POST /api/v1/contracts/{id}/cap-check` (IF-API-19B) | `cap_check(check_kind='MANUAL')`, `audit_log` |

```
데이터 변경 ──────────────► ① 즉시 재계산
                                │

                                │
계약 상세 재검증 버튼 ────────► ⑤ 수동 한도 재검증 → 감사로그 기록
```

### 6-3. 절대 규칙

| # | 규칙 | 왜 |
|---|---|---|
| 1 | **모든 계약을 매일 전부 재검사하지 않는다.** 일일 배치는 `updated_at > last_processed_at` 인 변경분만 본다 | 계약이 늘어나면 밤에 안 끝난다 |
| 2 | **원수사 데이터 도착 주기를 코드·문서에 고정하지 않는다.** 보험회사와 자료 종류마다 다르고 법정 표준이 아니다 | 이 문서에 적는 "매일 02:00"은 **프로젝트 운영 가정**일 뿐이다 |

## 7. 배치 인터페이스 (Spring Batch) — 1차부터 사용

### 7-1. 왜 1차부터 Spring Batch인가

월 통합검증은 10단계를 순서대로 돌리고, 중간에 실패하면 **실패한 단계부터** 다시 시작해야 합니다.
이걸 직접 만들면 "어디까지 갔는지" 기록하는 코드를 우리가 짜야 합니다.
**Spring Batch**(정해진 작업을 단계별로 나눠 대량 처리하는 스프링 기능)는 그 기록을 대신 해 줍니다.

1차에서는 Job 2개만 씁니다. 화려한 기능은 쓰지 않습니다.

### 7-3. IF-BAT-01 `MonthlyValidationJob` — Step 정의

제43조 10단계를 **순서대로** 수행합니다. 다만 **Step 과 단계는 1:1이 아닙니다.**

- 6단계는 Step 2개(`journalPostingStep` → `imbalanceCheckStep`)
- 4단계는 partition 2개, 7단계는 지급단계별 2회 실행
- **9·10단계는 Job 이 아닙니다** (사람이 수행)

그래서 **진행률을 `batch_step_execution` 에서 역산하지 마세요.** 매핑이 성립하지 않고,
9·10단계는 Spring Batch 에 Step 자체가 없습니다.
각 Step 은 자기 일을 마치면 **`validation_run.current_step` 을 제43조 단계번호로 갱신**하고,
화면은 그 값만 읽습니다(IF-API-49). 단계 이름은 화면 상수입니다.

| # | 제43조 단계 | Step 이름 | 입력 → 출력 | 멱등키 (중복을 막는 열쇠) | 실패 시 |
|---|---|---|---|---|---|
| 1 | ①대상월 실행 생성 | `createRunStep` | JobParameter → `validation_run` | `uq_validation_run (validation_month, run_no)` + 부분 UNIQUE(진행중 1건) | 즉시 FAILED |
| 2 | ②계약·상품버전·환급률표 선별 | `selectTargetStep` | `insurance_contract`, `product_offering`, `refund_rate_table` → `validation_target` | `uq_validation_target (validation_run_id, contract_id)` | 재시작 시 이 Step부터 |
| 3 | ③현행 예상 스케줄 생성·재검증 | `regenerateScheduleStep` | `validation_target` → `schedule_header/line` | 활성 OPERATIONAL 부분 UNIQUE + `uq_schedule_line_business` | 계약 단위 skip → `exception_case(DATA_QUALITY)` |

> ## ★ 10단계 중 ⑨담당자 검토와 ⑩확정은 배치가 하지 않습니다.
> **사람이 검토하고 사람이 확정합니다.**
> 배치가 자동으로 확정해 버리면, 규제 검증 시스템을 만든 이유 자체가 사라집니다.

**`exception_key` 조립 규칙** (동결 대상 — 2026-08-18 [SRC-032]로 개정):

```text
{exceptionType}:{validationMonth YYYY-MM}:CONTRACT:{contractId}:{paymentStage}[:세부차원…]

예) CAP_VIOLATION:2026-07:CONTRACT:4104:GA_TO_FC:12
    RECONCILIATION_MISMATCH:2026-07:CONTRACT:4104:GA_TO_FC:{match_group_key}:{md5}:{원인코드}
    JOURNAL_IMBALANCE:2026-07:CONTRACT:4104:EXPECTED_FC_PAYOUT:SCHEDULE_LINE:8812
```

구 규칙(`{exceptionType}:{validationRunId}:{sourceEntityType}:{sourceEntityId}:{paymentStage?}`)은
실행 ID가 키에 들어가 재실행마다 같은 문제의 예외가 중복 생성되어 FGC-FUN-052의
"재실행해도 예외 중복 생성 없음" 인수조건과 충돌했다. SRC-032가 실행 ID·실행별 결과 PK를
제외한 **검증월 기준 안정 업무키**로 개정했다 — 같은 검증월의 같은 문제는 업무건
(`exception_case`) 1건으로 수렴하고, 실행별 검출 증거는 `exception_occurrence`에 쌓인다.
세부차원은 원천별로 다르다: CAP은 `cap_rule_set_id`, 대사는 `match_group_key`+MD5+원인코드,
원장은 분개유형+분개 원천 식별자(`journal_type`+`source_entity_type`+`source_entity_id` —
같은 실행의 서로 다른 불균형 분개를 구분한다), 그 외는 `reason_code`.

실시간 사전확정(FGC-FUN-034) 경로는 월 검증 실행 밖에서 동작하므로 위 안정 업무키 규칙이
아닌 별도 키를 쓴다 — 지급 건 단위 확정 게이트와 계약된 키라 월 업무키와 충돌하지 않는다.
현재 두 형태가 공존한다(2026-08-19 기준 구현 상태, SRC-032 후속 통합 과제):

- 확정 게이트 실패(CommissionPaymentServiceImpl): `PRE_CONFIRM:{paymentId}:{transactionAttributionId}:{exceptionType}`
  (세부 사유는 키가 아니라 reason_code 컬럼으로 남긴다 — GateFailure.reasonCode)
- CAP 실시간 판정(CapExceptionServiceImpl — **안정 업무키로 미이관**):
  `{exceptionType}:{validationRunId=null}:COMMISSION_TRANSACTION:{paymentId}:{paymentStage}:{capRuleSetId}`
  — 실시간 호출은 validationRunId 가 항상 null 이라 지급 건·단계·룰셋 기준으로 안정적이며,
  ON CONFLICT upsert 로 재시도 중복이 방지된다. 월 검증의 CAP 예외는 이 경로가 아니라
  8단계(`insertFromCapChecks` → `record_exception_detection`)가 생성한다.

이 키에 UNIQUE 제약이 걸려 있어서, 배치를 몇 번 다시 돌려도 **업무건은 1건만** 생깁니다.

### 7-5. IF-BAT-02 `DailyChangedContractJob`

| 항목 | 내용 |
|---|---|
| 목적 | 어제 밤 이후 **바뀐 계약만** 다시 확인 (모드 ③) |
| Reader | `JdbcPagingItemReader` — `WHERE c.updated_at > :lastProcessedAt` **OR** `EXISTS (SELECT 1 FROM contract_status_event e WHERE e.contract_id = c.contract_id AND NOT EXISTS (SELECT 1 FROM contract_status_event_processing p WHERE p.contract_status_event_id = e.contract_status_event_id AND p.processing_job = :jobName AND p.processing_status = 'SUCCEEDED'))` — **`e.processed_at IS NULL` 금지.** 처리 여부는 Job별로 판단한다 |
| 대상 검증 | 6-4 매트릭스의 "일일 변경분 = O" 행만. **1차**: 1,200% 누적 · 차익거래 · 원장 불균형 재검사 |
| Writer | 해당 검증 테이블 + `exception_case` |
| 워터마크 | **`batch_watermark` 테이블** (스키마 v2.1.3에서 신설) + **`contract_status_event_processing`**의 Job별 처리이력 |
| 멱등성 | `run_type='MANUAL_CONTRACT'`인 `validation_run`을 하루 1건 만들어 그 밑에 결과를 붙인다 → 기존 UNIQUE 제약이 그대로 작동 |
| 실패·재시작 | **워터마크는 Step이 성공한 뒤에만 전진**시킨다. 실패하면 다음 날 같은 구간을 다시 읽지만 UNIQUE가 중복을 막는다 |
| 적용 룰셋 없음 | 1,200% 룰셋이 없을 때(`FGC-CAP-004`) **계약 체결일과 지급단계로** 나눈다. 1,200%룰은 보험회사(INSURER_TO_GA) '21.1.1, 보험대리점(GA_TO_FC) '26.7.1. **이후 체결한 신계약**에 적용된다(REG-08·09, FAQ 2차 Q1-1). ① 체결일이 그보다 앞서면 그 단계는 대상이 아니다 — 실패도 검토 대상도 아니며, 다른 검증이 성공하면 상태 사건은 `SUCCEEDED`. ② 대상 단계인데 룰셋이 없으면 설정 누락 — 검토 큐(`exception_case` `POLICY_MISSING`, 계약·지급단계 업무키 UPSERT, 계약 저장 경로와 같은 건)에 남기고 데이터 품질 스킵(`exception_case`). 그 밖의 업무 예외도 ②와 같은 실패 처리. **다음 날 자동 재처리는 상태 사건이 있는 계약만**이다 — 미처리 사건이 `FAILED`로 남아 Reader의 `NOT EXISTS(… 'SUCCEEDED')`에 다시 걸린다(9-3). 상태 사건 없이 `updated_at`으로만 잡힌 계약은 처리행이 없고 워터마크가 전진하므로 다음 날 다시 읽지 않는다 — 실패는 검토 큐·데이터 품질 예외로만 남고, 설정을 고친 뒤 계약 수정·월 실행에서 다시 계산된다 |
| 처리량 가정 | 1차 시연 시드 기준 수백 건. chunk size 100 |

**워터마크(watermark)란** — "여기까지는 처리했다"고 표시해 두는 기준선입니다.
강물에 남은 물자국처럼, 다음에는 그 위(그 이후)만 보면 됩니다.

|---|---|---|---|---|
| **효력 발생** | `contract_status_event.effective_at` | 실제로 그 일이 일어난 날 (해지된 날) | **수수료 자격 · 차익거래 판정 · 초년도 구간 · 계약 이력 재구성 순서** | — |
| **수신** | `contract_status_event.received_at` | FGC DB가 그 사실을 받은 날 | 지연 모니터링, "왜 어제 결과와 다른가" 설명 | 수수료 자격 판단 |
| **처리** | `contract_status_event_processing.processed_at` (**Job별**) | 특정 Job이 그 사건을 처리한 날 | **재처리 대상 선별**(해당 Job의 성공행이 없으면 아직 안 봄), 감사 | 수수료 자격 판단, **다른 Job의 처리 완료 여부** |

```
9/01 계약 해지 발생 ─────────► 9/02 FGC DB 수신 ─────────► 9/03 02:00 배치 처리
   effective_at                   received_at        contract_status_event_processing
                                                       .processed_at (processing_job별)
   └─ 차익거래·수수료 자격은 이 날짜로 판단한다 ─┘
```

> ⚠️ **`contract_status_event.processed_at`은 v2.1.6부터 폐기 예정 호환 컬럼이다.**
> 신규 코드에서 읽거나 쓰지 않는다. 처리 여부는 사건 하나에 하나가 아니라
> **`processing_job`별로** 따로 존재하므로, 한 Job의 성공을 다른 Job의 처리완료로
> 간주하면 안 된다. 실패는 재시도마다 새 행으로 남고 사건×Job의 성공행은 최대 1건이다.
> (운영정책서 제7장 · 시드데이터명세서 §19)

### 9-2. API 노출 규칙

| 규칙 |
|---|
| 상태 이력을 주는 모든 API(IF-API-16 · IF-API-12)는 **세 날짜를 전부 내보낸다.** 하나만 주면 화면에서 잘못 쓴다 |
| 처리일은 **단일 필드가 아니라 `processings[]` 배열**이다. 사건 하나가 Job마다 따로 처리되므로 `processedAt` 하나만 주면 한 Job의 성공을 전체 처리완료로 오인한다 |
| 아직 어떤 Job도 처리하지 않았으면 `processings`는 **빈 배열**이다. `null`이 아니다 |
| 화면 표기: `효력 2026-09-01 · 수신 2026-09-02 · 처리 DailyChangedContractJob 2026-09-03` (미처리 Job은 "대기") |
| 이력 정렬 기본값은 **`effectiveAt,asc`**. `receivedAt` 정렬은 "도착 순서 보기" 토글로만 |

### 9-3. 순서역전 · 지연도착 처리

| 상황 | 규칙 |
|---|---|
| 수신 순서가 효력 순서와 다름 (8/16에 8/14 실효, 8/17에 8/12 미납 수신) | 계약 이력 재구성은 **`effective_at ASC, event_seq ASC`** 로 정렬해서 다시 만든다. **수신순 절대 금지** |
| 같은 `effective_at`에 두 건 | `source_version`이 큰 것을 최신으로. 없으면 `event_seq`가 큰 것 |
| 같은 사건이 두 번 수신 | `UNIQUE(source_system, source_event_key)`가 물리적으로 차단 → API는 `409`가 아니라 **`200 + "이미 반영됨"`**으로 응답한다 (재전송은 정상 상황이다) |
| 이미 검증이 끝난 달에 늦게 도착 | ① 그 사건에 **해당 Job의 성공 처리행을 남기지 않아** 다음 일일 배치가 잡게 한다 ② 결과는 **새 `validation_run`**에 남긴다 ③ **FINALIZED된 run은 절대 수정하지 않는다** |
| 원수사 도착 주기 | **고정하지 않는다.** 문서에 적는 "매일 02:00", "월말 후 5영업일"은 전부 *프로젝트 운영 가정*이다 |

### 9-4. 미납과 실효는 다릅니다 (자주 틀리는 부분)

| 상태 | 뜻 | 지급 처리 |
|---|---|---|
| **미납**(UNPAID) | 보험료를 아직 안 냈다. 계약이 끝난 것은 아니다 | 회사 정책에 따라 **보류**할 수 있다. 미래 수수료를 곧바로 영구 중단하면 안 된다 |
| **실효**(LAPSED) | 미납 등으로 계약의 효력이 실제로 정지됐다 | 미래 지급회차 보류·중단. 차익거래 즉시 실행 |
| **부활**(REVIVED) | 실효된 계약이 다시 살아났다 | 미래 회차 재개 여부를 정책으로 판단 |
| **해지**(TERMINATED) | 계약이 끝났다 | 미래 유지관리 회차 중단. 환수 후보 생성 |

> **미래 회차를 안 주는 것**과 **이미 준 돈을 되받는 것(환수)**은 다릅니다(REG-13).

### 9-5. 월중 실효·부활 시 그 달 수수료 처리 — `STATUS_MONTH_RULE`

**문제**: 9월 1일에 실효된 계약의 9월분 유지관리수수료를 줘야 할까요, 말아야 할까요?
9월 15일에 부활했다면 9월분을 다시 줘야 할까요?

법정 확정 기준을 아직 확보하지 못했습니다. 그래서 **파라미터로 두고 기본값을 정합니다.**
이 값은 `policy_version.source_class = 'PROJECT_ASSUMPTION'`으로 저장되어
화면에 <strong>주황색 "프로젝트 가정" 배지</strong>가 붙습니다. 법정 기준이 아니라는 뜻입니다.

#### 채택한 기본값 (3개 파라미터)

| 파라미터 | 채택값 | 뜻 |
|---|---|---|
| `STATUS_MONTH_RULE` | **`PAY_IF_ACTIVE_ON_DUE_DATE`** | 그 회차의 **지급예정일(`schedule_line.due_date`) 시점**에 계약이 유효했으면 그 회차를 지급한다 |
| `PRORATION_RULE` | **`NO_PRORATION`** | 일할계산하지 않는다. 주거나 안 주거나 둘 중 하나다 |
| `REVIVAL_BACKFILL_RULE` | **`NO_RETROACTIVE`** | 부활해도 실효 기간에 건너뛴 회차를 소급해 주지 않는다. 부활일 이후 회차부터 재개한다 |

#### 왜 이 값들인가

| # | 근거 |
|---|---|
| 1 | **`NO_PRORATION`이 규제와 맞습니다.** 유지관리수수료는 "**매월 동일 금액**"이어야 합니다(REG-03). 일할계산을 하면 어떤 달만 금액이 달라져 이 요건과 정면으로 충돌합니다 |
| 2 | **`due_date` 기준이 데이터로 명확합니다.** 스케줄에 이미 지급예정일이 있고, 대사(reconciliation)도 같은 회차를 그 회차의 발생월(`due_month = settlement_month`)로 짝짓습니다(지급예정일의 일 단위는 매칭키가 아님, 운영정책서 제36조). **검증과 대사가 같은 기준을 쓰면 결과가 갈라지지 않습니다** |
| 3 | **`END_OF_MONTH_STATUS`(월말 상태로 판단)를 쓰지 않은 이유** — 월말 하루의 상태로 한 달 전체를 판단하면, 9/2 실효 → 9/28 부활한 계약과 9/28 실효한 계약이 정반대 결과가 됩니다. 사람이 설명하기 어렵습니다 |
| 4 | **`FULL_MONTH_REQUIRED`(그 달 내내 유지)를 쓰지 않은 이유** — 가장 보수적이지만, 월중 부활한 계약은 영원히 그 달을 못 받습니다. 부활 제도의 취지와 맞지 않습니다 |
| 5 | **`NO_RETROACTIVE`인 이유** — 실효 기간에는 **실제로 유지관리 서비스가 없었습니다.** 이 규칙은 `PROJECT_ASSUMPTION`(교육용 가정)입니다. REG-03은 2027-01-01 이후 판매개시 분급 상품의 법정 유지관리수수료 조항이라 현행 계약관리수수료의 부활 처리 근거가 아닙니다 — 근거 없음 확인 필요. 업계 영업규정에는 부활 시 직전 환수수수료를 재지급하는 "부활수수료"가 있으므로(SRC-019 `:214`·`:1586`), 2차 환수 구현 때 재검토합니다. 운영정책서는 부활 후 소급을 `REVIEW_REQUIRED`로 둡니다 |
| 6 | **미납(UNPAID)은 중단이 아니라 보류입니다.** 미납만으로 미래 수수료를 영구 중단하지 않습니다. `HOLD`로 두었다가 실효되면 중단, 납입이 재개되면 지급합니다. 이때 보류 회차의 지급예정일은 재개(입금) 기준으로 다시 잡습니다. 보류 회차의 지급 확정은 막습니다(2026-10-12·13 PL 결정, #523) |

#### 상태별 처리표

| 그 회차 지급예정일 시점의 계약 상태 | 그 회차 처리 | `schedule_line.line_status` |
|---|---|---|
| 정상(ACTIVE) · 부활(REVIVED) | **지급** | `PLANNED` → `CONFIRMED` |
| 미납(UNPAID) | **보류** — 보류 회차는 지급 확정을 막는다. 납입 재개 시 지급하되 지급예정일은 재개(입금) 기준으로 다시 잡는다(2026-10-12·13 PL 결정, #523) | `HOLD` |
| 실효(LAPSED) | **미지급** (소급하지 않음) | `CANCELLED` |
| 해지(TERMINATED) · 만기(MATURED) | **미지급**, 이후 회차 전부 중단 | `CANCELLED` |
| 청약철회(CANCELLED) | **미지급** + 기지급분은 환수 후보 | `CANCELLED` |

> **구현 범위(2026-10-22, SRC-027 D-03·SRC-064):** 위 표는 2차 상태 처리 규칙이다. 현재 대사 조회는 이미 `HOLD`·`CANCELLED`인 회차와 신뢰할 수 있는 상태 이력의 실효·해지·만기 회차, 청약철회 계약을 제외한다. `UNPAID`만으로 회차를 보류하거나 재개 시 지급예정일을 변경하는 기능은 #523의 후속 구현이다. 이력을 신뢰하는 조건과 현재 상태 불일치 시 처리는 운영정책서 제36조를 따른다.

#### 예시

```
계약 C-1001 · 유지관리수수료 지급예정일 = 매월 25일

 9월분 (예정일 9/25):  9/01 실효 → 9/25 시점 실효   → 미지급 (CANCELLED)
10월분 (예정일 10/25): 10/15 부활 → 10/25 시점 정상  → 지급   (CONFIRMED)
 9월분 소급 지급?      → 하지 않음 (NO_RETROACTIVE)
```

#### API·DB에 어떻게 나타나나

| 항목 | 규칙 |
|---|---|
| 저장 위치 | `policy_version(policy_code='STATUS-MONTH-RULE-2026', source_class='PROJECT_ASSUMPTION')` |
| 화면 표시 | POL-W01 정책 버전 탭에 **주황색 "프로젝트 가정" 배지**로 노출 |
| API | `GET /api/v1/policies?type=SCHEDULE_ELIGIBILITY` 로 조회 |
| 판정 근거 | `schedule_line.payment_condition_code` 에 적용된 규칙 코드를 남긴다 |
| **코드에 박지 말 것** | COR-004. `if (status == LAPSED)` 같은 하드코딩 금지. 반드시 정책에서 읽는다 |

|---|---|---|
| `GET /api/v1/audit-logs/options` | `actionCodes[]`·`entityTypes[]`·`users[]` | 1차 모델 `actionCodes`·`entityTypes`·`auditUsers`와 같은 쿼리 |

## #482 시행 전 계약의 1,200% 적용대상 판정

`NOT_APPLICABLE`은 시행 전 계약으로 계산 대상이 아닌 결과다. 원수사→GA는 2021-01-01, GA→설계사는 2026-07-01 계약일부터 적용한다. CAP 목록/계약 한도 탭/계산근거에서 조회할 수 있으며 계산 금액·사용률·룰셋 ID는 null(화면 —)이다. 정상 건수 및 금액 모니터링에는 포함하지 않는다. 계산근거 `calculationSnapshot.applicability`에 계약일·시행 기준일·사유 코드·문구·기준 버전을 보존한다. 사전검증은 applicabilityReasonCode/applicabilityReason을 반환하고 저장하지 않는다. 지급확정은 판정과 후보 귀속 사유를 저장한다. 자세한 결정은 `FGC_482_적용대상판정_설계.md`를 따른다.

### IF-API-24 초년도 밖 후보 제외 근거 (#479)

`capExclusions`는 빈 배열 또는 후보별 제외 근거 배열이다. 기존 `capPreview`, `blockers`, `confirmable` 필드를 유지한다.

| 필드 | 형식 | 의미 |
|---|---|---|
| transactionAttributionId / contractId | integer | 제외한 귀속행 / 계약 ID |
| paymentStage | string | 지급단계 |
| attributionDate | yyyy-MM-dd | 판정한 귀속일 |
| firstYearStartInclusive | yyyy-MM-dd | 계약일, 포함 |
| firstYearEndExclusive | yyyy-MM-dd | 계약일 + 12개월, 미포함 |
| excludedAmount | integer | 초년도 산입에서 제외한 후보 금액(원) |
| resultStatus | string | NOT_APPLICABLE (후보 기간 범위) |
| reasonCode / reason | string | OUTSIDE_FIRST_YEAR / 초년도 밖 — 판정 대상 아님 |

초년도 밖 후보만 있으면 `capPreview=[]`여도 다른 게이트를 통과한 경우 `confirmable=true`다.
기간은 귀속일 기준 `[계약일, 계약일+12개월)`이다. 계약일 전 귀속은 입력 오류로 차단한다.
확정 시 동일 근거를 PAYMENT_CONFIRMED 감사행의 `after_value.capExclusions`에 저장한다.
계약 전체의 기존 `cap_check` 판정은 후보 제외로 대체하지 않는다. 혼합 후보는 기존 한도 상세에
EXCLUDED 분류·금액·제외 사유를 추가하며, INCLUDED 상세 합계는 판정 산입액과 일치한다.

기간 제외는 산입 분류 검토 완료를 의미하지 않는다. 초년도 밖 후보라도 `REVIEW_REQUIRED` 귀속은 CAP_002로 사전검증·확정을 차단한다.

#479 날짜 정합성: 귀속일이 초년도 밖인 후보는 지급예정일도 계약일+12개월 이상인 경우에만
`capExclusions`로 반환한다. 지급예정일이 초년도 안이거나 누락되면 CAP_002 차단 사유에 귀속일·지급예정일·
종료일을 표시한다. 정산월을 지급예정일로 대신하지 않는다. 초년도 안 귀속은 지급예정일이 늦어도 기존 한도 검증을 유지한다.

#479 지급예정일에 따른 CAP_002 차단은 1,200% 규제 대상 계약에 적용하며, #477의 비보장성 계약은 이 검사로 차단하지 않는다.

### 계약 이력 필터와 기존 참조 보존 (#408 리뷰 보완)

- `includeHistorical=true`는 목록 검색용입니다. 상품의 판매기간·활성 상태, 조직 유효기간, 설계사 위촉기간 제한을 해제합니다. 기본값 `false`와 기존 `includeExpired`·`includeTerminated` 동작은 유지합니다.
- `PUT /api/v1/contracts/{id}`는 계약일과 보험사·판매버전 또는 모집 설계사·계약 당시 조직이 변경되지 않은 참조 묶음을 보존합니다. 현재 해촉·소속 변경·기준정보 비활성화만으로 보험료 등 다른 필드의 정정을 막지 않습니다. 참조 묶음이나 계약일을 바꾸면 기존 입력 검증을 수행합니다. 잠금·`expectedUpdatedAt`·409·스케줄 재생성·감사 기록은 유지합니다.
- 없는 계약은 기존 `400 FGC-COMMON-002`와 서버 메시지를 표시합니다. React 전환을 위해 HTTP 상태나 오류 코드를 변경하지 않습니다.
