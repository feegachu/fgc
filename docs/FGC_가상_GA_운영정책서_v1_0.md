# FGC 가상 GA 운영정책서 v1.0

> 이 문서는 실제 특정 GA의 내부규정이나 운영시스템을 복제한 문서가 아니다.  
> 공개된 법령·FAQ·보험회사 지급자료·GA 영업규정 사례·특허를 바탕으로 만든 **교육용 가상 대형 GA의 정산·내부통제 정책**이다.  
> 법률자문서, 실제 보험회사 지급약정서 또는 실제 회계정책서로 사용할 수 없다.

> **정합성 기준:** 규제 판단은 `FGC 규제 근거·조문표 v0.2.1`의 근거 우선순위와 REG-01~24를 따르고, 물리 DB 판단은 `src/main/resources/db/migration/`의 V1~V7을 순서대로 적용한 v2.1.7을 따른다. `db/demo`의 시드는 축소 검증자료이며 규제 또는 운영정책의 원천이 아니다.

---

## 0. 문서의 목적

FGC 팀은 실제 보험회사·GA와 전산 연계하거나 현업 담당자에게 업무 검증을 받을 수 없다. 따라서 다음 원칙으로 프로젝트 범위를 고정한다.

1. FGC금융서비스라는 **가상 대형 법인보험대리점(GA)**을 정의한다.
2. 원수사 데이터는 수집·변환이 끝나 **FGC 표준 DB에 정규화되어 적재된 상태**로 시작한다.
3. 규제상 의무, 원수사 지급기준, GA 내부 지급정책, 프로젝트 가정을 구분한다.
4. 실제 개인정보·실제 증권번호·실제 설계사 지급액을 사용하지 않고 합성 데이터를 사용한다.
5. FGC는 실제 송금·세금신고·보험청약·법정 회계결산을 수행하지 않는다.
6. FGC의 핵심 역할은 예상액 계산, 규제검증, 복식부기형 검증원장, 실제명세 대사, 예외관리이다.
7. 법정 수치·시행일·FAQ 운영기준은 코드 상수가 아니라 승인된 `policy_version`·정책상세·`policy_parameter`로 버전 관리한다.

### 문서에서 사용하는 구현상태

| 표시 | 의미 |
|---|---|
| `DB 강제` | CHECK·FK·UNIQUE·트리거가 위반 저장 자체를 차단한다. |
| `서비스 강제` | DB 구조는 보유하지만 계산·선택·게이트는 애플리케이션이 수행해야 한다. |
| `메타데이터만` | 외부 의무 자체는 범위 밖이고 근거·버전·결과 연결정보만 저장한다. |
| `미구현/향후` | 테이블이 있더라도 실행 서비스·화면·배치가 아직 제공되지 않는다. |

테이블 존재만으로 규제 기능이 구현되었다고 판단하지 않는다. 특히 2차용 테이블은 v2.1.7에 물리적으로 존재하더라도 애플리케이션 제공범위와 별개다.

# 제1장 회사와 시스템의 범위

## 제1조 가상 회사 정의

| 항목 | 확정 내용 |
|---|---|
| 회사명 | FGC금융서비스 주식회사 |
| 회사 성격 | 여러 보험회사의 상품을 판매하는 법인보험대리점(GA) |
| 회사 상태 | 교육용 가상 회사 |
| 소속 설계사 규모 | 3,200명 |
| 조직구조 | 본사 1 → 본부 4 → 지사 20 → 팀 100 → 설계사 |
| 취급 영역 | 생명보험·손해보험의 장기 보장성보험 중심 |
| 1차 데모 보험회사 | 가상 생보 4개사, 가상 손보 2개사 |
| 1차 사용자 | 시스템관리자, GA관리자, 정산담당자, 준법·감사 |
| 정산 기준 통화 | 원(KRW) |
| 시스템 시간대 | Asia/Seoul |
| 데이터베이스 | PostgreSQL 17 |

실제 회사 자료에서 확인되는 FC·팀장·지사장·본부장 등의 용어는 업무구조 참고에만 사용한다. FGC금융서비스의 조직·지급률은 독자적인 가상 정책이다.

## 제2조 제품 정의

FGC는 다음 제품으로 정의한다.

> **가상 대형 GA의 계약별 판매수수료 예상·지급 데이터를 계산하고, 1,200%룰·차익거래·분급·복식원장·대사 규칙을 검증하여 예외를 관리하는 내부통제 시스템**

### 포함 범위

- 보험회사·상품·상품 판매버전·조직·설계사 기준정보 조회
- 보험계약과 계약상태 사건
- 원수사→GA 예상 수입 스케줄
- GA→설계사 예상 지급 스케줄
- 실제 원수사 지급명세와 GA 지급 건
- 계약별 수수료 귀속
- 초년도 1,200% 한도 검증
- 차익거래 후보 검증
- 예상·실제 금액 대사
- FGC 내부 검증용 복식원장
- 예외 처리와 감사로그
- 2차의 4년·7년 분급, 유지관리, 계약체결비용, 환수·상계

### 제외 범위

- 보험회사 포털 접속과 파일 다운로드
- CSV·Excel 업로드, 컬럼 매핑, 스테이징, 원본파일 보관
- 보험청약·인수심사·보험료 결제
- 실제 계좌이체와 급여 지급
- 세금 원천징수·세무신고
- GA 전체 인사·평가·승격·민원·광고 시스템
- 보험협회 비교설명 확인서 작성 전체 기능
- 법정 회계장부와 재무제표 작성

## 제3조 근거의 종류

모든 규칙은 다음 네 종류 중 하나로 분류한다.

| 분류 | 의미 | 예 |
|---|---|---|
| `REGULATORY` | 회사가 임의로 바꿀 수 없는 법령·고시·FAQ 기준 | 1,200%룰, 차익거래, 4년·7년 분급의 상한·적용시기 (`REG-02~05·19`, `SRC-003·022`) |
| `INSURER_RULE` | 보험회사가 GA에 제공한 회사별 지급기준 | 회차별 수입수수료, 시책, 환수율 |
| `GA_POLICY` | FGC금융서비스가 정한 내부 지급·배부·승인 기준 | FC 지급률, 관리자수수료, 공통비 정책 |
| `PROJECT_ASSUMPTION` | 현업자료 미확보로 팀이 정한 교육용 가정 | 자료 도착일, 월중 부활 처리, 대사 허용오차 |

정책 화면과 계산근거에는 이 분류, 유효기간, 정책버전, 출처참조를 표시한다.

`source_class`는 설명용 문자열 배열에 넣지 않고 `policy_version.source_class` 전용 컬럼으로 저장한다.
허용값은 `REGULATORY`, `INSURER_RULE`, `GA_POLICY`, `PROJECT_ASSUMPTION`뿐이다.
승인·활성·폐기된 정책은 `source_class`를 포함하여 수정할 수 없으며 새 정책버전을 생성해야 한다.

`source_class`는 정책의 소유 성격이고, 규제조문표의 `[현행규정]`, `[개정고시]`, `[시행세칙]`, `[FAQ-1차]`, `[FAQ-2차]`, `[해석]` 같은 **근거 상태 태그와는 다른 축**이다. 다음 값을 함께 보존한다.

- `policy_version.regulation_refs`: `REG-08`, `REG-10` 같은 규제조문표 식별자
- `policy_version.source_refs`: 공문번호·문서명·파일명·원문 버전
- `policy_parameter`: `REGULATION_SOURCE_TYPE`, `FAQ_VERSION`, `FAQ_APPROVAL_STATUS`, 경계사례 해석값
- 계산 결과의 `calculation_snapshot`: 실제 선택된 정책·파라미터·기준일

`policy_version.status=APPROVED`는 FGC 내부 정책 승인상태이지 FAQ가 최종 공문이라는 뜻이 아니다. 배포안 FAQ를 근거로 한 정책은 내부 승인을 거쳐도 `FAQ_APPROVAL_STATUS=DRAFT` 또는 동등한 값을 유지하며, 최종 FAQ가 나오면 기존 행을 고치지 않고 새 정책버전을 발행한다.

## 제4조 자료 우선순위

1. 현행 보험업감독규정
2. 금융위원회 개정고시와 부칙
3. 보험업감독업무시행세칙과 별표
4. 금융위·금감원 공식 FAQ
5. 금융위원회 공식 보도자료
6. 보험협회 자율규제·공시기준
7. 보험회사 지급기준·GA 내부규정·위촉계약
8. 특허·연구보고서·업계자료
9. FGC 프로젝트 가정

상위 근거와 하위 자료가 충돌하면 상위 근거를 우선한다. 확인되지 않은 내용은 `REVIEW_REQUIRED(사람의 검토가 필요한 상태)`로 남긴다.

# 제2장 릴리스별 운영범위

## 제5조 1차 릴리스

1차 개발은 2026년 8월 23일까지 완료한다.

### 1차 규제·업무 범위

| 구분 | 처리 |
|---|---|
| 2026.3 이후 차익거래 방지 | 계약 전 기간의 시계열을 이용해 후보 검증 |
| 2026.7.1 이후 GA→설계사 1,200%룰 | 월납 보장성 합성계약에 계약별 적용 |
| 원수사→GA 1,200%룰 | 별도 지급단계 게이지로 검증 |
| 현행 회사별 지급방식 | 원수사→GA와 GA→설계사 예상 스케줄 생성 |
| 실제명세 대사 | 양방향 예상·실제 전수 비교 |
| 복식부기 검증원장 | 예상·실제·확정 금액의 차변·대변 균형 검증 |
| 예외관리 | 한도·대사·원장·차익거래 예외 처리 |
| 월 통합검증 | 사용자가 월을 선택해 수동 실행하고 결과 잠금 |

### 1차 적용 계약군

- 1,200% 데모: 2026-07-01 이후 체결된 월납 보장성보험
- 차익거래 데모: 2026-03-01 이후의 월납 보장성보험
- 일시납·연납·저축성·자동차·일반보험: 계산엔진 확장 대상으로 남기고 1차 규제판정에서는 제외
- 2026년 3~6월 계약: 차익거래는 검증하되 GA→설계사 1,200%룰은 적용하지 않는다.
- 2026년 7월 이후 계약: 원수사→GA와 GA→설계사 게이지를 각각 계산한다.

### 2026년 규제 중 FGC의 처리 수준

| 규제영역 | 1차 처리 수준 |
|---|---|
| 초년도 1,200% | 강제 검증 |
| 차익거래 | 후보 검증 |
| 예상 해약환급률표 | 1~36차월 입력·버전 검증 |
| 지급기준 변경통제 | 정책버전 불변·감사로그 |
| 판매수수료 비교공시 | 산식의 입력값을 보유하되 소비자 공시화면은 범위 외 |
| 대형 GA 비교설명 | FGC 정산시스템 범위 외 |
| 보험회사 상품위원회 | `product_offering` 승인 메타데이터만 보관 |

따라서 “2026년 모든 규제를 수행하는 종합 보험판매시스템”이라고 발표하지 않는다.  
“2026년 판매수수료 규제 중 정산·금액검증에 해당하는 핵심 통제를 구현했다”고 설명한다.

| REG-13 | 해지·실효 후 미래 유지관리 미지급을 법정 환수와 구분 | 스케줄 상태, `maintenance_check` | 2차 서비스 강제 |
| REG-14 | 회사별 환수율·책임사유를 별도 정책버전으로 관리 | `clawback_rule`, `clawback_case`, `clawback_line` | 물리 선반영, 2차 서비스 강제 |

| REG-17 | 별표 1의1 산식의 입력값·검산값 보존 | 상품·스케줄·정책·계산 스냅샷 | 메타데이터/검산만, 공시화면 미구현 |
| REG-18 | 비교상품·등급·추천사유의 외부 결과 연계 | 전용 비교설명 테이블 없음 | 시스템 경계 밖, 현재 미구현 |

| REG-22 | 지급기준 버전 불변·작성자/승인자 분리·우회지급 근거 추적 | `policy_version`, `policy_approval_action`, 감사·증빙 | 신규 정책 일부 DB 강제, 우회지급 실질판단은 서비스/사람 |

# 제3장 데이터 수신과 처리시점

## 제7조 정규화 데이터 전제

FGC는 원수사 자료를 직접 수집하지 않는다. 다음 데이터가 이미 표준화되어 DB에 들어온 것으로 가정한다.

1. 신계약 데이터
2. 보유계약과 현재 상태
3. 보험료 수금·누적납입 데이터
4. 수수료·수수료환수 데이터
5. 시책 데이터
6. 상품·상품코드·판매버전
7. 수수료율·지급방식·환수율
8. 예상 해약환급률표

마이데이터 보험 API는 계약·상품·상태·납입주기 명칭을 참고하는 보조자료이며, 원수사→GA 판매수수료 인터페이스로 간주하지 않는다.

## 제8조 시점의 구분

계약상태 원본과 배치 처리이력을 분리한다.

| 테이블·컬럼 | 설명 | 운영규칙 |
|---|---|---|
| `contract_status_event.effective_at` | 상태가 실제 효력을 발생한 시점 | 규제판정·스케줄 자격의 기준 |
| `contract_status_event.received_at` | FGC DB가 상태를 받은 시점 | 지연수신·순서역전 판정 |
| `contract_status_event.processed_at` | v2.1.6 이전 호환용 처리시각 | **폐기 예정 컬럼. 신규 코드에서 읽거나 쓰지 않음** |
| `contract_status_event_processing.processed_at` | 특정 Job이 사건을 처리한 시각 | 신규 처리이력의 기준 |

계산은 원칙적으로 `effective_at`을 기준으로 한다. 늦게 들어온 사건도 과거 효력일에 맞춰 재검증한다.

`contract_status_event_processing`은 사건과 `processing_job`별로 `SUCCEEDED` 또는 `FAILED` 행을 추가하는 append-only 이력이다. 실패는 재시도마다 새 행으로 남기고, 사건×Job의 성공은 최대 1행만 허용한다. 미처리 사건은 반드시 `processing_job=:jobName`을 조건으로 한 `NOT EXISTS`로 조회한다. 한 Job의 성공을 다른 Job의 처리완료로 간주하지 않는다.

`contract_status_event_processing.processed_at >= contract_status_event.received_at`은 부모·자식 간 조건이라 현재 DB CHECK가 강제하지 않는다. 서비스가 검증하고 위반 시 데이터품질 예외를 만든다.

## 제9조 실제 운영주기 가정

다음은 법정 공통주기가 아니라 FGC금융서비스의 프로젝트 가정이다.

| 업무 | 가상 운영주기 | 1차 구현 |
|---|---|---|
| 신계약·상태·수금 데이터 반영 | 매일 01:00까지 정규화 DB 반영 | 시드 또는 화면 수기등록 |
| 변경 계약 재검증 | 매일 02:00 | 수동 재검증 버튼 |
| 원수사 월 지급명세 반영 | 다음 달 제5영업일까지 | 시드 적재 |
| 월 통합검증 | 제6영업일 | 화면에서 수동 실행 |
| 예외 검토 | 제6~8영업일 | 예외함 |
| 검증결과 확정 | 제9영업일 | `FINALIZED` |
| 실제 설계사 지급 | 제10영업일 | FGC 범위 외 |

## 제10조 실시간과 배치의 역할

### 실시간 처리

- 계약 등록 시 적용 정책과 한도 계산
- 예상 스케줄 생성·재생성
- 지급 건 초안 저장
- 지급 건 확정 직전 1,200% 사전검증
- 정책 누락·귀속근거 누락 확인
- 계약 단위 수동 차익거래 재검증
- 원장 `POSTED` 전 차변·대변 검사

### 일일 변경분 처리

- 신규·수정된 계약
- 새 상태 사건
- 추가 시책·정착지원금·공통비 귀속
- 정정 지급 건

DB는 `batch_watermark`, `contract_status_event_processing`, `validation_run.current_step`으로 일일·월간 배치를 지원한다. 다만 현재 저장소에는 `DailyChangedContractJob`, `MonthlyValidationJob`, `ValidationRunController` 구현이 없으므로 **DB 지원과 애플리케이션 제공을 구분**한다. 현재 제공수준은 수동·테스트 중심이며, Spring Batch 자동화가 구현·회귀검증된 릴리스에서만 “자동 배치 운영”으로 표시한다.

`batch_watermark`의 업무키는 `(job_name, step_name)`이다. 워터마크 후퇴의 승인·사유·감사기록은 DB가 자동 생성하지 않으므로 운영 서비스가 남겨야 한다.

### 월 전체 처리

- 대상 계약 선별
- 현행 예상 스케줄 재검증
- 계약별 1,200% 재합산
- 차익거래 후보 재검증
- 원장 균형 검사
- 예상·실제 대사
- 예외 생성
- 결과 확정·잠금

# 제4장 계약·설계사·조직 정책

## 제11조 계약 식별

- 계약 업무키: `보험회사 + 증권번호`
- DB 유니크 키: `(insurer_id, contract_no)`
- 주계약과 특약은 차익거래 검증 시 증권번호 단위 합산을 원칙으로 한다.
- 실제 고객명·주민번호·주소는 저장하지 않는다.
- 화면에 필요한 고객 표시는 `합성 고객 식별명`만 사용한다.

## 제12조 보험료 기준금액

계약에는 다음 금액을 구분한다.

| 컬럼 | 의미 |
|---|---|
| `premium_per_cycle_amount` | 납입주기 1회의 실제 보험료 |
| `first_premium_amount` | 초회 실제 보험료 |
| `monthly_equivalent_first_premium` | 월납환산 초회보험료 |
| `standard_surrender_deduction_amount` | 표준해약공제액 관련 입력값 |

1차는 월납만 판정하므로 세 금액이 동일한 사례를 기본으로 한다. 연납·일시납은 2차 확장용 데이터만 보관한다.

## 제13조 계약상태

| 코드 | 쉬운 설명 |
|---|---|
| `APPLIED` | 청약 단계 |
| `ACTIVE` | 정상 유지 |
| `UNPAID` | 보험료 미납 |
| `LAPSED` | 실효, 계약 효력이 정지됨 |
| `REVIVED` | 부활, 효력이 다시 살아남 |
| `CANCELLED` | 청약철회·취소 |
| `TERMINATED` | 해지·종료 |
| `MATURED` | 만기 |

1차에서도 차익거래 근거를 위해 `contract_status_event`를 입력 데이터로 보유한다.  
다만 상태전이 자동화, 미래 스케줄 자동보류·재개, 부활 판단 화면은 2차 기능이다.

## 제14조 설계사와 보험회사 코드

한 설계사가 보험회사마다 다른 코드를 가질 수 있으므로 `agent_insurer_code`로 매핑한다.

```text
보험회사 + 원수사 설계사코드 + 효력기간 → FGC agent_id
```

대사 시 예상 수취인과 실제 명세의 원수사 설계사코드가 다른 경우 `AGENT_MISMATCH`로 분류한다.

조직 직급은 실제 회사의 지급률을 복제하지 않는다. 아래 제20조의 가상 비율을 사용한다.

## 제17조 지급단계

```text
INSURER_TO_GA : 보험회사 → FGC금융서비스
GA_TO_FC      : FGC금융서비스 → 설계사·관리자
```

두 단계는 별도 예상 스케줄, 지급 건, 귀속, 한도결과, 대사실행을 갖는다.

## 제17조의2 금액 산출·반올림

FGC의 모든 수수료 예상액·실제 귀속액·검증금액은 다음 하나의 규칙을 사용한다.

```text
산출 원금액 = 기준금액 × 요율 ÷ 100
확정 금액   = 산출 원금액을 원 단위(scale 0) HALF_UP 반올림
```

- 요율 계산은 PostgreSQL `numeric`과 Java `BigDecimal`로 수행한다.
- `double`과 `float` 사용을 금지한다.
- 반올림은 **수수료 규칙 1행·계약 1건·수취인 1명·회차 1개 단위**로 먼저 수행한다.
- 월·설계사·조직 합계는 이미 원 단위로 반올림된 상세행을 합산한다.
- 음수는 금액 자체에 부호를 넣지 않고 `cashflow_type=DEDUCTION`으로 구분한다.
- 정책에는 `rounding_scale=0`, `rounding_mode=HALF_UP`을 저장하고,
  스케줄에는 당시 값을 스냅샷으로 보존한다.
- 다른 반올림 방식은 새 정책버전과 요구사항 변경 없이는 허용하지 않는다.

# 제6장 2026년 현행 지급정책

## 제18조 정책 목적

현행 지급방식은 2027년 법정 분급과 다른 회사별 회차 지급계획이다.

# 제7장 시책·지원금·공통비

## 제22조 시책

- 시책은 보험회사 또는 GA가 일정 상품·기간·실적조건에 따라 추가 지급하는 금액이다.
- 초년도에 귀속되는 시책은 원칙적으로 1,200%에 포함한다.
- 13회차 시책은 실제 귀속월과 지급예정일이 계약 13차월 이후인 경우에만 초년도 밖의 금액으로 본다.
- 초년도에 실제 지급하면서 DB 날짜만 13회차로 바꾸는 행위를 금지한다.
- 정책·지급 건·원장에는 지급근거 문서와 유효기간을 기록한다.

### 가상 시책

| 코드 | 대상 | 지급회차 | 요율 | 판정 |
|---|---|---:|---:|---|
| `INC-STD-100` | 지정 보장성 상품 | 1 | 100% | 포함 |
| `INC-HIGH-300` | 월간 캠페인 상품 | 1 | 300% | 포함, 한도 사전검증 필수 |
| `INC-M13-200` | 13회차 정상유지 계약 | 13 | 200% | 초년도 밖, 선지급 금지 |


## 제23조 경력설계사 정착지원금

- 항목코드: `SETTLEMENT_SUPPORT`
- 전체 GOLDEN 목표의 정상 가상 약정액: **2,400,000원**
- 전체 GOLDEN 목표의 한도초과 스트레스 테스트 약정액: **4,000,000원**
- 지급대상: 최근 타사 모집경력이 있는 신규 위촉 설계사
- 1,200% 판정: 포함
- 계약귀속: 해당 설계사가 **신계약을 모집한 월**의 신계약에 월납환산 초회보험료 비례로 귀속한다. 지급월이 아니다 — 8월 지급분은 7월 모집 신계약에 귀속한다. (`REG-20`, `SRC-025` FAQ 2차 Q7-1)
- 지급 시기를 13차월 이후로 이연해도 귀속월은 달라지지 않는다. 지급예정일로 초년도 게이지를 빠져나갈 수 없다.
- 위촉 당월 등 귀속 대상 모집월에 신계약이 없으면 위촉 후 최초 신계약 모집월로 이월
- 귀속 후 각 계약의 1,200% 게이지를 다시 검사
- 초과분을 관리자가 임의 승인할 수 없음
- 해결방법: 감액, 취소, 실제 미지급 이연, 계약귀속 오류 정정
- 12개월 내 신계약 8건 미달 시 100% 환수한다는 약정은 **가상 회사정책**이며 2차에서만 구현

정상 시드의 2,400,000원은 기본 GA 지급률 740%와 결합해도 예시 5개 계약이 모두 1,200% 이내가 되도록 정한 값이다.
4,000,000원은 정상 정책이 아니라 **모든 계약이 한도초과하는 의도적 실패 시나리오**로만 사용한다.

현재 `db/demo` 축소 fixture의 정착지원금은 **210,000원**이며 2개 신계약에 105,000원씩 귀속한다. 이는 전체 GOLDEN 목표값 2,400,000원/4,000,000원을 구현한 것이 아니다. 발표·테스트 기대값은 실행한 프로파일의 값을 표시해야 하며 두 데이터 세트를 혼용하지 않는다.


## 제24조 신인활동지원비

- 항목코드: `NEWCOMER_SUPPORT`
- 가상 지원한도: 2,000,000원
- 대상: 등록예정일 직전 3년의 등록·모집 이력을 순서대로 조회한다. 등록 이력이 있더라도 같은 기간 모집 이력이 없으면 신인으로 판정할 수 있고, 모집 이력이 있으면 신인이 아니다. 최근 등록일부터 1년 이내인 경우에만 지원한다. (`REG-21`, `SRC-025`)
- 목적: 모집활동을 위한 별도 장비·교육·활동지원
- 실적·계약건수·근속조건과 직접 연계하지 않는다.
- 증빙을 모두 충족하면 해당 룰셋에서 `EXCLUDED`로 분류할 수 있다.
- 경력조회·등록일·지원기간·지급근거가 누락되면 `REVIEW_REQUIRED`
- “1년 내 8건 미달 시 환수”처럼 실적조건을 붙인 지원금은 정착지원금으로 분류하고 1,200%에 포함한다.

신인활동지원비는 신인이 아직 계약을 모집하지 않았더라도 발생할 수 있으므로 다음 귀속유형을 허용한다.

```text
attribution_scope = AGENT
contract_id       = NULL
agent_id          = 신인 설계사
attribution_method = NEWCOMER_NON_CONTRACT
```

계약 미귀속 확정은 `EXCLUDED` 판정과 적격 증빙이 모두 있을 때만 허용한다.
`INCLUDED`로 판정되거나 실적과 연계된 지원금은 반드시 `CONTRACT` 범위로 재분류하여 계약에 귀속해야 한다.

## 제25조 공통비

공통비는 모집활동과 관련하여 조직 단위로 발생했지만 개별 계약에 바로 특정하기 어려운 비용이다.

공통비를 세 범주로 혼합하지 않는다.

- REG-06A: 초년도 1,200%룰에 산입할 수 있는 모집 관련 공통비
- REG-06B: 유지관리수수료 지급기준의 간접지원경비
- REG-06C: 법정 단일 산식이 없는 회사별 승인 안분정책

보도자료·업계 예시의 `약 19%`는 법정 고정률이나 공통 상한이 아니므로 정책 기본값으로 하드코딩하지 않는다. 비용풀·배부대상·배부기준·유효기간·승인근거·반올림·잔액처리를 회사별 정책버전으로 저장한다.

### 가상 회사 정책

- 비용풀 발생단위: 지사
- 발생주기: 월
- 대상: 해당 지사의 당월 신계약
- 배부기준: 월납환산 초회보험료 비례
- 반올림: 원 단위 `HALF_UP`
- 잔액처리: 소수점 잔액이 가장 큰 계약부터 1원씩 배분
- 1,200% 판정: 모집종사자에게 귀속되는 금액은 포함
- 근거 없는 임의 배부: 금지

### 예시

공통비 700,000원, 보험료가 100,000 / 100,000 / 200,000 / 300,000원이면:

| 계약 | 배부액 |
|---|---:|
| A | 100,000원 |
| B | 100,000원 |
| C | 200,000원 |
| D | 300,000원 |
| 합계 | 700,000원 |

1차에서는 범용 안분계산기를 개발하지 않는다. 외부에서 계산된 계약별 귀속결과를 입력하고 다음만 검증한다.

- 배부정책 버전 존재
- 배부 전 총액 = 배부 후 총액
- 대상월·조직·계약 일치
- 계약별 근거참조 존재
- 확정 후 귀속행 변경 금지

# 제8장 초년도 1,200% 정책

## 제26조 게이지 분리

```text
INSURER_TO_GA_1200
GA_TO_FC_1200
```

두 게이지는 합치지 않는다. 같은 계약이라도 각각 별도 결과를 저장한다.


## 제27조 적용기간

- 원수사→GA: 보험회사 지급기준의 초년도 1,200%룰은 2021-01-01 이후 체결 계약부터. 시스템은 해당 정책 유효기간과 상품범위를 함께 판정
- GA→설계사: 2026-07-01 이후 체결 계약부터
- 초년도 기간은 **계약체결일 이상, 계약체결일의 1주년일 미만**으로 계산한다.

```text
contract_date <= 귀속일 < contract_date + 1 year
```

예를 들어 계약일이 2026-07-10이면 2027-07-09는 초년도이고 2027-07-10은 초년도 밖이다.

- 예상 스케줄의 귀속일: `schedule_line.due_date`
- 실제 지급·귀속의 귀속일: `transaction_attribution.attribution_date`
- `attribution_month`는 월별 집계키이며 초년도 경계 판정에 사용하지 않는다.
- `settlement_month`는 월 명세 묶음일 뿐 초년도 귀속판정일로 사용하지 않는다.

## 제28조 기본 한도

월납 보장성 일반계약:

```text
기본 한도 = monthly_equivalent_first_premium × 12
```

표준해약공제액 80% 이상 공제 대상 상품:

```text
한도 = 월납환산 초회보험료 × 12 + 12차월 예상 해약환급금
```

정확한 상품·납입기간·채널·기준일의 환급률표가 없으면 자동 계산하지 않고 `REVIEW_REQUIRED`로 판정한다.

| 환수·정정 차감 | 확정된 차감만 누계에 반영 |
| 준법경영비 3% | `INSURER_TO_GA`에서만 증빙 충족분을 공제. 일반채널은 2027-01-01, TM·방송채널은 2028-01-01부터. 시행 전과 `GA_TO_FC`는 0 |

준법경영비는 자동으로 초회보험료의 3%를 빼는 정액공제가 아니다. 실제 지급액 중 비교설명·업무기준 준수 및 내부통제 인력 운영 목적에 해당하고 증빙된 금액을, 월납 기준 초회보험료의 3% 이내에서만 제외한다. `cap_rule_set.compliance_deduction_pct=3`은 최대 허용률이며 실제 공제액은 `cap_check.compliance_deduction_amount`와 상세 근거로 보존한다.

현재 `db/demo/V6_1__cap_ins_compliance_deduction_correction.sql`은 일반채널 시행일 보정을 제공하지만 `channel_code` 범위를 나누지 않는다. 따라서 TM·방송채널의 2027년 계약에는 이 fixture를 규제 통과 근거로 사용하지 않고 `REVIEW_REQUIRED`로 처리한다. TM 2028 시행 룰셋을 별도 추가하기 전에는 일반채널 테스트에만 사용한다.

## 제30조 판정상태

| 상태 | 기준 |
|---|---|
| `NORMAL` | 사용률 90% 미만 |
| `WARNING` | 90% 이상 100% 이하 |
| `VIOLATION` | 100% 초과 |
| `REVIEW_REQUIRED` | 정책·귀속·증빙·환급률표가 부족함 |

## 제31조 지급확정 게이트

지급 건은 반드시 다음 순서로 처리한다.

```text
DRAFT 생성
→ 계약별 귀속행 등록
→ 귀속합계 = 지급액 검사
→ REVIEW_REQUIRED 귀속 존재 여부 검사
→ 1,200% 사전검증
→ 통과 시 CONFIRMED
```

다음은 허용하지 않는다.

- 귀속 없이 `CONFIRMED`
- 한도초과 관리자 강제승인
- 근거 없는 `EXCLUDED`
- 확정 지급 건 금액 직접수정
- 확정 귀속행 수정·추가·삭제
- 초년도 지급을 13회차로 허위 이연

현재 DB 트리거가 직접 강제하는 범위는 `DRAFT` 생성, 귀속합계=지급액, `REVIEW_REQUIRED` 귀속의 확정 차단, 확정 후 불변성이다. **DB 트리거는 `commission_transaction` 확정 시 `cap_check`를 조회해 1,200% 통과 여부를 자동 확인하지 않는다.** 따라서 서비스는 같은 후보 지급 건을 포함한 `PRE_CONFIRM` 검증을 먼저 생성하고 `VIOLATION`·`REVIEW_REQUIRED`이면 `CONFIRMED` UPDATE를 호출하지 않아야 한다. 이 서비스 게이트가 구현되지 않은 경로에서는 지급확정 기능을 제공하지 않는다.

## 제33조 계산식과 지급단계

FGC의 법규준수용 차익거래 검증은 `GA_TO_FC`를 기본 지급단계로 한다.
보험회사 지급자료를 이용한 `INSURER_TO_GA` 분석이 필요하면 별도 진단결과로 저장하되 두 단계를 합산하지 않는다.

```text

= max(0, 순누적 판매수수료 + 지급예정 판매수수료 - 누적 납입보험료)

해약환급금 합산 대상
= max(0, 순누적 판매수수료 + 지급예정 판매수수료
         + 해약환급금 - 누적 납입보험료)
```

`arbitrage_check.paid_commission_amount`는 다음 의미로 고정한다.

```text
순누적 판매수수료
= 해당 payment_stage의 확정 PAYMENT 누계
  - 해당 payment_stage의 확정 DEDUCTION 누계
```

총 지급액과 총 차감액은 `calculation_snapshot`에 별도로 보존한다.
같은 계약·기준일이라도 지급단계별 결과는 독립 행으로 저장한다.

# 제11장 복식부기 검증원장

## 제37조 성격

FGC 원장은 법정 회계장부가 아니라 예상·실제 수수료의 금액정합성을 확인하기 위한 내부 보조원장이다.

## 제38조 1차 분개유형

| 유형 | 의미 |

## 제39조 최소 계정과목

| 계정코드 | 설명 | 정상잔액 |
|---|---|---|
| `EXPECTED_RECEIVABLE` | 예상 수수료미수금 | 차변 |

| `CONFIRMED_PAYOUT_PAYABLE` | 확정 지급채무 | 대변 |

분개 확정 전 `차변합계 = 대변합계`여야 한다.

### 예상분개와 실제분개의 생명주기

예상분개와 실제분개는 서로 대체하는 회계장부가 아니라 서로 다른 검증 기준이다.

- 대사가 `MATCHED`되어도 예상분개와 실제분개를 모두 `POSTED` 상태로 보존한다.
- 보고서에서 두 계열을 합산하지 않고 `EXPECTED`와 `ACTUAL`로 분리한다.
- 예상 스케줄이 실제 명세 도착 전에 변경·취소되면 예상분개를 역분개하고 새 예상분개를 기표한다.
- 실제 명세가 정정되면 실제분개를 역분개하고 새 실제분개를 기표한다.
- 대사결과는 예상분개와 실제분개의 연결관계를 나타낼 뿐 어느 한쪽을 삭제하지 않는다.

## 제40조 정정

확정분개를 직접 수정하지 않는다.

```text
원분개 POSTED
→ REVERSAL 분개
→ 원분개 REVERSED
→ revision_no가 증가한 신규 분개 POSTED
```

# 제12장 예외와 월 통합검증

## 제41조 예외 상태

`DEFER`는 실제 지급을 미루는 경우에만 사용하며 날짜만 바꾸는 우회처리는 금지한다.

## 제43조 월 통합검증 순서

```text
1. 대상월 실행 생성
2. 계약·상품버전·환급률표 선별
3. 현행 운영 스케줄 생성·재검증
4. 지급단계별 1,200% 검증
5. 차익거래 검증
6. 검증원장 기표·균형검사
7. 양방향 대사
8. 예외 생성
9. 담당자 검토
10. FINALIZED
```

`FINALIZED`는 FGC 검증결과 잠금이며 실제 송금마감·법정 회계마감이 아니다.

### 실행상태와 `current_step`

| 상태 | 허용 `current_step` | 의미 |
|---|---:|---|
| `CREATED` | 0 | 시작 전 |
| `RUNNING` | 0~8 | 자동 처리 중 |
| `FAILED` | 0~8 | 해당 단계에서 실패, 보정 후 `RUNNING` 재개 가능 |
| `COMPLETED` | 8 | 1~8단계 완료, 9단계 담당자 검토 대기 |
| `FINALIZED` | 10 | 담당자 검토·확정 완료 |

9단계는 별도 숫자 9로 저장하지 않는다. `COMPLETED + current_step=8`이 담당자 검토 대기 상태이고, 확정 시 `FINALIZED + current_step=10`으로 전환한다. 실행은 항상 `CREATED`로 INSERT하며 허용 전이는 `CREATED→RUNNING`, `RUNNING→COMPLETED/FAILED`, `FAILED→RUNNING`, `COMPLETED→FINALIZED`뿐이다.

## 제44조 확정조건

- 실행 상태가 `COMPLETED`
- 차변·대변 불균형 0건
- `CRITICAL` 미처리 예외 0건
- 정책 미존재·중복 0건
- 귀속합계 오류 0건
- 결과 상세합계와 요약합계 일치
- 확정 사용자와 시각 기록

이 중 DB가 직접 강제하는 것은 실행의 생성·상태전이, `status/current_step` 조합, `FINALIZED`의 `finalized_at`, 확정 후 하위결과 불변성이다. 차변·대변 불균형 0건, `CRITICAL` 미처리 예외 0건, 정책 누락·중복 0건, 귀속합계·상세합계 일치는 서비스가 확정 직전에 조회해 강제해야 한다. `finalized_by`도 현재 DB에서 NOT NULL이 아니므로 서비스가 반드시 채운다. 서비스 검사를 우회할 수 있는 직접 DB 권한은 운영 역할에 부여하지 않는다.

# 제13장 2027년 이후 가상 분급정책

## 제45조 적용판정

분급체계는 계약연도만으로 결정하지 않는다.

```text
product_offering.sales_start_date
+ basic_document_version
+ basic_document_date
+ channel_code
+ fee_regime_code
→ 분급체계 선택
```

1,200%와 차익거래 적용은 계약체결일 기준으로 별도 판정한다.


## 제45조의2 계약체결비용은 나눠 쓰는 통장이 아니다

분급 계산에서 가장 많이 하는 실수는 **선지급수수료와 유지관리수수료를 계약체결비용이라는 하나의 통장에서 꺼내 쓴다고 생각하는 것**이다. 그렇지 않다.

계약체결비용은 각 수수료의 한도를 계산할 때 쓰는 **기준 금액**이다. 두 수수료는 각자 따로 이 기준을 사용한다.

| 수수료 | 한도 | 근거 | `source_class` |
|---|---|---|---|
| 선지급수수료 | 예정 지급총액 ≤ 계약체결비용 | REG-02 / 제4-32조제11항 | `REGULATORY` |
| 유지관리수수료 | 월 지급액 ≤ 계약체결비용 × 월 상한율 **그리고** 전체 총액 ≤ 계약체결비용 | REG-03 / 제4-32조제12항 본문·제4호 | `REGULATORY` |
| 장기유지수수료 | 월 지급액 ≤ 계약체결비용 × 0.4% | REG-05 / 제4-32조제12항제2호 | `REGULATORY` |

따라서 다음 계산은 **하지 않는다.**

```text
잘못된 계산
계약체결비용 - 선지급수수료 - 유지관리수수료 총액 = 미사용 한도   ✗
```

세 한도는 각각 따로 검증하며, 서로 차감하지 않는다.

```text
올바른 계산
선지급수수료 사용률   = 선지급 총액 ÷ 계약체결비용
유지관리 월 사용률    = 유지관리 월액 ÷ (계약체결비용 × 월 상한율)
유지관리 총액 사용률  = 유지관리 총액 ÷ 계약체결비용
장기유지 월 사용률    = 장기유지 월액 ÷ (계약체결비용 × 0.4%)
```

`acquisition_cost_check`는 계약·실행별 부모 요약을 저장하고, `acquisition_cost_check_detail`이 다음 네 계약체결비용 검증을 유형별로 저장한다.

```text
UPFRONT_TOTAL
MAINTENANCE_MONTHLY    (대상월 필수)
MAINTENANCE_TOTAL
LONG_TERM_MONTHLY      (대상월 필수)
```

각 상세행은 `actual_amount`, `limit_amount`, `usage_pct`, `result_status`, `decision_reason`, `calculation_snapshot`을 보존하며 하나라도 100%를 넘으면 부모를 `VIOLATION`으로 판정한다. 초년도 1,200% 사용률은 이 네 유형에 포함하지 않고 별도 `cap_check`에 저장한다.

## 제46조 4년 분급 시드정책

교육용 상품의 계약체결비용을 월납환산 초회보험료의 3,000%로 가정한다. 이 값은 실제 보험사의 상품 기초서류에서 확인한 규제 수치가 아니라 합성 상품을 위한 `PROJECT_ASSUMPTION`이다. 실제 연계 시에는 보험사·상품·판매버전별 기초서류 값을 `INSURER_RULE`로 적재해 대체한다. (`REG-02`, `SRC-022`; 기사 예시의 비규제성은 `SRC-016`)

### 규제 상한 (`REGULATORY` — 회사가 바꿀 수 없음)

| 항목 | 상한 | 근거 |
|---|---|---|
| 선지급수수료 총액 | 계약체결비용 이내 | REG-02, 제4-32조제11항 |
| 유지관리수수료 월 지급액 | 계약체결비용의 **1.5% 이내** | REG-04, 부칙 제3조 (제12항의 `0.8%`를 `1.5%`로 읽음) |
| 유지관리수수료 지급기간 | 최대 **4년(48개월)** | REG-04, 부칙 제3조 (제12항의 `7년`을 `4년`으로 읽음) |
| 유지관리수수료 총액 | 계약체결비용 이내 (최대치 검산 1.5% × 48 = **72%**) | REG-03 제4호, REG-04 |
| 적용 대상 | 일반채널, 2027.1.1~2028.12.31 특례기간 | REG-19, 부칙 제2·3조 |

### FGC 시드정책 (`GA_POLICY` / `PROJECT_ASSUMPTION`)

| 항목 | FGC 선택값 | 분류·근거 |
|---|---|---|
| 계약체결비용 | 월납환산 초회보험료 × 30 (3,000%) | `PROJECT_ASSUMPTION` — 합성 상품 기초서류 입력값 (`REG-02`, `SRC-016·022`) |
| 선지급수수료 | 계약 1회차 월납보험료의 600% | `GA_POLICY` — 계약체결비용의 20% 사용 (`REG-02`, `SRC-022`) |
| 유지관리수수료 | 계약체결비용의 월 **1.5%** | `GA_POLICY` — 규제상 월 상한 이내 선택 (`REG-04`, `SRC-003·022`) |
| 지급기간 | 1~48차월 | `PROJECT_ASSUMPTION` — 최대 48개월만 규제상 한도이며 최초 지급회차는 근거 없음 — 확인 필요 (`REG-04`, `SRC-003·022`) |

> FGC는 월 상한율을 상한과 같은 값으로 잡았다. 상한과 회사 선택값이 우연히 같더라도 **두 값은 다른 분류**이므로 규제 상한 정책은 `REGULATORY`, FGC 지급률 정책은 `GA_POLICY`로 분리한다. 계약체결비용과 최초 지급회차처럼 실제 기초서류·지급기준을 확보하지 못한 값은 `PROJECT_ASSUMPTION`으로 표시한다. (`REG-02~04`, `SRC-003·016·022`)

### 월납보험료 100,000원 검산

```text
계약체결비용   = 100,000 × 30 = 3,000,000원

[선지급수수료]
  지급액       =   600,000원
  한도         = 3,000,000원 (계약체결비용)
  사용률       = 20.0%                          → 정상

[유지관리수수료]
  월액         = 3,000,000 × 1.5% = 45,000원
  월 한도      = 3,000,000 × 1.5% = 45,000원
  월 사용률    = 100.0%                          → 정상 (상한 이내)
  총액         = 45,000 × 48 = 2,160,000원
  총액 한도    = 3,000,000원
  총액 사용률  = 72.0%                           → 정상

[초년도 1,200%]
  초년도 예정  = 600,000 + 45,000 × 12 = 1,140,000원
  한도         = 100,000 × 12 = 1,200,000원
  사용률       = 95.0%                           → WARNING
```

초년도 사용률이 95%이므로 시책·지원금·공통비가 조금이라도 추가되면 바로 `VIOLATION`이 된다. 4년 분급 시드계약은 1,200% 여유가 거의 없는 상태로 설계한 것이며 이는 의도한 것이다.

계약체결비용은 전액 지급해야 하는 목표금액이 아니라 지급한도다. `(계약체결비용 − 선지급수수료) ÷ 48 = 50,000원`으로 강제하면 월 1.666667%가 되어 1.5% 상한을 초과하므로 사용하지 않는다.


## 제47조 7년 분급 시드정책

### 규제 상한 (`REGULATORY` — 회사가 바꿀 수 없음)

### 두 수수료의 한도는 합치지 않는다

유지관리수수료(월 0.8%)와 장기유지수수료(월 0.4%)는 **조문상 서로 다른 호에 규정된 별개 한도**다. 합쳐서 월 0.8%를 넘으면 안 된다는 규정은 없다.

```text
장기유지수수료 지급 구간에는 두 수수료가 동시에 지급된다.
  유지관리   월 0.8% 이내
+ 장기유지   월 0.4% 이내
= 해당 월 최대 1.2%
```

`maintenance_check.limit_valid_yn`은 **두 수수료를 각각 별도로** 월 상한과 비교한다. 합산액을 하나의 상한과 비교하지 않는다.

> `PROJECT_ASSUMPTION` — REG-03 제4호의 "총액은 계약체결비용 이내"에 장기유지수수료가 포함되는지는 조문에 명시되어 있지 않다. FGC는 **포함되는 것으로 보수적으로 가정**하고 두 총액의 합을 계약체결비용과 비교한다. 최대치로 계산해도 67.2% + 9.6% = 76.8%이므로 어느 해석을 따르든 한도를 넘지 않는다. 최종 FAQ 공문이 확정되면 재검토한다.

## 제48조 계약상태와 담당자

- `ACTIVE`, 정책상 허용된 `REVIVED`: 지급 가능
- `UNPAID`: 가상 정책상 보류
- `LAPSED`, `TERMINATED`, `CANCELLED`: 미래 유지관리 지급 중단
- 부활 후 소급지급은 자동으로 하지 않고 `REVIEW_REQUIRED`
- 최초 모집설계사와 현재 유지관리 담당자를 분리
- 담당자 변경일 이전 확정 회차는 변경하지 않음

월중 상태변경의 당월 지급기준은 공식 최종기준 확보 전까지 `PROJECT_ASSUMPTION`으로 관리한다.

## 제48조의2 4년·7년 분급 환수 운영원칙

4년·7년 분급의 지급중단·환수·회수는 다음 원칙으로 처리한다. (`REG-13·14·16`, `SRC-016·019·020`)

1. 보험회사→GA(`INSURER_TO_GA`)와 GA→설계사(`GA_TO_FC`)의 환수 규칙·사건·원장행을 분리한다.
2. 해지·실효 뒤 아직 지급하지 않은 미래 유지관리수수료를 중단하는 것과 이미 지급한 금액을 환수하는 것을 구분한다. 미래 미지급액은 환수액으로 기록하지 않는다. (`REG-13`, `SRC-022`)
3. 실제 환수율은 보험회사·상품·수수료항목·계약일·경과회차·책임사유별 `clawback_rule` 정책버전으로 관리한다. (`REG-14`, `SRC-019·020`)
4. 일반 해지·실효와 설계사 귀책 사유를 구분하되, 업계자료에 등장하는 특정 환수율이나 `100% 환수` 표현을 공통 법정값으로 자동 적용하지 않는다. 실제 위탁·위촉계약 또는 회사 지급기준이 필요하다. (`REG-14·16`, `SRC-016·019·020`)
5. 기사·분석자료에 제시된 조항 번호나 예시 수치는 법령 파라미터로 직접 등록하지 않는다. 확인 전에는 `PROJECT_ASSUMPTION` 또는 `REVIEW_REQUIRED`로 남긴다. (`REG-14·16`, `SRC-016`)
6. 적용일 현재 유효한 회사별 약정 원본을 확보하지 못하면 **근거 없음 — 확인 필요**로 표시하고 환수 확정을 차단한다. (`REG-14·16`; `SRC-021` 미확보)

# 제14장 정책변경과 감사

## 제49조 정책상태

```text
DRAFT → REVIEW → APPROVED → ACTIVE → RETIRED
           ↘ DRAFT
APPROVED → RETIRED
```

`APPROVED`, `ACTIVE`, `RETIRED` 정책과 상세 규칙은 수정·삭제하지 않는다. 변경은 새 `version_no`로 만든다.

## 제50조 1차 정책관리 방식

1차에는 정책 CRUD 화면을 만들지 않는다.

- 정책은 Flyway 시드로 적재하되, `DRAFT`로 INSERT하고 규칙 행을 모두 넣은 다음 `DRAFT → APPROVED → ACTIVE` 두 단계로 승격한다. `ACTIVE` 정책 아래에는 규칙 행을 추가할 수 없다.
- `created_by`와 `approved_by`는 모두 필수이며 서로 다른 사용자여야 하고, `APPROVED` 전환 시 `approved_at`과 승인근거를 함께 기록한다. 이 분리는 v2.1.6부터 신규 `APPROVED`·`ACTIVE` 행에 DB CHECK로 강제된다.
- 조회·적용만 가능
- 변경 시 새 마이그레이션과 새 정책버전 생성
- 2차부터 작성·검토·승인 화면 제공

예외적으로 `db/migration/V2__batch_watermark_and_schedule_eligibility.sql`이 만든 `STATUS-MONTH-RULE-2026` v1은 작성자·승인자 없이 `ACTIVE`로 직접 삽입된 유산 행이다. v2.1.6의 `ck_policy_authorship`가 `NOT VALID`인 이유도 이 행을 보존하기 위해서다. `db/demo/V3`가 로드되면 v1을 `RETIRED`하고 정상 절차의 v2를 발행하지만, 기본 `db/migration`만 적용한 DB에는 유산 행이 남을 수 있다. 운영 전 해당 행을 폐기·재발행하고 제약을 `VALIDATE`하기 전까지 정책 저작통제가 완결되었다고 표시하지 않는다.

## 제51조 감사대상

- 정책버전 활성화·종료
- 계약·상태 사건
- 지급 건과 계약귀속
- 1,200% 포함·제외 판단
- 정착지원금·공통비 배부근거
- 검증 실행과 확정
- 예외 담당·상태·처리사유
- 원장 역분개·재기표
- 역할·권한 변경

`audit_log`는 append-only 증거 저장소이지만 위 사건을 모두 자동 수집하는 범용 감사 트리거는 아니다. 정책·지급·예외·권한을 변경하는 서비스는 같은 트랜잭션에서 감사행을 명시적으로 생성해야 하며, “테이블이 있으므로 감사로그 기록률 100%”라고 가정하지 않는다.

# 제15장 ERD·요구사항 최종 고정사항

## 제52조 ERD·유효 스키마 v2.1.7 확정사항

다음 구조는 그대로 확정한다.

- `product` / `product_offering` 분리
- `commission_transaction` / `transaction_attribution` 분리
- `payment_stage` 분리
- `schedule_line.expected_amount` 단일 예상금액 원천
- `validation_run` 검증잠금
- 정책버전 불변 처리
- 운영·비교·시뮬레이션 스케줄 분리
- 원수사 설계사코드 브리지
- 원장 역분개·재기표
- `FINALIZED` 하위결과 잠금
- `policy_version.source_class` 전용 컬럼
- `transaction_attribution.attribution_date` 일 단위 귀속일과 `AGENT` 귀속범위
- `arbitrage_check.payment_stage`
- 원 단위 `HALF_UP` 반올림 스냅샷
- 확정 스케줄 헤더의 상태 되돌리기 차단
- `batch_watermark`의 Job·Step별 워터마크
- `policy_parameter`의 소규모 버전 파라미터
- `contract_status_event_processing`의 Job별 append-only 처리이력
- `acquisition_cost_check_detail`의 네 계약체결비용 검증유형
- `validation_run.current_step`과 실행상태의 결합 제약
- `cap_check_detail.item_code`, `item_name`, 조건부 `contract_month_no` 계산시점 스냅샷

유효 스키마는 V1 baseline v2.1.2에 V2(v2.1.3), V2_1(v2.1.4), V5(v2.1.5), V6(v2.1.6), V7(v2.1.7)을 순서대로 적용한 결과다. 파일명이 V1에 적힌 단일 baseline만 보고 현재 ERD를 판단하지 않는다.

## 제53조 요구사항 문구를 맞춰야 하는 사항

### 1. 계약상태

- `contract_status_event`는 1차 입력·검증근거 테이블로 사용한다.
- 상태전이 UI와 자동 지급보류·재개는 2차다.
- FUN-025~029는 “테이블 존재”와 “애플리케이션 기능”을 구분해 적는다.

### 2. 정책관리

- FUN-011은 1차 조회·적용
- FUN-012·013의 관리자 정책설정 화면은 2차
- 1차 정책변경은 Flyway 새 버전만 허용

### 3. 초년도 귀속일

- OI-019의 `accrual_date` 대신:
  - 예상행은 `schedule_line.due_date`
  - 실제행은 `transaction_attribution.attribution_date` (일 단위)
- 초년도 판정식은 `계약일 <= 귀속일 < 계약일 + 1년`이다.
- `attribution_month`는 월별 집계키이며 초년도 경계 판정에 사용하지 않는다.
- `settlement_month`는 월 명세 묶음 기준이며 초년도 판정일로 사용하지 않는다.

### 4. 공통비

- `allocation_policy` 구조는 유지한다.
- 1차 범용 안분엔진은 개발하지 않는다.
- 정규화된 계약별 배부결과를 입력받고 총액·근거만 검증한다.

### 5. 차익거래의 지급수수료

- `arbitrage_check.paid_commission_amount`는 확정 지급액에서 확정 차감액을 뺀 순누계다.
- 총 지급액·총 차감액은 `calculation_snapshot`에 저장한다.

### 6. 2026년 규제범위 표현

발표·문서에는 다음 표현을 사용한다.

> “FGC는 2026년 3월 이후 판매수수료 개편 중 계약별 금액통제에 해당하는 차익거래, 2026년 7월 이후 GA 설계사 1,200%룰, 현행 수수료 스케줄·원장·대사를 구현한다. 비교설명·소비자 공시·보험회사 상품위원회 전체 업무는 시스템 경계 밖이며 필요한 메타데이터만 보관한다.”


## 제54조 확정 상태와 남은 작업

본 문서는 `v1.0 규제·스키마·추가자료 정합성 보정본(2026-08-10)`이며 팀에 배포한다. 이는 운영정책의 승인본이라는 뜻이며, 아래의 애플리케이션·전체 GOLDEN 시드가 모두 구현되었다는 완료선언은 아니다. (`REG-02~05·13·14·16·21`, `SRC-016·019·020·022·025`)

### 이 문서에 종속되지 않는 남은 작업

아래 작업은 본 문서를 기준으로 진행하며, 진행 결과가 본 문서를 바꾸지 않는다. 따라서 배포를 막지 않는다.

1. 요구사항명세서 v2.2.1에 제53조의 여섯 문구 반영
2. 현재 축소 `db/demo`와 별도로 전체 GOLDEN 시드 SQL 작성 (정책 승격 순서를 반드시 지킬 것)
3. `src/test/resources/sql/golden_reset.sql`, `golden_expected_assertions.sql`, `load_data_generator.sql` 작성
4. REG-10 TM 2028 채널분리 룰셋 및 REG-17·18·24 범위표시 회귀테스트
5. 월 통합검증 서비스·배치 구현 후 전체 회귀테스트 실행
