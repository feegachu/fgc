# FGC 가상 GA 운영정책서 v1.0

> 이 문서는 실제 특정 GA의 내부규정이나 운영시스템을 복제한 문서가 아니다.  
> 공개된 법령·FAQ·보험회사 지급자료·GA 영업규정 사례·특허를 바탕으로 만든 **교육용 가상 대형 GA의 정산·내부통제 정책**이다.  
> 법률자문서, 실제 보험회사 지급약정서 또는 실제 회계정책서로 사용할 수 없다.

> **정합성 기준:** 규제 판단은 `FGC 규제 근거·조문표 v0.2.1`의 근거 우선순위와 REG-01~24를 따르고, 물리 DB 판단은 `src/main/resources/db/migration/`의 V1~V55를 버전 순서대로 적용한 결과를 따른다. `v2.1.7`은 V7까지의 스키마 이름이며 V9 이후는 Flyway 버전 번호로만 부른다. `db/demo`(V3~V56)의 시드는 축소 검증자료이며 규제 또는 운영정책의 원천이 아니다.

## 0. 문서의 목적

FGC 팀은 실제 보험회사·GA와 전산 연계하거나 현업 담당자에게 업무 검증을 받을 수 없다. 따라서 다음 원칙으로 프로젝트 범위를 고정한다.

1. FGC금융서비스라는 **가상 대형 법인보험대리점(GA)**을 정의한다.
2. 원수사 데이터는 수집·변환이 끝나 **FGC 표준 DB에 정규화되어 적재된 상태**로 시작한다.
3. 규제상 의무, 원수사 지급기준, GA 내부 지급정책, 프로젝트 가정을 구분한다.
4. 실제 개인정보·실제 증권번호·실제 설계사 지급액을 사용하지 않고 합성 데이터를 사용한다.
5. FGC는 실제 송금·세금신고·보험청약·법정 회계결산을 수행하지 않는다.
6. FGC의 핵심 역할은 예상액 계산, 규제검증, 복식부기형 검증원장, 실제명세 대사, 예외관리이다.
7. 법정 수치·시행일·FAQ 운영기준은 원칙적으로 승인된 `policy_version`·정책상세·`policy_parameter`로 버전 관리한다. 예외: **설정 누락을 판별하는 기준값**은 코드 상수로 둔다. 1,200%룰 단계별 시행일(보험회사→GA 2021-01-01, GA→설계사 2026-07-01)이 그렇다(`CapApplicabilityPolicy`, #522). 이 값은 이미 지난 법령 부칙 값이고, 룰셋이 빠졌을 때 "비적용"과 "설정 누락"을 가르는 기준이기 때문이다. 차익거래 적용일은 정책 파라미터(`ARBITRAGE_EFFECTIVE_CONTRACT_DATE`)로 둔다(#475).

### 문서에서 사용하는 구현상태

| 표시 | 의미 |
|---|---|
| `DB 강제` | CHECK·FK·UNIQUE·트리거가 위반 저장 자체를 차단한다. |
| `서비스 강제` | DB 구조는 보유하지만 계산·선택·게이트는 애플리케이션이 수행해야 한다. |
| `메타데이터만` | 외부 의무 자체는 범위 밖이고 근거·버전·결과 연결정보만 저장한다. |
| `미구현/향후` | 테이블이 있더라도 실행 서비스·화면·배치가 아직 제공되지 않는다. |

테이블 존재만으로 규제 기능이 구현되었다고 판단하지 않는다. 특히 2차용 테이블은 현재 스키마에 물리적으로 존재하더라도 애플리케이션 제공범위와 별개다(SRC-027 D-03).

# 제1장 회사와 시스템의 범위

## 제1조 가상 회사 정의

| 항목 | 확정 내용 |
|---|---|
| 회사명 | FGC금융서비스 주식회사 |
| 회사 성격 | 여러 보험회사의 상품을 판매하는 법인보험대리점(GA) |
| 회사 상태 | 교육용 가상 회사 |
| 소속 설계사 규모 | 기준일 직전 분기 일평균 소속 설계사 **600명** (`PROJECT_ASSUMPTION`, DAR-012·OI-024 — r19 초안, 팀 승인 시 확정). 감독규정 제4-11조①의 대형 GA 기준(500명 이상)을 넘으므로 별표 5의6 제5호 비교·설명 의무가 적용된다(SRC-022·SRC-056). 레코드 수(해촉 포함)로 대형 GA를 증명하지 않고 데이터셋 메타데이터의 가정값으로 기록하며, 활동 설계사는 500명 미만이 되지 않게 생성한다 |
| 조직구조 | GA 1 → 본사 1 → 본부 → 지사(지점) → 팀 → 설계사 (`organization_type` = GA·HQ·DIVISION·BRANCH·TEAM). 개수는 데이터셋마다 다르다 — 2차 600인 데이터셋은 지점 12곳 예시(DAR-012), 1차 축소 시드는 본부 2·지사 2·팀 3(`db/demo/V3`) |
| 취급 영역 | 생명보험·손해보험의 장기 보장성보험 중심 |
| 모집 채널 | **대면 모집만**(`FACE_TO_FACE`). 통신판매종사자(TM)를 두지 않고 방송채널사용사업자로 승인된 보험대리점도 아니다 — `PROJECT_ASSUMPTION`, 2026-10-13 팀 결정 (SRC-036) |
| 1차 데모 보험회사 | 가상 생보 4개사, 가상 손보 2개사 |
| 1차 사용자 | 시스템관리자, GA관리자, 정산담당자, 준법·감사 |
| 2차 추가 사용자 | 설계사(`AGENT`) — 본인과 연결된 설계사 1명(`app_user.agent_id`)의 데이터만 본다(FUN-085, r19 초안). 경계는 제58조 |
| 정산 기준 통화 | 원(KRW) |
| 시스템 시간대 | Asia/Seoul |
| 데이터베이스 | PostgreSQL 17 |

멀티 GA 테넌트 격리는 2차에서도 구현하지 않는다 — 가상 GA는 한 곳이다(OI-010, 프로젝트 가정).

실제 회사 자료에서 확인되는 FC·팀장·지사장·본부장 등의 용어는 업무구조 참고에만 사용한다. FGC금융서비스의 조직·지급률은 독자적인 가상 정책이다.

## 제2조 제품 정의

FGC는 다음 제품으로 정의한다.

> **가상 대형 GA의 계약별 판매수수료 예상·지급 데이터를 계산하고, 1,200%룰·차익거래·분급·복식원장·대사 규칙을 검증하여 예외를 관리하는 내부통제 시스템**

### 포함 범위

- 보험회사·상품·상품 판매버전·조직·설계사 기준정보 조회
- 보험계약과 계약상태 사건
- 원수사→GA 예상 수입 스케줄
- GA→설계사 예상 지급 스케줄
- 실제 원수사 지급명세와 GA 지급 건
- 계약별 수수료 귀속
- 초년도 1,200% 한도 검증
- 차익거래 후보 검증
- 예상·실제 금액 대사
- FGC 내부 검증용 복식원장
- 예외 처리와 감사로그
- 2차의 4년·7년 분급, 유지관리, 계약체결비용, 환수·상계

### 제외 범위

- 보험회사 포털 자동 접속·스크래핑·RPA 수집, 서식 제한 없는 범용 파일 수집, 컬럼 매핑 마스터·스테이징 테이블 (1차·2차 모두 제외)
- 1차: 파일 업로드와 원본파일 보관 전체. **2차 예외(OI-021 결정, 프로젝트 가정)**: 구현된 서식(Must 3종 — 예상 해약환급률표·보험사 정산데이터·협회 수수료 등급자료)의 합성·가상 문서를 AI 문서함으로 올리고, 사람이 검토·확정한 결과만 기존 저장 경로로 반영한다(제55조, FUN-066~069·078). 10/27 PoC 게이트를 통과하지 못하면 LLM 추출을 빼고 xlsx 결정론 파서로 축소한다
- 보험청약·인수심사·보험료 결제
- 실제 계좌이체와 급여 지급
- 세금 원천징수·세무신고
- GA 전체 인사·평가·승격·민원·광고 시스템
- 보험협회의 수수료 등급·순위 산출 자체(협회가 산출해 GA에 제공 — SRC-025 Q19·Q20). 2차는 협회가 준 자료를 적재해 비교설명에 쓰는 기능만 둔다(제56조)
- TM(전화 모집)·방송채널(홈쇼핑) 모집과 그 채널 특례. 감독규정 부칙(제2026-3호) 제1조②·제2조 단서·제3조②와 제4-32조⑦ 제1·2호는 FGC에 적용할 대상이 없으므로 시행일·특례기간은 일반 채널 값 하나만 쓴다 (SRC-036, SRC-022 `:5094-5100`·`:919-921`)
- 법정 회계장부와 재무제표 작성

## 제3조 근거의 종류

모든 규칙은 다음 네 종류 중 하나로 분류한다.

| 분류 | 의미 | 예 |
|---|---|---|
| `REGULATORY` | 회사가 임의로 바꿀 수 없는 법령·고시·FAQ 기준 | 1,200%룰, 차익거래, 4년·7년 분급의 상한·적용시기 (`REG-02~05·19`, `SRC-003·022`) |
| `INSURER_RULE` | 보험회사가 GA에 제공한 회사별 지급기준 | 회차별 수입수수료, 시책, 환수율 |
| `GA_POLICY` | FGC금융서비스가 정한 내부 지급·배부·승인 기준 | FC 지급률, 관리자수수료, 공통비 정책 |
| `PROJECT_ASSUMPTION` | 현업자료 미확보로 팀이 정한 교육용 가정 | 자료 도착일, 월중 부활 처리, 대사 허용오차 |

정책 화면과 계산근거에는 이 분류, 유효기간, 정책버전, 출처참조를 표시한다.

`source_class`는 설명용 문자열 배열에 넣지 않고 `policy_version.source_class` 전용 컬럼으로 저장한다.
허용값은 `REGULATORY`, `INSURER_RULE`, `GA_POLICY`, `PROJECT_ASSUMPTION`뿐이다.
승인·활성·폐기된 정책은 `source_class`를 포함하여 수정할 수 없으며 새 정책버전을 생성해야 한다.

`source_class`는 정책의 소유 성격이고, 규제조문표의 `[현행규정]`, `[개정고시]`, `[시행세칙]`, `[FAQ-1차]`, `[FAQ-2차]`, `[해석]` 같은 **근거 상태 태그와는 다른 축**이다. 다음 값을 함께 보존한다.

- `policy_version.regulation_refs`: `REG-08`, `REG-10` 같은 규제조문표 식별자
- `policy_version.source_refs`: 공문번호·문서명·파일명·원문 버전
- `policy_parameter`: `REGULATION_SOURCE_TYPE`, `FAQ_VERSION`, `FAQ_APPROVAL_STATUS`, 경계사례 해석값
- 계산 결과의 `calculation_snapshot`: 실제 선택된 정책·파라미터·기준일

`policy_version.status=APPROVED`는 FGC 내부 정책 승인상태이지 FAQ가 최종 공문이라는 뜻이 아니다. 배포안 FAQ를 근거로 한 정책은 내부 승인을 거쳐도 `FAQ_APPROVAL_STATUS=DRAFT` 또는 동등한 값을 유지하며, 최종 FAQ가 나오면 기존 행을 고치지 않고 새 정책버전을 발행한다. 현재 `FAQ_APPROVAL_STATUS`·`FAQ_VERSION`·`REGULATION_SOURCE_TYPE` 파라미터는 어느 정책에도 적재되지 않았다(미구현). 배포 차수는 지금 `source_refs`(SRC-024/025)로 구분하며, FAQ 배포안을 근거로 한 정책을 2차에 새로 승인할 때부터 파라미터를 넣는다.

## 제4조 자료 우선순위

1. 현행 보험업감독규정
2. 금융위원회 개정고시와 부칙
3. 보험업감독업무시행세칙과 별표
4. 금융위·금감원 공식 FAQ
5. 금융위원회 공식 보도자료
6. 보험협회 자율규제·공시기준
7. 보험회사 지급기준·GA 내부규정·위촉계약
8. 특허·연구보고서·업계자료
9. FGC 프로젝트 가정

상위 근거와 하위 자료가 충돌하면 상위 근거를 우선한다. 확인되지 않은 내용은 `REVIEW_REQUIRED(사람의 검토가 필요한 상태)`로 남긴다.

# 제2장 릴리스별 운영범위

## 제5조 1차 릴리스

1차 개발은 2026년 8월 23일까지 완료한다.

### 1차 규제·업무 범위

| 구분 | 처리 |
|---|---|
| 2026.3 이후 차익거래 방지 | 계약 전 기간의 시계열을 이용해 후보 검증 |
| 2026.7.1 이후 GA→설계사 1,200%룰 | 월납 보장성 합성계약에 계약별 적용 |
| 원수사→GA 1,200%룰 | 별도 지급단계 게이지로 검증 |
| 현행 회사별 지급방식 | 원수사→GA와 GA→설계사 예상 스케줄 생성 |
| 실제명세 대사 | 양방향 예상·실제 전수 비교 |
| 복식부기 검증원장 | 예상·실제·확정 금액의 차변·대변 균형 검증 |
| 예외관리 | 한도·대사·원장·차익거래 예외 처리 |
| 월 통합검증 | 사용자가 월을 선택해 수동 실행하고 결과 잠금 |

### 1차 적용 계약군

- 1,200% 데모: 2026-07-01 이후 체결된 월납 보장성보험
- 차익거래 데모: 2026-03-01 이후의 월납 보장성보험
- 일시납·연납·저축성·자동차·일반보험: 계산엔진 확장 대상으로 남기고 1차 규제판정에서는 제외
- 현재 구현 상태(develop fe6d0e6c): 1,200%·차익거래 판정은 보장성 여부와 계약일만 거르고 **납입주기는 거르지 않는다.** 비월납 보장성 계약을 등록하면 입력한 월납환산 초회보험료로 판정된다. 이 조·OI-018과 다르므로 비월납 계약은 시연 데이터에 넣지 않는다. 2차에서 비월납을 판정 대상에 넣을지는 근거 없음 — 확인 필요(제4-32조⑤의 "1년간 납입할 것으로 예상되는 보험료"를 연납·일시납에 어떻게 적용할지 원문 확인 필요)
- 2026년 3~6월 계약: 차익거래는 검증하되 GA→설계사 1,200%룰은 적용하지 않는다.
- 2026년 7월 이후 계약: 원수사→GA와 GA→설계사 게이지를 각각 계산한다.

# 제3장 데이터 수신과 처리시점

## 제7조 정규화 데이터 전제

FGC는 원수사 자료를 직접 수집하지 않는다. 다음 데이터가 이미 표준화되어 DB에 들어온 것으로 가정한다.

1. 신계약 데이터
2. 보유계약과 현재 상태
3. 보험료 수금·누적납입 데이터
4. 수수료·수수료환수 데이터
5. 시책 데이터
6. 상품·상품코드·판매버전
7. 수수료율·지급방식·환수율
8. 예상 해약환급률표

마이데이터 보험 API는 계약·상품·상태·납입주기 명칭을 참고하는 보조자료이며, 원수사→GA 판매수수료 인터페이스로 간주하지 않는다.

2차는 이 전제를 유지하되, 보험회사·협회가 GA에 문서로 준 일부 서식을 담당자가 직접 올려 같은 표준 구조로 넣는 경로를 예외로 둔다(제55조, OI-021).

### 전제의 예외 — 수기 등록 계약의 초회 재무 스냅샷

위 3번(보험료 수금·누적납입 데이터)은 정규화 적재를 전제하지만, 화면(FGC-UI-CONT-W03)에서 수기로 등록한 계약에는 적재된 스냅샷이 존재하지 않는다. 이 계약은 `contract_financial_snapshot`이 없어 제32조 차익거래 검증이 항상 `REVIEW_REQUIRED`(자료부족)로 빠진다.

따라서 계약 저장 트랜잭션에서 다음 1행을 시스템이 생성한다.

| 필드 | 값 | 근거 |
|---|---|---|
| `as_of_date` | 계약일 | 등록 직후 검증이 가능해야 한다 |
| `contract_month_no` | 1 | 초회 |
| `cumulative_paid_premium` | 계약의 초회보험료 | 계약 시점 누적 납입액은 정의상 초회보험료와 같다 |
| `surrender_value` | `NULL` | **자동 산정 금지** |
| `surrender_value_type` | `EXPECTED_TABLE` | 실제 환급금이 나중에 적재되면 `ACTUAL`이 우선한다 |
| `refund_rate_table_id` | `NULL` | 표를 임의로 지정하지 않는다 |
| `source_ref` | `MANUAL_CONTRACT_INITIAL` | 합성 근거 표기 |

해약환급금은 채우지 않는다. 표준해약공제액 80% 이상 공제 상품이면 환급률표가 없는 상태이므로 제33조의 해약환급금 합산 대상 판정에서 `REVIEW_REQUIRED`가 나오며, 이것이 의도된 동작이다. 억지로 환급금을 추정해 차익거래 판정을 만들지 않는다(REG-23).

이 규칙의 근거분류는 제3조의 `PROJECT_ASSUMPTION`이다. 현업 수금자료를 확보하지 못한 상태에서 시연·수기 등록 경로를 성립시키기 위한 프로젝트 가정이며, 정규화 적재가 도입되면 적재분이 우선한다. 1차는 파일 업로드·스테이징을 만들지 않으므로 COR-010과 충돌하지 않는다(2차 예외는 제55조).

### 초회보험료 정정과 재무 스냅샷 버전 (#389)

수기 합성 초회 스냅샷의 보험료를 정정하면 동일 업무 기준일에 `snapshot_version`을 증가시키고 `previous_snapshot_id`로 직전 행을 연결한 새 행을 추가한다. 기존 값은 보존하며 동일 내용 재요청에는 버전을 추가하지 않는다. ACTUAL·시드·정규화 적재·후속 월별 자료는 계약의 초회보험료로 대체하지 않는다.

계약일 정정은 변경된 날짜의 업무키에 반영하고 과거 합성 행을 보존한다. 차익거래 조회는 현재 계약일의 합성 초회 자료와 기준일 이하의 다른 자료 중 동일 업무키의 최신 버전을 사용하며, 최신 기준일·같은 기준일 ACTUAL 우선순위를 유지한다. 계산 결과에는 사용한 스냅샷 ID·버전·출처를 보관한다.

## 제8조 시점의 구분

계약상태 원본과 배치 처리이력을 분리한다.

| 테이블·컬럼 | 설명 | 운영규칙 |
|---|---|---|
| `contract_status_event.effective_at` | 상태가 실제 효력을 발생한 시점 | 규제판정·스케줄 자격의 기준 |
| `contract_status_event.received_at` | FGC DB가 상태를 받은 시점 | 지연수신·순서역전 판정 |
| `contract_status_event.processed_at` | v2.1.6 이전 호환용 처리시각 | **폐기 예정 컬럼. 신규 코드에서 읽거나 쓰지 않음** |
| `contract_status_event_processing.processed_at` | 특정 Job이 사건을 처리한 시각 | 신규 처리이력의 기준 |

계산은 원칙적으로 `effective_at`을 기준으로 한다. 늦게 들어온 사건도 과거 효력일에 맞춰 재검증한다.

`contract_status_event_processing`은 사건과 `processing_job`별로 `SUCCEEDED` 또는 `FAILED` 행을 추가하는 append-only 이력이다. 실패는 재시도마다 새 행으로 남기고, 사건×Job의 성공은 최대 1행만 허용한다. 미처리 사건은 반드시 `processing_job=:jobName`을 조건으로 한 `NOT EXISTS`로 조회한다. 한 Job의 성공을 다른 Job의 처리완료로 간주하지 않는다.

`contract_status_event_processing.processed_at >= contract_status_event.received_at`은 부모·자식 간 조건이라 현재 DB CHECK가 강제하지 않는다. 서비스가 검증하고 위반 시 데이터품질 예외를 만든다.

## 제9조 실제 운영주기 가정

다음은 법정 공통주기가 아니라 FGC금융서비스의 프로젝트 가정이다.

| 업무 | 가상 운영주기 | 현재 구현(fe6d0e6c) / 2차 |
|---|---|---|
| 신계약·상태·수금 데이터 반영 | 매일 01:00까지 정규화 DB 반영 | 시드 또는 화면 수기등록 |
| 변경 계약 재검증 | 매일 02:00 | `DailyChangedContractJob`(IF-BAT-02)이 매일 02:00 KST 자동 실행(`fgc.batch.daily-changed-contract`), 계약 상세의 수동 재검증도 가능 |
| 원수사 월 지급명세 반영 | 다음 달 제5영업일까지 | 1차: 시드 적재·TRAN-W02 수기 등록. 2차: AI 문서함 정산데이터 업로드·확정(FUN-068, 제55조) |
| 월 통합검증 | 제6영업일 | 화면에서 수동 실행 |

| 실제 설계사 지급 | 제10영업일 | FGC 범위 외 |

## 제10조 실시간과 배치의 역할

### 실시간 처리

- 계약 등록 시 적용 정책과 한도 계산

### 일일 변경분 처리

- 신규·수정된 계약
- 새 상태 사건
- 추가 시책·정착지원금·공통비 귀속
- 정정 지급 건

DB는 `batch_watermark`, `contract_status_event_processing`, `validation_run.current_step`으로 일일·월간 배치를 지원하고, 애플리케이션은 1차부터 Spring Batch Job 두 개를 제공한다(SRC-027 D-02).

| Job | 기동 | 1차 제공 범위 |
|---|---|---|
| `MonthlyValidationJob` (IF-BAT-01) | VRUN-W02 실행 버튼 → `POST /api/v1/validation-runs/{id}/execute` | 제43조 1~8단계 자동, 9~10단계는 사람. `CREATED` 실행만 기동한다. `FAILED` 실행은 재기동하지 않고 새 실행을 만든다 — 실패 지점 재시작은 2차(FUN-045) |
| `DailyChangedContractJob` (IF-BAT-02) | 매일 02:00 KST 자동(`@Scheduled`, 프로젝트 운영 가정) + 수동 재실행 | 변경 계약의 1,200% 재합산·차익거래·원장 불균형 재검사. 실행 유형은 `MANUAL_CONTRACT`이며 확정 대상이 아니다(제44조) |

상태 사건이 없는 계약이 일 배치에서 실패하면 다음 날 자동으로 다시 읽히지 않는다(워터마크가 전진하므로). 실패는 데이터 품질 예외·검토 큐로 남는다(#522).

`batch_watermark`의 업무키는 `(job_name, step_name)`이다. 워터마크 후퇴의 승인·사유·감사기록은 DB가 자동 생성하지 않으므로 운영 서비스가 남겨야 한다.

# 제4장 계약·설계사·조직 정책

## 제11조 계약 식별

- 계약 업무키: `보험회사 + 증권번호`
- DB 유니크 키: `(insurer_id, contract_no)`
- 주계약과 특약은 차익거래 검증 시 증권번호 단위 합산을 원칙으로 한다.
- 실제 고객명·주민번호·주소는 저장하지 않는다.
- 화면에 필요한 고객 표시는 `합성 고객 식별명`만 사용한다.

## 제12조 보험료 기준금액

계약에는 다음 금액을 구분한다.

| 컬럼 | 의미 |
|---|---|
| `premium_per_cycle_amount` | 납입주기 1회의 실제 보험료 |
| `first_premium_amount` | 초회 실제 보험료 |
| `monthly_equivalent_first_premium` | 월납환산 초회보험료 |
| `standard_surrender_deduction_amount` | 표준해약공제액 관련 입력값 |

1차는 월납만 판정하므로 세 금액이 동일한 사례를 기본으로 한다. 연납·일시납은 2차 확장용 데이터만 보관한다. 단, 현재 구현은 납입주기를 거르지 않는다(제5조 1차 적용 계약군).

## 제13조 계약상태

| 코드 | 쉬운 설명 |
|---|---|
| `APPLIED` | 청약 단계 |
| `ACTIVE` | 정상 유지 |
| `UNPAID` | 보험료 미납 |
| `LAPSED` | 실효, 계약 효력이 정지됨 |
| `REVIVED` | 부활, 효력이 다시 살아남 |
| `CANCELLED` | 청약철회·취소 |
| `TERMINATED` | 해지·종료 |
| `MATURED` | 만기 |

1차에서도 차익거래 근거를 위해 `contract_status_event`를 입력 데이터로 보유한다.  
다만 상태전이 자동화, 미래 스케줄 자동보류·재개, 부활 판단 화면은 2차 기능이다.

현재 구현(fe6d0e6c)은 계약을 처음 저장할 때 `NEW_CONTRACT` 사건 1건만 만든다. 계약 수정 화면에서 상태를 바꿔도 상태 사건을 만들지 않는다(`ContractServiceImpl` TODO FUN-026). 이런 계약은 효력일을 알 수 없으므로 ① 일일 배치 차익거래는 기준일을 실행일로 쓰고 ② 대사·월 검증의 "지급예정일 시점 상태" 판정은 사건이 없는 회차를 지급 대상으로 남긴다. 2차 FUN-026은 상태 변경을 반드시 사건 등록(효력일·접수일·사유) 경로로만 하게 하고, 수정 화면의 직접 상태 변경을 막거나 같은 트랜잭션에서 사건을 만든다.

## 제14조 설계사와 보험회사 코드

한 설계사가 보험회사마다 다른 코드를 가질 수 있으므로 `agent_insurer_code`로 매핑한다.

```text
보험회사 + 원수사 설계사코드 + 효력기간 → FGC agent_id
```

대사 시 예상 수취인과 실제 명세의 원수사 설계사코드가 다른 경우 `AGENT_MISMATCH`로 분류한다.

## 제16조 수수료 항목

| 항목코드 | 한글명 | 기본 현금흐름 | 1차 |
|---|---|---|---|

| `MAINTENANCE_COMMISSION` | 현행 계약관리·유지성 수수료 | 지급 | 사용 |
| `INCENTIVE` | 시책수수료 | 지급 | 사용 |
| `MANAGEMENT_COMMISSION` | 관리자수수료 | 지급 | 사용 |
| `SETTLEMENT_SUPPORT` | 경력설계사 정착지원금 | 지급 | 사용 |
| `NEWCOMER_SUPPORT` | 신인활동지원비 | 지급 | 사용 |
| `COMMON_COST` | 모집 관련 공통비 | 지급 또는 비용귀속 | 사용 |
| `ADJUSTMENT` | 정정금액 | 지급·차감 | 사용 |
| `CLAWBACK` | 환수 | 차감 | 2차 |
| `RECOVERY` | 환수금 회수 | 차감·회수 | 2차 |
| `LONG_TERM_MAINTENANCE` | 장기유지수수료 | 지급 | 2차 |

항목명만으로 1,200% 포함·제외를 결정하지 않는다. `cap_rule_item`의 정책버전별 판정결과를 사용한다.

- 2027년 이후 분급의 수수료는 **항목코드 + 수수료 구성(`fee_component_type`)** 으로 구분한다. 선지급수수료 = `BASE_COMMISSION` + `UPFRONT`, 유지관리수수료 = `MAINTENANCE_COMMISSION` + `MAINTENANCE`(`equal_monthly_yn=true`), 장기유지수수료 = `LONG_TERM_MAINTENANCE` + `LONG_TERM_MAINTENANCE`(`equal_monthly_yn=true`). 현행 회사별 지급의 계약관리수수료는 `MAINTENANCE_COMMISSION` + `CURRENT`다. 이 매핑은 **업무 규칙 아님 — 가상 GA 정책으로 정함**(구현 설계 규칙, 팀 확정 필요). 실제 보험사 지급기준이 별도 항목을 요구하면 새 항목코드를 추가한다.
- `ADJUSTMENT`는 시드에서 `PAYMENT` 항목이다(항목당 현금흐름은 하나). 차감 방향 정정은 해당 원 항목의 `DEDUCTION` 지급 건이나 제40조 역분개로 처리한다.
- 대여금·교육비(SRC-029 실질 판단 사례)용 항목코드는 아직 없다. 들어오면 `REVIEW_REQUIRED`로 두고, SRC-029 원천 공문 또는 제3차 FAQ가 확보되면 항목코드 신설을 결정한다(근거 없음 — 확인 필요).


## 제17조 지급단계

```text
INSURER_TO_GA : 보험회사 → FGC금융서비스
GA_TO_FC      : FGC금융서비스 → 설계사·관리자
```

두 단계는 별도 예상 스케줄, 지급 건, 귀속, 한도결과, 대사실행을 갖는다.

## 제17조의2 금액 산출·반올림

FGC의 모든 수수료 예상액·실제 귀속액·검증금액은 다음 하나의 규칙을 사용한다.

```text
산출 원금액 = 기준금액 × 요율 ÷ 100
확정 금액   = 산출 원금액을 원 단위(scale 0) HALF_UP 반올림
```

- 요율 계산은 PostgreSQL `numeric`과 Java `BigDecimal`로 수행한다.
- `double`과 `float` 사용을 금지한다.
- 반올림은 **수수료 규칙 1행·계약 1건·수취인 1명·회차 1개 단위**로 먼저 수행한다.
- 월·설계사·조직 합계는 이미 원 단위로 반올림된 상세행을 합산한다.
- 음수는 금액 자체에 부호를 넣지 않고 `cashflow_type=DEDUCTION`으로 구분한다.
- 정책에는 `rounding_scale=0`, `rounding_mode=HALF_UP`을 저장하고,
  스케줄에는 당시 값을 스냅샷으로 보존한다.
- 다른 반올림 방식은 새 정책버전과 요구사항 변경 없이는 허용하지 않는다.
- `commission_rule`·`schedule_line`은 DB CHECK가 `scale 0`·`HALF_UP`만 허용한다(`DB 강제`). `allocation_policy`는 DB가 다른 값(scale 0~6, `HALF_EVEN` 등)을 허용하므로 공통비 배부정책은 저장 시 서비스가 `rounding_scale=0`·`HALF_UP`을 검사한다(`서비스 강제`).

## 제21조 정책선택

계약 1건의 지급단계별 수수료 정책은 다음 조건을 **모두** 만족하는 활성 정책버전에서 고른다(현재 구현: `PolicyVersionRepository#findApplicableCurrentCommissionPolicies`, `CommissionPolicyServiceImpl`).

1. 정책 유형이 판매버전의 수수료체계(`product_offering.fee_regime_code`)와 맞다 — 현행 = `CURRENT_COMMISSION`, 4년 = `FOUR_YEAR_COMMISSION`, 7년 = `SEVEN_YEAR_COMMISSION`(REG-19)
2. 정책 상태가 `ACTIVE`이고 정책 유효기간이 **계약일**을 포함한다
3. 정책의 기초서류 버전이 비어 있거나 판매버전의 기초서류 버전과 같다
4. 판매버전의 판매기간이 계약일을 포함한다
5. 그 정책 아래 해당 지급단계·보험회사·판매버전·조직에 맞는 수수료 규칙이 있다

정확히 하나가 아니면 계산하지 않고 `POLICY_MISSING`(0건) 또는 `POLICY_DUPLICATE`(2건 이상) 검토를 만든다. 고른 정책 안의 규칙 행은 `priority_no`, 회차 구간 순으로 적용하고, GA→설계사 관리자수수료는 직급(`agent_rank_code`)으로 수취인을 정한다. 판매채널은 FGC에서 대면 하나라 선택 조건이 아니다(SRC-036). 1,200% 룰셋 선택은 제27조(지급단계·계약일·보험회사·상품군)를 따른다.

현재 구현은 현행 정책만 선택한다. 4년·7년 판매버전 계약은 전용 정책이 생기기 전까지 `POLICY_MISSING`으로 빠진다(#484, 제45조).

# 제7장 시책·지원금·공통비

## 제22조 시책

- 시책은 보험회사 또는 GA가 일정 상품·기간·실적조건에 따라 추가 지급하는 금액이다.
- 초년도에 귀속되는 시책은 원칙적으로 1,200%에 포함한다.
- 13회차 시책은 실제 귀속월과 지급예정일이 계약 13차월 이후인 경우에만 초년도 밖의 금액으로 본다.
- 초년도에 실제 지급하면서 DB 날짜만 13회차로 바꾸는 행위를 금지한다.
- 정책·지급 건·원장에는 지급근거 문서와 유효기간을 기록한다.

### 가상 시책

| 코드 | 대상 | 지급회차 | 요율 | 판정 |
|---|---|---:|---:|---|
| `INC-STD-100` | 지정 보장성 상품 | 1 | 100% | 포함 |
| `INC-HIGH-300` | 월간 캠페인 상품 | 1 | 300% | 포함, 한도 사전검증 필수 |
| `INC-M13-200` | 13회차 정상유지 계약 | 13 | 200% | 초년도 밖, 선지급 금지 |

`INC-M13-200`은 초년도 밖으로 분류하지만 정상 계약임을 보증하지 않는다. 13회차에 몰린 고율 시책은 우회지급 점검 대상이 될 수 있으므로(REG-22, SRC-025 Q4, SRC-031) 시연에서는 "1,200%를 피하려 13회차로 미룬 지급이 아닌지" 확인하는 사례로 쓴다. 감독당국 경고 보도(2026-09)는 원문·SRC 확보 전까지 조사 질문일 뿐 판정 규칙이 아니다.


## 제23조 경력설계사 정착지원금

- 항목코드: `SETTLEMENT_SUPPORT`
- 전체 GOLDEN 목표의 정상 가상 약정액: **2,400,000원**
- 전체 GOLDEN 목표의 한도초과 스트레스 테스트 약정액: **4,000,000원**
- 지급대상: 최근 타사 모집경력이 있는 신규 위촉 설계사
- 1,200% 판정: 포함
- 계약귀속: 해당 설계사가 **신계약을 모집한 월**의 신계약에 귀속한다. 지급월이 아니다 — 8월 지급분은 7월 모집 신계약에 귀속한다(`REG-20`, `SRC-025` FAQ 2차 Q7-1). 그 달 신계약 사이의 배분은 월납환산 초회보험료 비례로 한다 — **배분 방법은 업무 규칙 아님 — 가상 GA 정책으로 정함**(공식 기준 없음, SRC-037, #525). 정착지원금 추가 FAQ가 배분 방법을 정하면 다시 연다.
- 지급 시기를 13차월 이후로 이연해도 귀속월은 달라지지 않는다 `[해석]`. 이연분의 1,200% 산입은 보도된 TF 안내(SRC-029, 2차 자료)에만 근거하므로 제3차 FAQ 원문 확인 전까지 판정이 갈리는 건은 `REVIEW_REQUIRED`로 둔다(조문표 REG-20).
- 위촉 당월 등 귀속 대상 모집월에 신계약이 없으면 위촉 후 최초 신계약 모집월로 이월
- 귀속 후 각 계약의 1,200% 게이지를 다시 검사
- 초과분을 관리자가 임의 승인할 수 없음
- 해결방법: 감액, 취소, 실제 미지급 이연, 계약귀속 오류 정정
- 12개월 내 신계약 8건 미달 시 100% 환수한다는 약정은 **가상 회사정책**이며 2차에서만 구현

정상 시드의 2,400,000원은 기본 GA 지급률 740%와 결합해도 예시 5개 계약이 모두 1,200% 이내가 되도록 정한 값이다.
4,000,000원은 정상 정책이 아니라 **모든 계약이 한도초과하는 의도적 실패 시나리오**로만 사용한다.

현재 `db/demo` 축소 fixture의 정착지원금은 **210,000원**이며 2개 신계약에 105,000원씩 귀속한다. 이는 전체 GOLDEN 목표값 2,400,000원/4,000,000원을 구현한 것이 아니다. 발표·테스트 기대값은 실행한 프로파일의 값을 표시해야 하며 두 데이터 세트를 혼용하지 않는다.


## 제24조 신인활동지원비

- 항목코드: `NEWCOMER_SUPPORT`
- 가상 지원한도: 2,000,000원
- 대상: 등록예정일 직전 3년을 기준으로 다음 순서로 판정한다 — ① 모집종사자 고유번호 미보유 → 신인 ② 이클린 경력조회 불가(경력 제공 미동의) → 신인 아님(동의 후 재판정) ③ 등록이력 없음 → 신인 ④ 등록이력이 있어도 모집이력 없음 → 신인, 모집이력 있음 → 신인 아님. 생명·손해보험 교차 이력을 포함한다. 최근 등록일부터 1년 이내 지원분만 제외 대상이 된다. (`REG-21`, `SRC-022` 제4-32조⑦3호, `SRC-025` Q5~Q7)
- 목적: 모집활동을 위한 별도 장비·교육·활동지원
- 실적·계약건수·근속조건과 직접 연계하지 않는다.
- 증빙을 모두 충족하면 해당 룰셋에서 `EXCLUDED`로 분류할 수 있다.
- 경력조회·등록일·지원기간·지급근거가 누락되면 `REVIEW_REQUIRED`
- “1년 내 8건 미달 시 환수”처럼 실적조건을 붙인 지원금은 정착지원금으로 분류하고 1,200%에 포함한다.

신인활동지원비는 신인이 아직 계약을 모집하지 않았더라도 발생할 수 있으므로 다음 귀속유형을 허용한다.

```text
attribution_scope = AGENT
contract_id       = NULL
agent_id          = 신인 설계사
attribution_method = NEWCOMER_NON_CONTRACT
```

계약 미귀속 확정은 `EXCLUDED` 판정과 적격 증빙이 모두 있을 때만 허용한다.
`INCLUDED`로 판정되거나 실적과 연계된 지원금은 반드시 `CONTRACT` 범위로 재분류하여 계약에 귀속해야 한다.

## 제25조 공통비

공통비는 모집활동과 관련하여 조직 단위로 발생했지만 개별 계약에 바로 특정하기 어려운 비용이다.

공통비를 세 범주로 혼합하지 않는다.

- REG-06A: 초년도 1,200%룰에 산입할 수 있는 모집 관련 공통비
- REG-06B: 유지관리수수료 지급기준의 간접지원경비
- REG-06C: 법정 단일 산식이 없는 회사별 승인 안분정책

보도자료·업계 예시의 `약 19%`는 법정 고정률이나 공통 상한이 아니므로 정책 기본값으로 하드코딩하지 않는다. 비용풀·배부대상·배부기준·유효기간·승인근거·반올림·잔액처리를 회사별 정책버전으로 저장한다.

### 가상 회사 정책

- 비용풀 발생단위: 지사
- 발생주기: 월
- 대상: 해당 지사의 당월 신계약
- 배부기준: 월납환산 초회보험료 비례
- 반올림: 원 단위 `HALF_UP`
- 잔액처리: 소수점 잔액이 가장 큰 계약부터 1원씩 배분
- 1,200% 판정: 모집종사자에게 귀속되는 금액은 포함
- 근거 없는 임의 배부: 금지

### 예시

공통비 700,000원, 보험료가 100,000 / 100,000 / 200,000 / 300,000원이면:

| 계약 | 배부액 |
|---|---:|
| A | 100,000원 |
| B | 100,000원 |
| C | 200,000원 |
| D | 300,000원 |
| 합계 | 700,000원 |

1차에서는 범용 안분계산기를 개발하지 않는다. 외부에서 계산된 계약별 귀속결과를 입력하고 다음만 검증한다.

- 배부정책 버전 존재
- 배부 전 총액 = 배부 후 총액
- 대상월·조직·계약 일치
- 계약별 근거참조 존재
- 확정 후 귀속행 변경 금지

# 제8장 초년도 1,200% 정책

## 제26조 게이지 분리

```text
INSURER_TO_GA_1200
GA_TO_FC_1200
```

두 게이지는 합치지 않는다. 같은 계약이라도 각각 별도 결과를 저장한다.

설계사·지점 단위의 1,200% '공용 잔액'이나 합산 사용률 지표는 만들지 않는다. 1,200%는 계약 1건 단위 판정이다(REG-08, FUN-031·080).


## 제27조 적용기간

- 원수사→GA: 보험회사 지급기준의 초년도 1,200%룰은 2021-01-01 이후 체결 계약부터. 시스템은 해당 정책 유효기간과 상품범위를 함께 판정
- GA→설계사: 2026-07-01 이후 체결 계약부터
- 초년도 기간은 **계약체결일 이상, 계약체결일의 1주년일 미만**으로 계산한다.

```text
contract_date <= 귀속일 < contract_date + 1 year
```

예를 들어 계약일이 2026-07-10이면 2027-07-09는 초년도이고 2027-07-10은 초년도 밖이다.

- 예상 스케줄의 귀속일: `schedule_line.due_date`
- 실제 지급·귀속의 귀속일: `transaction_attribution.attribution_date`
- `attribution_month`는 월별 집계키이며 초년도 경계 판정에 사용하지 않는다.
- `settlement_month`는 실적(발생)월이며 월 명세 묶음 기준이다. 지급월이 아니다 — 회차 수수료는 그 회차가 발생하는 달(`schedule_line.due_month` = 계약일 + 회차−1개월, 예: 7월 계약의 2회차는 8월)로 등록하고, 정착지원금은 신계약을 모집한 달로 등록해 그 달의 신계약에 귀속한다. 정착지원금의 지급예정일은 모집월 1일 이후여야 한다(`REG-20`, #476). 초년도 귀속판정일로는 사용하지 않는다.

## 제28조 기본 한도

월납 보장성 일반계약:

```text
기본 한도 = monthly_equivalent_first_premium × 12
```

표준해약공제액 80% 이상 공제 대상 상품:

```text
판정: 초년도 산입금액 + 12차월 예상 해약환급금 ≤ 월납환산 초회보험료 × 12
```

해약환급금은 한도에 더하는 금액이 아니라 **산입금액 쪽에 합산**하는 금액이다(SRC-022 제4-32조제5항 "예상 해약환급금을 합산한다", SRC-025 FAQ 2차 Q1-1 "초년도 수수료등 + 1년 경과 시점 예상 해약환급금 ≤ 월납보험료의 1,200%"). 구현(`CapCalculatorImpl`, #468)은 이 판정식을 한도 쪽으로 이항해 `limit_amount = 월납×12 − 12차월 예상 해약환급금 + 준법경영비 공제액`(0 미만은 0)으로 저장하고 `included_amount`는 지급 합계 그대로 둔다. 판정 결과는 위 식과 같다.

정확한 상품·납입기간·채널·기준일의 환급률표가 없으면 자동 계산하지 않고 `REVIEW_REQUIRED`로 판정한다.

## 제29조 산입 분류

| 항목 | 기본 판정 |
|---|---|
| 기본 모집수수료 | 포함 |
| 관리자수수료 | 포함 |
| 초년도 시책 | 포함 |
| 경력설계사 정착지원금 | 포함 |
| 계약에 귀속된 공통비 | 포함 |
| 신인활동지원비 | 요건·증빙 충족 시 제외, 아니면 검토 |
| 13차월 이후 실제 지급 시책 | 초년도 밖 |
| 오입력 정정 차감 | 확정된 정정만 누계에 반영 |
| 환수(지급 후 회수) | 1,200% 누계에서 빼지 않는다. 일시적으로라도 한도를 넘은 시점에 위반이며(SRC-025 Q1-1), 지급 후 회수·재지급은 편법 예시에 해당한다(SRC-025 Q4 예시 4) `[해석]`. 환수는 차익거래(제33조)에서만 뺀다 |
| 준법경영비 3% | `INSURER_TO_GA`에서만 증빙 충족분을 공제. 2027-01-01부터(FGC는 대면만이라 TM·방송 2028-01-01 특례 없음, SRC-036). 시행 전과 `GA_TO_FC`는 0 |

준법경영비는 한도에서 빼는 금액이 아니라 **수수료등(산입금액)에서 제외**하는 금액이다(SRC-022 제4-32조제14항 "제외할 수 있다", 실질 한도 1,203%). 또한 자동으로 초회보험료의 3%를 빼는 정액공제가 아니다. 실제 지급액 중 비교설명·업무기준 준수 및 내부통제 인력 운영 목적에 해당하고 증빙된 금액을, 월납 기준 초회보험료의 3% 이내에서만 제외한다. `cap_rule_set.compliance_deduction_pct=3`은 최대 허용률이며 실제 공제액은 `cap_check.compliance_deduction_amount`와 상세 근거로 보존한다.

현재 `db/demo/V6_1__cap_ins_compliance_deduction_correction.sql`은 2027-01-01 시행일 보정을 제공한다. FGC는 대면 모집만 다루므로(SRC-036) 채널별 룰셋을 나누지 않는다.

## 제30조 판정상태

| 상태 | 기준 |
|---|---|
| `NORMAL` | 1,200% 예산 사용률 90% 미만 |
| `WARNING` | 1,200% 예산 사용률 90% 이상이고 위반이 아님 |
| `VIOLATION` | 사용률(산입금액 ÷ 한도) 100% 초과 — 제28조 판정식 위반과 같다 |
| `REVIEW_REQUIRED` | 정책·귀속·증빙·환급률표가 부족하거나, 12차월 환급률이 100%를 넘는 비정상 환급률표 |
| `NOT_APPLICABLE` | 적용대상 아님 — 보장성보험이 아니거나(제4-32조⑤), 계약일이 그 지급단계 시행일(보험회사→GA 2021-01-01, GA→설계사 2026-07-01) 이전이다. 룰셋·한도·산입액을 저장하지 않고 사유를 `calculation_snapshot`에 남긴다. 예외를 만들지 않는다(V48·V51, #477·#482) |

화면의 사용률은 `산입금액 ÷ 한도`이고, 한도는 제28조 판정식을 이항한 **실질 허용 한도**(`월납×12 − 12차월 예상 해약환급금 + 준법경영비 공제액`)다. 주의(`WARNING`)는 이 사용률이 아니라 **1,200% 예산 사용률** `(산입금액 + 12차월 예상 해약환급금 − 준법경영비 공제액) ÷ (월납×12)`로 판정한다(#490). 구현은 같은 뜻의 `잔여 ≤ (100 − 90)% × 월납×12`로 비교해 나눗셈 반올림이 끼지 않는다. 해약환급금 합산 대상 계약은 화면 사용률 90%보다 앞에서 주의가 켜지므로 게이지의 주의 표시선도 그 위치(`100 − 10 × 월납×12 ÷ 한도` %)에 그린다. 예: 월납 100,000원·해약환급금 288,000원이면 한도 912,000원, 주의는 산입 792,000원(사용률 86.84%)부터다. 계약 등록·월 검증(`CapCalculatorImpl`)과 지급확정(`CapValidatorImpl`·스케줄/실지급 결합 판정)이 같은 규칙(`CapResultStatus.judge`)을 쓴다. 90%는 규정이 아닌 자체 운영 기준(`cap_rule_set.warning_usage_pct`)이라 위반 판정과 초과액에는 영향이 없다(REG-08·10, SRC-022 제4-32조⑤⑭, SRC-025 Q1-1, #468·#490).

## 제31조 지급확정 게이트

지급 건은 반드시 다음 순서로 처리한다.

```text
DRAFT 생성
→ 계약별 귀속행 등록
→ 귀속합계 = 지급액 검사
→ REVIEW_REQUIRED 귀속 존재 여부 검사
→ 1,200% 사전검증
→ 통과 시 CONFIRMED
```

다음은 허용하지 않는다.

- 귀속 없이 `CONFIRMED`
- 한도초과 관리자 강제승인
- 근거 없는 `EXCLUDED`
- 확정 지급 건 금액 직접수정
- 확정 귀속행 수정·추가·삭제
- 초년도 지급을 13회차로 허위 이연

현재 DB 트리거가 직접 강제하는 범위는 `DRAFT` 생성, 귀속합계=지급액, `REVIEW_REQUIRED` 귀속의 확정 차단, 확정 후 불변성이다. **DB 트리거는 `commission_transaction` 확정 시 `cap_check`를 조회해 1,200% 통과 여부를 자동 확인하지 않는다.** 따라서 서비스는 같은 후보 지급 건을 포함한 `PRE_CONFIRM` 검증을 먼저 생성하고 `VIOLATION`·`REVIEW_REQUIRED`이면 `CONFIRMED` UPDATE를 호출하지 않아야 한다. 이 서비스 게이트가 구현되지 않은 경로에서는 지급확정 기능을 제공하지 않는다.

**게이트 적용 범위.** 이 게이트는 **GA가 돈을 주는 결정**에 건다 — GA→설계사 지급 건과, 원수사→GA 수기 지급 건(`GA_MANUAL_PAYMENT`). 다음은 예외다.

- `CLAWBACK` 항목의 `DEDUCTION` 지급 건은 1,200% 사전검증을 하지 않는다. 환수는 1,200% 누계에서 빼지 않기 때문이다(제29조, #478, 구현됨). 다른 차감 항목(`RECOVERY` 등)의 분류 검사는 유지한다.
- **보험사 원천 명세(`INSURER_STATEMENT`) 적재는 지급 승인이 아니다.** 2차 AI 문서 입력으로 확정한 정산데이터 행은 스키마·참조·귀속 합계·업무키만 검사하고 `CONFIRMED`로 적재한다. 1,200% 초과·해지 후 지급·중복은 보험사가 이미 보낸 사실이므로 거르지 않고, 월 통합검증의 기표·대사·예외가 판정한다(제55조, FUN-068 — r19 초안). 원천 적재 경로는 GA 지급 건 확정 API와 분리해 이 게이트를 우회하는 수단이 되지 않게 한다. 기존 수기 지급 확정 경로의 `GA_MANUAL_PAYMENT` 제한은 그대로 둔다.

# 제9장 차익거래 방지

## 제32조 적용대상

- 보장성보험. 일반손해보험·자동차보험·저축성은 `NOT_APPLICABLE`(제34조)
- 해지·실효를 포함한다. 실효계약은 납입최고·해지통보 시기와 관계없이 **실효사유 발생 시(상태 사건 효력일)** 를 해지시점으로 본다(SRC-025 Q12)
- 피보험자 사망·보험금 지급사유로 인한 소멸, 납입면제 특약 기능에 따른 전부·일부 해지는 제외한다(SRC-025 Q12 `[FAQ-2차]`). **현재 미구현** — 상태 사유 코드에 이 구분이 없다. 2차에서 사유 코드를 추가하기 전까지 이런 계약은 시연 데이터에 넣지 않는다
- 증권번호 기준으로 주계약과 특약을 합산한다(제11조)
- 2026-03-01 이후 체결 신계약 — SRC-022 부칙 제1조①, SRC-025 Q11. 이 날짜는 `ARBITRAGE` 정책의 `ARBITRAGE_EFFECTIVE_CONTRACT_DATE` 파라미터로 관리한다(#475). TM·방송 승인 대리점의 2027-01-01 특례는 FGC 범위 밖(SRC-036)
- 계약 전 기간 점검
- 표준해약공제액 80% 이상 공제 상품이 계약 체결일부터 3년(경과기간, 납입회차 아님) 이내 해지·실효되면 해약환급금을 합산한다(REG-12 `[해석]`). 기간은 `ARBITRAGE_REFUND_ADDITION_MONTHS=36`(경과 개월), 3주년 당일은 제외(`ARBITRAGE_REFUND_ADDITION_BOUNDARY_INCLUSIVE=false`, demo V56)다. 경계일 처리는 **프로젝트 해석**이며, 유일한 자료인 SRC-029 보도("37회차 응당일 당일 24시까지 3년 이내 포함")와 반대다 — 2차 자료라 채택하지 않았고 원문이 나오면 새 정책버전으로 바꾼다(#480). 그 전까지 경계일 해지 건은 `REVIEW_REQUIRED` 대상으로 본다(조문표 10.2)


## 제33조 계산식과 지급단계

FGC의 법규준수용 차익거래 검증은 `GA_TO_FC`를 기본 지급단계로 한다.
보험회사 지급자료를 이용한 `INSURER_TO_GA` 분석이 필요하면 별도 진단결과로 저장하되 두 단계를 합산하지 않는다.

```text
판정 초과액 (CANDIDATE 판정 기준)
= max(0, 순누적 판매수수료 [+ 조건부 해약환급금] - 누적 납입보험료)

사전 모니터링 지표 (판정에 쓰지 않음)
= max(0, 순누적 판매수수료 + 지급예정 판매수수료 [+ 조건부 해약환급금] - 누적 납입보험료)
```

조문은 "해지시점까지 **지급한** 수수료등"이다(SRC-022 제4-32조제6항, SRC-025 Q11 "수수료등 + 해약환급금 - 환수금 > 납입보험료"). 그래서 `CANDIDATE`는 판정 초과액(지급분)으로만 정한다. 지급예정분을 더한 초과는 `candidate_type='PROJECTED_EXCESS'`와 사전 모니터링 지표로만 남기고 판정을 바꾸지 않는다(FUN-063, `ArbitrageService` 구현 일치).

`arbitrage_check.paid_commission_amount`는 다음 의미로 고정한다.

```text
순누적 판매수수료
= 해당 payment_stage의 확정 PAYMENT 누계
  - 해당 payment_stage의 확정 DEDUCTION 누계
```

총 지급액과 총 차감액은 `calculation_snapshot`에 별도로 보존한다.
같은 계약·기준일이라도 지급단계별 결과는 독립 행으로 저장한다.

## 제34조 실행시점

- 계약 단위 수동검증
- 실효·해지 사건 입력 직후의 재검증
- 지급·시책·정정 금액 변경 후 재검증
- 월 통합검증

1차는 후보만 생성하며 법적 위반을 자동 확정하지 않는다.

| 결과 | 의미 |
|---|---|
| `CLEAR` | 초과액 없음 |
| `CANDIDATE` | 초과 후보 |
| `REVIEW_REQUIRED` | 필수자료 부족·코드 불일치 |
| `NOT_APPLICABLE` | 적용대상 아님 — 보장성보험이 아니거나, 계약일이 차익거래 적용일(`ARBITRAGE_EFFECTIVE_CONTRACT_DATE`) 이전이다. 예외를 만들지 않는다(V48, #477). 현재 구현은 적용일 이전 계약을 `CLEAR`(candidate_type `NOT_APPLICABLE`)로 저장해 1,200%(#482)와 다르다 — 수정 대상 |

# 제10장 예상 스케줄과 대사

## 제35조 스케줄

- 계약·지급단계·정책버전별 스케줄을 생성한다.
- 예상금액의 유일한 원천은 `schedule_line.expected_amount`이다.
- 운영 스케줄은 지급단계별 활성 1개만 둔다.
- 현행·4년·7년 비교화면은 `COMPARISON` 목적과 서로 다른 `scenario_code`로 생성한다.
- 확정된 스케줄을 덮어쓰지 않고 새 버전을 만든다.
- `CONFIRMED`·`MATCHED`·`ADJUSTED`·`CANCELLED` 상태의 스케줄 헤더는 `PLANNED` 등으로 **되돌릴 수 없다.** 되돌린 뒤 상세행을 고치는 우회를 DB 트리거(`trg_schedule_header_status`)로 차단한다.

## 제36조 대사 기준

### 원수사→GA

```text
예상 원수사 수입 스케줄
↔ 원수사 실제 지급명세
```

### GA→설계사

```text
예상 설계사 지급 스케줄
↔ GA 확정 지급 건
```

### 기본 매칭키

- 지급단계
- 보험회사
- 계약
- 설계사 — 지급단계에 따라 뜻이 다르다

| 지급단계 | 예상측 | 실제측 | 무엇을 검증하나 |
|---|---|---|---|
| `GA_TO_FC` | 예상 스케줄의 수취인(`schedule_line.beneficiary_agent_id`) | 지급 건의 수취인 | 줄 사람에게 갔는가 |
| `INSURER_TO_GA` | 계약 모집설계사(`insurance_contract.agent_id`) | 원수사 설계사코드를 `agent_insurer_code`로 매핑한 결과. 코드가 없으면 귀속행의 설계사 | 원수사 자료의 설계사가 우리 계약 정보와 맞는가 |

원수사→GA 는 받는 주체가 GA 법인이므로 **개인 수취인이 없다**(`ck_transaction_recipient`가 `GA_TO_FC`에만 수취인을 요구한다). 이 단계의 설계사 축은 수취인이 아니라 **모집설계사**이며, 검증 목적은 원수사가 보낸 자료의 설계사코드가 우리 계약과 일치하는지 확인하는 데이터 무결성 점검이다.

`transaction_attribution.agent_id`도 같은 규칙을 따른다 — 수취인이 있으면 수취인, 없으면 귀속 계약의 모집설계사를 넣는다. 이 값을 비우면 원수사→GA 대사가 설계사를 식별하지 못해 금액이 정확히 일치해도 `REVIEW_REQUIRED`로 빠진다.
- 수수료항목
- 회차
- `due_month = settlement_month`

### 수취인 짝짓기 규칙

한 계약·수수료항목·정산월 안에 **수취인이 여러 명인 지급이 정상적으로 존재한다.** 관리자수수료(`MANAGEMENT_COMMISSION`)가 대표 사례로, 제20조 패턴에 따라 팀장·지사장·본부장 세 명이 같은 항목·같은 1회차로 각각 수령한다.

따라서 대사는 계약·항목·월로 묶은 뒤 **그 안에서 수취인 단위로 짝을 지어** 판정한다. 합계만 비교하지 않는다.

| 순서 | 규칙 | 결과 |
|---|---|---|
| 1 | 예상·실제 양쪽에 **같은 수취인**이 있으면 짝을 만든다 | 그 짝의 금액·회차를 비교해 `MATCHED` 또는 `AMOUNT_DIFFERENCE`·`INSTALLMENT_MISMATCH` |
| 2 | 짝짓고 남은 예상 수취인과 실제 수취인이 **각각 정확히 한 명씩**이면 서로 짝지어 본다 | `AGENT_MISMATCH` |
| 3 | 그 외 남은 예상 수취인 | 각각 `ACTUAL_MISSING` |
| 4 | 그 외 남은 실제 수취인 | 각각 `EXPECTED_MISSING` |
| 5 | 2번에서 남은 쪽이 양쪽 모두 두 명 이상이면 어느 쪽과 짝인지 단정할 수 없다 | `REVIEW_REQUIRED` |

2번이 있어야 "팀장에게 갈 돈이 엉뚱한 사람에게 갔다"를 `AGENT_MISMATCH`로 잡아낼 수 있다. 수취인을 그룹 키에 넣어 통째로 갈라버리면 이 검출이 불가능해지므로, **묶는 것은 계약·항목·월로 하고 짝짓기는 그 안에서** 한다.

짝 하나가 대사 결과 한 행이다. 관리자수수료 한 계약·한 달은 결과가 최대 3행이 되며, 업무키의 수취인 구간(`E{예상수취인}-A{실제수취인}`)이 서로 달라 중복되지 않는다.

### 원천유형별 대사 대상 요건

원수사→GA 실제 원천은 두 갈래이며 요구조건이 다르다.

| 원천유형 | 명세 묶음 | 보험회사 | 대사·기표 대상 행 | 실제 분개 |
|---|---|---|---|---|
| `INSURER_STATEMENT` (정규화 적재분 · 2차 AI 문서 입력분) | `statement_batch` 필수 · `statement_type='INSURER_COMMISSION'` · 상태 `AVAILABLE`/`VALIDATED`/`RECONCILED` · `data_origin` `NORMALIZED_DB`/`SEED`(2차 제안 `AI_INTAKE`) | `commission_transaction.insurer_id` | `payment_stage='INSURER_TO_GA'` · `cashflow_type='PAYMENT'` · `status='CONFIRMED'` · 귀속 `attribution_scope='CONTRACT'` | `ACTUAL_INSURER_STATEMENT` POSTED |
| `GA_MANUAL_PAYMENT` (TRAN-W02 수기 등록분) | 없음 (`statement_batch_id IS NULL`) | 귀속 계약의 보험회사에서 유도해 `insurer_id`에 저장 | 위와 같음 | `ACTUAL_INSURER_STATEMENT` POSTED |

`DEDUCTION` 행, `INSURER_ADJUSTMENT`·`INSURER_CLAWBACK` 명세는 현재 기표·대사 대상이 아니다(`InsurerGaReconciliationRepository`, `JournalPostingSourceQueryRepository`). 적재는 되지만 검증되지 않으므로 화면에 '후속 검증 대기'로 따로 보여 준다(제55조 4). 차감·환수 명세의 대사 규칙은 근거 없음 — 확인 필요.

수기 등록분을 대사 대상으로 인정하는 것은 제7조 정규화 전제의 예외이며, 근거분류는 제3조의 `PROJECT_ASSUMPTION`이다. 1차는 파일 업로드·스테이징을 만들지 않으므로 COR-010과 충돌하지 않는다. 정규화 적재분은 명세 묶음 요건을 완화하지 않는다 — 적재 경로의 무결성은 그대로 강제한다.

### 1차 허용오차

- 금액: 0원
- **월: 정확일치** — 기본 매칭키의 `due_month = settlement_month`를 말한다. 지급예정일(`due_date`)은 매칭키가 아니므로 일 단위 일치를 요구하지 않는다
- 회차: 정확일치
- 1원 차이도 `AMOUNT_DIFFERENCE`

> **지급예정일을 매칭키에서 뺀 이유** — 예상 지급예정일은 계약일 기준(계약일 + 회차−1개월)이고, 실제 지급예정일은 정산 사이클 기준(정산월 마감 후)이다. 2026-07 정산분이 예상 07-10 / 실제 08-25처럼 **월조차 다른 것이 정상**이다. 일 단위 일치를 매칭 조건으로 걸면 어떤 계약도 짝을 찾지 못해 `MATCHED`가 영구히 0건이 된다. 예정일은 짝을 지은 뒤 대사 결과에 함께 기록해 담당자가 확인한다.

### 대사 대상의 범위

1. 대사 실행은 정산월·지급단계·보험회사 단위로 만든다. 대사할 보험회사는 그 달 검증 대상(`SELECTED`) 계약의 보험회사와, 그 정산월·지급단계에 계약 귀속 확정 지급(`CONFIRMED`·`PAYMENT`·`CONTRACT`)이 있는 보험회사를 합친 집합이다(#516). 선정 계약이 없는 보험회사의 지급도 대사된다.
2. 예상 원천은 그 보험회사의 운영 스케줄 전체이며 검증 대상 계약으로 거르지 않는다. 다만 상태 사건으로 확인된 **지급예정일 시점의 실효·해지·만기 회차와 청약철회 계약 회차는 예상 원천에서 뺀다**(인터페이스정의서 §9-5, #518). 사건이 없으면 남긴다(제13조).
3. 상태 사건으로 확인된 계약은 현재 상태와 무관하게 지급예정일 시점 상태로 비유효 지급을 판정한다. 실효 뒤 부활한 계약의 실효 기간 회차 지급은 `INVALID_CONTRACT_PAYMENT`다.
4. 그 실행에서 검토필요로 보류된 대상(환급률표 누락 등)의 `EXPECTED_MISSING`은 주 사유를 `REVIEW_REQUIRED`(심각도 WARNING)로 낮추고 `EXPECTED_MISSING`은 보조 사유로 남긴다(#518).

### 불일치 유형

- `AMOUNT_DIFFERENCE`
- `EXPECTED_MISSING`
- `ACTUAL_MISSING`
- `DUPLICATE`
- `AGENT_MISMATCH`
- `INSTALLMENT_MISMATCH`
- `INVALID_CONTRACT_PAYMENT`
- `POLICY_VERSION_ERROR`
- `JOURNAL_IMBALANCE`
- `REVIEW_REQUIRED`

# 제11장 복식부기 검증원장

## 제37조 성격

FGC 원장은 법정 회계장부가 아니라 예상·실제 수수료의 금액정합성을 확인하기 위한 내부 보조원장이다.

## 제38조 1차 분개유형

| 유형 | 의미 |
|---|---|
| `EXPECTED_INSURER_INCOME` | 원수사→GA 예상 수입 |
| `ACTUAL_INSURER_STATEMENT` | 원수사 실제 지급명세 |
| `EXPECTED_FC_PAYOUT` | GA→설계사 예상 지급 |
| `CONFIRMED_FC_PAYOUT` | GA 확정 지급 건 |
| `REVERSAL` | 확정분개의 역분개 |

2차에서 `ADJUSTMENT`, `CLAWBACK`, `RECOVERY`를 활성화한다.

## 제39조 최소 계정과목

| 계정코드 | 설명 | 정상잔액 |
|---|---|---|
| `EXPECTED_RECEIVABLE` | 예상 수수료미수금 | 차변 |
| `EXPECTED_INCOME` | 예상 수수료수익 대응 | 대변 |
| `ACTUAL_RECEIVABLE` | 실제 수수료미수금 | 차변 |
| `ACTUAL_INCOME` | 실제 수수료수익 대응 | 대변 |
| `EXPECTED_PAYOUT_EXPENSE` | 예상 설계사 지급비용 | 차변 |
| `EXPECTED_PAYOUT_PAYABLE` | 예상 지급채무 | 대변 |
| `CONFIRMED_PAYOUT_EXPENSE` | 확정 설계사 지급비용 | 차변 |
| `CONFIRMED_PAYOUT_PAYABLE` | 확정 지급채무 | 대변 |

분개 확정 전 `차변합계 = 대변합계`여야 한다.

### 예상분개와 실제분개의 생명주기

예상분개와 실제분개는 서로 대체하는 회계장부가 아니라 서로 다른 검증 기준이다.

- 대사가 `MATCHED`되어도 예상분개와 실제분개를 모두 `POSTED` 상태로 보존한다.
- 보고서에서 두 계열을 합산하지 않고 `EXPECTED`와 `ACTUAL`로 분리한다.
- 예상 스케줄이 실제 명세 도착 전에 변경·취소되면 예상분개를 역분개하고 새 예상분개를 기표한다.
- 실제 명세가 정정되면 실제분개를 역분개하고 새 실제분개를 기표한다.
- 대사결과는 예상분개와 실제분개의 연결관계를 나타낼 뿐 어느 한쪽을 삭제하지 않는다.

## 제40조 정정

확정분개를 직접 수정하지 않는다.

```text
원분개 POSTED
→ REVERSAL 분개
→ 원분개 REVERSED
→ revision_no가 증가한 신규 분개 POSTED
```

### 원장 정정 예외 연계

단순히 원거래를 취소하는 경우는 원장 화면에서 역분개할 수 있다. 잘못된 분개를 올바른 분개로 교체하는 경우는 다음 절차를 따른다.

```text
LEDG-W01에서 [역분개 + 재기표]
→ 원분개를 참조하는 JOURNAL_CORRECTION_REQUIRED 예외 생성 또는 미종결 예외 재사용
→ EXCP-W01에서 담당자가 원분개를 확인하고 올바른 신규 분개 입력
→ 역분개·재기표·처리이력·예외 RESOLVED를 하나의 트랜잭션으로 반영
```

- 같은 원분개에 대한 미종결 정정 예외는 하나만 유지한다.
- 원분개·역분개·재기표는 `journal_correction_group`으로 연결하며 원분개를 UPDATE 또는 DELETE하지 않는다.
- 역분개와 재기표 중 하나라도 실패하면 처리이력과 예외 상태 변경도 모두 롤백한다.
- `CORRECT`라는 처리이력만 기록해서 원장 정정 예외를 종결할 수 없다.
- 정정 성공 후 화면은 원분개·역분개·재기표와 정정그룹을 함께 조회할 수 있어야 한다.
- 원분개가 지급 건에서 나온 실제 분개(`CONFIRMED_FC_PAYOUT`·`ACTUAL_INSURER_STATEMENT`)이고 그 지급 건이 계약 1건에 귀속된 확정 `PAYMENT`이면, 역분개·재기표와 같은 트랜잭션에서 원 지급 건을 취소하고 대체 지급 건을 만든다. 원·대체 지급 건은 `payment_journal_correction`(수정·삭제 불가)으로 연결하고, 영향받은 대사 실행은 지우지 않고 대체됨(`superseded_yn`)으로 표시한 뒤 새 대사 실행을 만든다(#548, V54). 확정 지급 건의 금액을 직접 고치지 않는다는 제31조 원칙은 그대로다.
- `FINALIZED` 검증 실행에 연결된 분개는 역분개하지 않는다(`FGC-VRUN-003`). 2차 보험사 정정 명세도 이 경우 전환 전에 거절한다(제55조 5).

# 제12장 예외와 월 통합검증

## 제41조 예외 상태

```text
NEW ──START_REVIEW──▶ IN_REVIEW ──RESOLVE──▶ RESOLVED
                         │
                         └──REJECT / FALSE_POSITIVE──▶ REJECTED ──REOPEN──▶ IN_REVIEW
(화살표 위 글자는 조치, 상자는 상태. ASSIGN·COMMENT는 상태를 바꾸지 않는다)
```

상태는 `NEW`·`IN_REVIEW`·`RESOLVED`·`REJECTED` 네 개다. `REOPEN`은 상태가 아니라 조치다(`ExceptionStatus`, `ExceptionActionType`).

상태변경에는 처리사유가 필수다.

`REOPEN`은 오탐·반려 판단의 오조작 또는 추가 증빙이 확인된 경우에 한해 `REJECTED`를
`IN_REVIEW`로 되돌리는 재검토 조치다. 최초 검토인 `START_REVIEW`와 감사이력에서 구분하며,
`RESOLVED` 원장 정정 예외는 직접 재오픈하지 않는다. 이미 역분개·재기표가 끝난 원장을 다시
고쳐야 하면 직전 재기표 분개를 원분개로 하는 새 정정 예외를 생성한다.

## 제42조 해결조치

- `ASSIGN`: 담당 배정 / `START_REVIEW`: 최초 검토 시작 / `REJECT`: 반려(사유 필수) / `COMMENT`: 메모만 남김(상태 불변)
- `CORRECT`: 원천자료 정정. 원장 정정 예외에서는 실제 역분개·재기표 성공 결과를 연결한 경우에만 사용할 수 있다.
- `REDUCE`: 지급액 감액
- `CANCEL`: 지급 취소
- `DEFER`: 실제 미지급 후 미래 회차로 이연
- `RECONCILE_AGAIN`: 재대사
- `FALSE_POSITIVE`: 오탐
- `REOPEN`: 오탐·반려 재검토 시작
- `RESOLVE`: 해결확정

`DEFER`는 실제 지급을 미루는 경우에만 사용하며 날짜만 바꾸는 우회처리는 금지한다.

일반 예외의 상태·사유 기록과 실제 도메인 정정은 구분한다. 실제 정정 명령이 필요한 예외는 해당 명령 성공과 같은 트랜잭션에서만 `RESOLVED`로 전이한다.

## 제43조 월 통합검증 순서

```text
1. 대상월 실행 생성
2. 계약·상품버전·환급률표 선별
3. 현행 운영 스케줄 생성·재검증
4. 지급단계별 1,200% 검증
5. 차익거래 검증
6. 검증원장 기표·균형검사
7. 양방향 대사
8. 예외 생성
9. 담당자 검토
10. FINALIZED
```

`FINALIZED`는 FGC 검증결과 잠금이며 실제 송금마감·법정 회계마감이 아니다.

### 2단계 대상 선별 기준 (#474)

- 계약일이 기준일 이하이고, 계약의 판매버전 판매기간이 계약일을 포함하는 계약 중
- 현재 상태가 정상(`ACTIVE`)·미납(`UNPAID`)·부활(`REVIVED`)인 계약 — 미납은 납입최고기간이 끝나기 전까지 유지 계약이다(SRC-023 별표15 표준약관 제26조)
- 또는 **효력일이 검증월 1일 이후**인 해지·실효 사건이 있는 계약 — 차익거래 규제의 핵심 대상이라 빼지 않는다(SRC-022 제4-32조⑥, SRC-025 Q12). 효력일 상한은 두지 않는다(정정 재실행의 대상이 실행 시점에 따라 바뀌지 않게, FUN-044)
- 청약철회(`CANCELLED`)·만기(`MATURED`)는 대상이 아니다
- 선별된 계약 중 환급률표가 없거나 코드가 다르면 `REVIEW_REQUIRED`로 두고 하위 계산에서 뺀다

### 실행상태와 `current_step`

| 상태 | 허용 `current_step` | 의미 |
|---|---:|---|
| `CREATED` | 0 | 시작 전 |
| `RUNNING` | 0~8 | 자동 처리 중 |
| `FAILED` | 0~8 | 해당 단계에서 실패. DB는 `FAILED→RUNNING` 재개를 허용한다. 1차 앱은 재기동하지 않고 새 실행을 만든다. 실패 지점 재시작은 2차 FUN-045(Spring Batch 메타데이터·체크포인트) |
| `COMPLETED` | 8 | 1~8단계 완료, 9단계 담당자 검토 대기 |
| `FINALIZED` | 10 | 담당자 검토·확정 완료 |

9단계는 별도 숫자 9로 저장하지 않는다. `COMPLETED + current_step=8`이 담당자 검토 대기 상태이고, 확정 시 `FINALIZED + current_step=10`으로 전환한다. 실행은 항상 `CREATED`로 INSERT하며 허용 전이는 `CREATED→RUNNING`, `RUNNING→COMPLETED/FAILED`, `FAILED→RUNNING`, `COMPLETED→FINALIZED`뿐이다.

## 제44조 확정조건

확정 체크리스트 8개 — 모두 통과해야 확정한다(VRUN-W02, IF-API-50 `no` 1~8, `ValidationRunFinalizationServiceImpl`).

1. 실행 상태가 `COMPLETED`
2. 차변·대변 불균형 0건
3. `CRITICAL` 미처리 예외 0건
4. 정책 미존재·중복 0건
5. 귀속합계 오류 0건
6. 결과 상세합계와 요약합계 일치
7. 같은 검증월의 가장 최근 월 전체 실행(`MONTHLY`·`PRE_CONFIRM`)일 것
8. 같은 검증월에 이미 확정(`FINALIZED`)된 실행이 없을 것

체크리스트 밖 전제: 확정할 수 있는 실행 유형은 월 전체를 계산한 `MONTHLY`·`PRE_CONFIRM`뿐이다. `MANUAL_CONTRACT`(일일 변경계약 배치·차익 재검증)는 변경된 계약만 계산하므로 `COMPLETED`여도 확정하지 않는다(`FGC-VRUN-004`). 확정 사용자와 시각을 기록한다.

같은 달을 다시 검증했다면 이전 실행은 확정하지 않는다. `FINALIZED`는 그 실행의 검증결과를 영구히 잠그므로(SRC-027 D-02), 계산식·정책이 바뀐 뒤 재검증했는데 이전 실행을 확정하면 틀린 판정이 잠긴다(#468 재검증에서 실제 발생, #491). 순서는 `validation_run_id`로 정하고, 뒤 실행의 상태는 가리지 않는다 — `CREATED`·`RUNNING`·`FAILED`여도 다시 돌리려 했다는 뜻이므로 새 실행을 완료해 그것을 확정한다. `MANUAL_CONTRACT`(일일 변경계약 배치)는 월 전체를 다시 계산하지 않고 매일 생기므로 비교 대상이 아니다. 확정 직전 확인과 같은 달 실행 생성이 엇갈리지 않도록, 실행 생성과 확정은 같은 검증월 잠금(PostgreSQL 트랜잭션 advisory lock)을 잡아 직렬화한다 — 생성 중이면 확정은 그 커밋을 기다렸다가 새 실행을 보고 거부하고, 확정 중이면 생성이 기다린다.

확정은 그 달의 검증결과를 대표하는 **한 건**이다. 확정된 달에도 재검증 실행은 만들 수 있다 — 요구사항 FGC-FUN-044 인수조건 "확정 실행의 결과행은 수정·삭제되지 않고 동일 월 재검증은 새 실행번호로 생성되어 이전 결과와 비교할 수 있다"를 따른다. 다만 그 재검증 실행은 확정하지 않는다(확정조건 "같은 검증월에 이미 확정된 실행이 없을 것"). 원천 오류나 계산식 교정으로 생긴 차이는 재검증 실행의 결과를 확정 결과와 비교해 확인하고, 사후 점검 기록으로 남긴다. 사후 점검 기록은 예외함의 업무건이다 — 재검증 실행의 예외 생성 단계(8단계)가 그 달의 확정 실행과 1,200% 판정(`cap_check`)을 계약·지급단계별로 자동 비교해, 판정(`result_status`)이나 한도액(`limit_amount`)이 다른 건마다 상위 유형 `CAP_REVIEW_REQUIRED`, 상세 원인 `FINALIZED_RESULT_DIFF`, 심각도 `HIGH`로 기록한다(확정 전후 값과 두 실행 번호를 검출 증거로 남김). 새 상위 유형을 만들지 않는 것은 같은 1,200% 담당자가 처리하기 때문이고(SRC-032 D-05), 심각도를 `CRITICAL`로 두지 않는 것은 이미 확정된 달의 확정을 다시 막을 수 없기 때문이다. 담당자는 예외함의 기존 조치·사유·감사로그 흐름으로 차이를 검토해 종결하며, 확정 결과는 바뀌지 않는다. 확정 결과는 바뀌지 않으므로 같은 달을 재검증할 때마다 같은 차이가 다시 검출된다. 그래서 검토 후 확정 결과를 유지하면 반려(`REJECTED`, 사유 필수)로 종결한다 — 반려된 건은 증거(확정·재검증 판정·한도액·산입액)가 같으면 닫힌 채 남고, 해결(`RESOLVED`)로 닫은 건은 다음 재검증에서 `NEW`로 다시 열린다(SRC-032 D-04). 두 실행 모두에 있는 계약·지급단계만 비교하고, 차익거래·대사 결과의 비교는 아직 하지 않는다 (#498). 같은 달 두 실행을 동시에 확정해도 확정이 검증월 잠금을 잡은 뒤 이 조건을 세므로 두 번째는 거부된다 (#494, SRC-027 D-02).

이 중 DB가 직접 강제하는 것은 실행의 생성·상태전이, `status/current_step` 조합, `FINALIZED`의 `finalized_at`, 확정 후 하위결과 불변성이다. 차변·대변 불균형 0건, `CRITICAL` 미처리 예외 0건, 정책 누락·중복 0건, 귀속합계·상세합계 일치, 최신 실행 여부, 같은 달 기존 확정 여부, 확정 가능한 실행 유형은 서비스가 확정 직전에 조회해 강제해야 한다. `finalized_by`도 현재 DB에서 NOT NULL이 아니므로 서비스가 반드시 채운다. 서비스 검사를 우회할 수 있는 직접 DB 권한은 운영 역할에 부여하지 않는다.

## 제45조의2 계약체결비용은 나눠 쓰는 통장이 아니다

분급 계산에서 가장 많이 하는 실수는 **선지급수수료와 유지관리수수료를 계약체결비용이라는 하나의 통장에서 꺼내 쓴다고 생각하는 것**이다. 그렇지 않다.

계약체결비용은 각 수수료의 한도를 계산할 때 쓰는 **기준 금액**이다. 두 수수료는 각자 따로 이 기준을 사용한다.

| 수수료 | 한도 | 근거 | `source_class` |
|---|---|---|---|
| 선지급수수료 | 예정 지급총액 ≤ 계약체결비용 | REG-02 / 제4-32조제11항 | `REGULATORY` |
| 유지관리수수료 | 월 지급액 ≤ 계약체결비용 × 월 상한율 **그리고** 전체 총액 ≤ 계약체결비용 | REG-03 / 제4-32조제12항 본문·제4호 | `REGULATORY` |
| 장기유지수수료 | 월 지급액 ≤ 계약체결비용 × 0.4% | REG-05 / 제4-32조제12항제2호 | `REGULATORY` |

따라서 다음 계산은 **하지 않는다.**

```text
잘못된 계산
계약체결비용 - 선지급수수료 - 유지관리수수료 총액 = 미사용 한도   ✗
```

세 한도는 각각 따로 검증하며, 서로 차감하지 않는다.

```text
올바른 계산
선지급수수료 사용률   = 선지급 총액 ÷ 계약체결비용
유지관리 월 사용률    = 유지관리 월액 ÷ (계약체결비용 × 월 상한율)
유지관리 총액 사용률  = 유지관리 총액 ÷ 계약체결비용
장기유지 월 사용률    = 장기유지 월액 ÷ (계약체결비용 × 0.4%)
```

`acquisition_cost_check`는 계약·실행별 부모 요약을 저장하고, `acquisition_cost_check_detail`이 다음 네 계약체결비용 검증을 유형별로 저장한다.

```text
UPFRONT_TOTAL
MAINTENANCE_MONTHLY    (대상월 필수)
MAINTENANCE_TOTAL
LONG_TERM_MONTHLY      (대상월 필수)
```

각 상세행은 `actual_amount`, `limit_amount`, `usage_pct`, `result_status`, `decision_reason`, `calculation_snapshot`을 보존하며 하나라도 100%를 넘으면 부모를 `VIOLATION`으로 판정한다. 초년도 1,200% 사용률은 이 네 유형에 포함하지 않고 별도 `cap_check`에 저장한다.

## 제46조 4년 분급 시드정책

교육용 상품의 계약체결비용을 월납환산 초회보험료의 3,000%로 가정한다. 이 값은 실제 보험사의 상품 기초서류에서 확인한 규제 수치가 아니라 합성 상품을 위한 `PROJECT_ASSUMPTION`이다. 실제 연계 시에는 보험사·상품·판매버전별 기초서류 값을 `INSURER_RULE`로 적재해 대체한다. (`REG-02`, `SRC-022`; 기사 예시의 비규제성은 `SRC-016`)

### 규제 상한 (`REGULATORY` — 회사가 바꿀 수 없음)

| 항목 | 상한 | 근거 |
|---|---|---|
| 선지급수수료 총액 | 계약체결비용 이내 | REG-02, 제4-32조제11항 |
| 유지관리수수료 월 지급액 | 계약체결비용의 **1.5% 이내** | REG-04, 부칙 제3조 (제12항의 `0.8%`를 `1.5%`로 읽음) |
| 유지관리수수료 지급기간 | 최대 **4년(48개월)** | REG-04, 부칙 제3조 (제12항의 `7년`을 `4년`으로 읽음) |
| 유지관리수수료 총액 | 계약체결비용 이내 (최대치 검산 1.5% × 48 = **72%**) | REG-03 제4호, REG-04 |
| 적용 대상 | 2027.1.1~2028.12.31 특례기간(판매채널 구분 없음, SRC-036) | REG-19, 부칙 제2·3조 |

### FGC 시드정책 (`GA_POLICY` / `PROJECT_ASSUMPTION`)

| 항목 | FGC 선택값 | 분류·근거 |
|---|---|---|
| 계약체결비용 | 월납환산 초회보험료 × 30 (3,000%) | `PROJECT_ASSUMPTION` — 합성 상품 기초서류 입력값 (`REG-02`, `SRC-016·022`) |
| 선지급수수료 | 계약 1회차 월납보험료의 600% | `GA_POLICY` — 계약체결비용의 20% 사용 (`REG-02`, `SRC-022`) |
| 유지관리수수료 | 계약체결비용의 월 **1.5%** | `GA_POLICY` — 규제상 월 상한 이내 선택 (`REG-04`, `SRC-003·022`) |
| 지급기간 | 1~48차월 | `PROJECT_ASSUMPTION` — 최대 48개월만 규제상 한도이며 최초 지급회차는 근거 없음 — 확인 필요 (`REG-04`, `SRC-003·022`) |
| 동일금액 | 매월 동일 | `REGULATORY` 요건을 준수하는 시드 설계 (`REG-03`, `SRC-022`) |

- 저장 위치: 계약체결비용은 분급 정책버전(`FOUR_YEAR_COMMISSION`·`SEVEN_YEAR_COMMISSION`)의 `policy_parameter`에 판매버전별 값으로 둔다 — 키 `ACQUISITION_COST_BASIS`(기준: 월납환산 초회보험료), `ACQUISITION_COST_RATE_PCT`(시드 3000). 현재 스키마에 전용 컬럼이 없어 정한 **구현 규칙(업무 규칙 아님 — 가상 GA 정책으로 정함, 팀 확정 필요)** 이다. 실제 보험사 기초서류 값이 들어오면 `INSURER_RULE` 정책버전으로 대체한다. 판정 결과에는 사용한 값을 `acquisition_cost_check.calculation_snapshot`에 남긴다.
- 지급단계: 위 시드 요율은 **GA→설계사** 규칙이다. 보험회사→GA 시드는 별도 정책버전으로 만들며 두 단계의 한도 검증을 합치지 않는다(제17조, REG-09).
- 매월 동일 금액은 `commission_rule.equal_monthly_yn=true`로 표시하고 스케줄 생성 시 회차 금액이 모두 같은지 검사한다(REG-03).

> FGC는 월 상한율을 상한과 같은 값으로 잡았다. 상한과 회사 선택값이 우연히 같더라도 **두 값은 다른 분류**이므로 규제 상한 정책은 `REGULATORY`, FGC 지급률 정책은 `GA_POLICY`로 분리한다. 계약체결비용과 최초 지급회차처럼 실제 기초서류·지급기준을 확보하지 못한 값은 `PROJECT_ASSUMPTION`으로 표시한다. (`REG-02~04`, `SRC-003·016·022`)

### 월납보험료 100,000원 검산

```text
계약체결비용   = 100,000 × 30 = 3,000,000원

[선지급수수료]
  지급액       =   600,000원
  한도         = 3,000,000원 (계약체결비용)
  사용률       = 20.0%                          → 정상

[유지관리수수료]
  월액         = 3,000,000 × 1.5% = 45,000원
  월 한도      = 3,000,000 × 1.5% = 45,000원
  월 사용률    = 100.0%                          → 정상 (상한 이내)
  총액         = 45,000 × 48 = 2,160,000원
  총액 한도    = 3,000,000원
  총액 사용률  = 72.0%                           → 정상

[초년도 1,200%]
  초년도 예정  = 600,000 + 45,000 × 12 = 1,140,000원
  한도         = 100,000 × 12 = 1,200,000원
  사용률       = 95.0%                           → WARNING
```

초년도 사용률이 95%이므로 시책·지원금·공통비가 조금이라도 추가되면 바로 `VIOLATION`이 된다. 4년 분급 시드계약은 1,200% 여유가 거의 없는 상태로 설계한 것이며 이는 의도한 것이다.

계약체결비용은 전액 지급해야 하는 목표금액이 아니라 지급한도다. `(계약체결비용 − 선지급수수료) ÷ 48 = 50,000원`으로 강제하면 월 1.666667%가 되어 1.5% 상한을 초과하므로 사용하지 않는다.


## 제47조 7년 분급 시드정책

### 규제 상한 (`REGULATORY` — 회사가 바꿀 수 없음)

| 항목 | 상한 | 근거 |
|---|---|---|
| 선지급수수료 총액 | 계약체결비용 이내 | REG-02, 제4-32조제11항 |
| 유지관리수수료 월 지급액 | 계약체결비용의 **0.8% 이내** | REG-03, 제4-32조제12항제1호 |
| 유지관리수수료 지급기간 | 최대 **7년(84개월)** | REG-03, 제4-32조제12항 본문 |
| 유지관리수수료 총액 | 계약체결비용 이내 (최대치 검산 0.8% × 84 = **67.2%**) | REG-03 제4호 |
| 장기유지수수료 월 지급액 | 계약체결비용의 **0.4% 이내** | REG-05, 제4-32조제12항제2호 |
| 장기유지수수료 지급조건 | 계약이 **5년 이상 유지**될 것 | REG-05 |
| 적용 대상 | 2029.1.1 이후 적용 상품버전(판매채널 구분 없음, SRC-036) | REG-19, 제4-32조제12항 |

### 두 수수료의 한도는 합치지 않는다

유지관리수수료(월 0.8%)와 장기유지수수료(월 0.4%)는 **조문상 서로 다른 호에 규정된 별개 한도**다. 합쳐서 월 0.8%를 넘으면 안 된다는 규정은 없다.

```text
장기유지수수료 지급 구간에는 두 수수료가 동시에 지급된다.
  유지관리   월 0.8% 이내
+ 장기유지   월 0.4% 이내
= 해당 월 최대 1.2%
```

`maintenance_check.limit_valid_yn`은 **두 수수료를 각각 별도로** 월 상한과 비교한다. 합산액을 하나의 상한과 비교하지 않는다.

> `PROJECT_ASSUMPTION` — REG-03 제4호의 "총액은 계약체결비용 이내"에 장기유지수수료가 포함되는지는 조문에 명시되어 있지 않다. FGC는 **포함되는 것으로 보수적으로 가정**하고 두 총액의 합을 계약체결비용과 비교한다. 최대치로 계산해도 67.2% + 9.6% = 76.8%이므로 어느 해석을 따르든 한도를 넘지 않는다. 최종 FAQ 공문이 확정되면 재검토한다.

### FGC 시드정책 (`GA_POLICY` / `PROJECT_ASSUMPTION`)

|---|---|---|

| 유지관리 지급기간 | 1~84차월 | `PROJECT_ASSUMPTION` — 최대 84개월만 규제상 한도이며 최초 지급회차는 근거 없음 — 확인 필요 (`REG-03`, `SRC-022`) |
| 장기유지수수료 | 계약체결비용의 월 **0.4%** | `GA_POLICY` — 규제상 월 상한 이내 선택 (`REG-05`, `SRC-022`) |

계약체결비용 저장 위치·지급단계·동일금액 표시는 제46조와 같다.

```text
계약체결비용   = 100,000 × 30 = 3,000,000원

[유지관리수수료]

  월 한도      = 24,000원
  월 사용률    = 100.0%                          → 정상
  총액         = 24,000 × 84 = 2,016,000원
  총액 한도    = 3,000,000원
  총액 사용률  = 67.2%                           → 정상

[장기유지수수료]  61~84차월
  월액         = 3,000,000 × 0.4% = 12,000원

  월 사용률    = 100.0%                          → 정상
  총액         = 12,000 × 24 =   288,000원

[유지관리 + 장기유지 총액 (보수적 가정)]
  합계         = 2,016,000 + 288,000 = 2,304,000원
  한도         = 3,000,000원

[61~84차월 월 지급액 합산]

[초년도 1,200%]
  초년도 예정  = 600,000 + 24,000 × 12 = 888,000원
  한도         = 100,000 × 12 = 1,200,000원
  사용률       = 74.0%                           → 정상
```

## 제48조 계약상태와 담당자

회차 지급 여부는 그 회차 **지급예정일(`schedule_line.due_date`) 시점의 계약 상태**로 정한다. 근거분류는 `PROJECT_ASSUMPTION`이며 `SCHEDULE_ELIGIBILITY` 정책(`STATUS-MONTH-RULE-2026`)의 파라미터로 관리한다 — `STATUS_MONTH_RULE=PAY_IF_ACTIVE_ON_DUE_DATE`, `PRORATION_RULE=NO_PRORATION`(일할계산 없음, 매월 동일 금액 요건 REG-03과 맞춤), `REVIVAL_BACKFILL_RULE=NO_RETROACTIVE`(인터페이스정의서 §9-5). 최종 FAQ 확정 시 새 정책버전으로 재검증한다.

| 지급예정일 시점 상태 | 회차 처리 | 회차 상태 |
|---|---|---|
| `ACTIVE`·`REVIVED` | 지급 | `PLANNED`→`CONFIRMED` |
| `UNPAID` | **보류**. 보류 회차는 지급 확정을 막는다. 납입이 재개되면 지급예정일을 재개(입금) 기준으로 다시 잡고, 실효되면 미지급으로 바꾼다(2026-10-12·13 PL 결정, #523) | `HOLD` |
| `LAPSED` | 그 회차 미지급. 부활하면 부활일 이후 회차부터 재개하고 실효 기간 회차는 소급하지 않는다 | `CANCELLED` |
| `TERMINATED`·`MATURED` | 미지급, 이후 회차 전부 중단 | `CANCELLED` |
| `CANCELLED`(청약철회) | 미지급, 기지급분은 환수 검토 후보(FUN-054) | `CANCELLED` |

- 실효 기간 회차를 부활 뒤 지급하려면 자동으로 하지 않고 회사 약정(업계 "부활수수료", SRC-019)을 근거로 사람이 처리한다. 2차 FUN-029가 재개 대상·비대상과 근거를 보여 준다.
- 미래 미지급은 법정 환수가 아니다(REG-13, 제48조의2 2).
- 최초 모집설계사와 현재 유지관리 담당자를 분리한다(REG-07). 담당자 변경일 이전 확정 회차는 바꾸지 않고, 변경 효력일 이후 회차의 수령인만 재지정한다(FUN-010 최소 범위·FUN-064). 효력일 기준 담당자가 없으면 회차를 보류·예외로 둔다.
- 회차 상태 전환(`HOLD`·`CANCELLED`·`RESTARTED`)은 2차 FUN-015·028·039 범위다. 1차는 대사 예상 원천을 읽을 때만 이 표를 적용한다(제36조 대사 대상의 범위).

## 제48조의2 환수 운영원칙 (4년·7년 분급·차익거래)

4년·7년 분급과 차익거래의 지급중단·환수·회수는 다음 원칙으로 처리한다. (`REG-13·14·16`, `SRC-016·019·020`)

1. 보험회사→GA(`INSURER_TO_GA`)와 GA→설계사(`GA_TO_FC`)의 환수 규칙·사건·원장행을 분리한다.
2. 해지·실효 뒤 아직 지급하지 않은 미래 유지관리수수료를 중단하는 것과 이미 지급한 금액을 환수하는 것을 구분한다. 미래 미지급액은 환수액으로 기록하지 않는다. (`REG-13`, `SRC-022`)
3. 실제 환수율은 보험회사·상품·수수료항목·계약일·경과회차·책임사유별 `clawback_rule` 정책버전으로 관리한다. (`REG-14`, `SRC-019·020`)
4. 일반 해지·실효와 설계사 귀책 사유를 구분하되, 업계자료에 등장하는 특정 환수율이나 `100% 환수` 표현을 공통 법정값으로 자동 적용하지 않는다. 실제 위탁·위촉계약 또는 회사 지급기준이 필요하다. (`REG-14·16`, `SRC-016·019·020`)
5. 기사·분석자료에 제시된 조항 번호나 예시 수치는 법령 파라미터로 직접 등록하지 않는다. 확인 전에는 `PROJECT_ASSUMPTION` 또는 `REVIEW_REQUIRED`로 남긴다. (`REG-14·16`, `SRC-016`)
6. 적용일 현재 유효한 회사별 약정 원본을 확보하지 못하면 **근거 없음 — 확인 필요**로 표시하고 환수 확정을 차단한다. (`REG-14·16`; `SRC-021` 미확보)
7. 차익거래 검증(제33조)에서 `CANDIDATE`가 나오면 환수 검토 대상을 만든다. 이 환수 조치와 환수사유·금액의 기록, 모집종사자 안내는 회사 약정이 아니라 감독규정 운영기준이다(`REG-12`, `SRC-025` Q11 ①). 회수 수단은 동종채권 상계·직접 납입 요구·수수료 이행보증보험 청구 중에서 고른다(Q11 ②). 환수율·산식은 여전히 회사 약정(`REG-14`)이다.
8. 환수율은 기지급액의 100%를 넘지 않는다 — DB가 `clawback_line.applied_rate_pct ≤ 100`으로 강제한다(V1). 100% 초과 환수(가산 환수)는 FGC 가상 GA 정책에서 쓰지 않는다 — **업무 규칙 아님 — 가상 GA 정책으로 정함**.
9. 환수 건 상태는 `DETECTED → CALCULATED → NOTIFIED → (OBJECTED) → CONFIRMED → RECOVERING → CLOSED`이고, 어느 단계에서든 `CANCELLED`로 간다(V1 `clawback_case`). 통지·이의 규칙은 제57조를 따른다.

# 제14장 정책변경과 감사

## 제49조 정책상태

```text
DRAFT ──SUBMIT──▶ REVIEW ──APPROVE──▶ APPROVED ──ACTIVATE──▶ ACTIVE ──▶ RETIRED
  ▲                  │                    │
  └──────REJECT──────┘                    └──────────────▶ RETIRED
DRAFT ──▶ APPROVED  : DB는 허용하지만 1차 Flyway 시드 전용. 2차 API(IF-API-75)는 허용하지 않는다
DRAFT ──▶ ACTIVE    : DB가 막는다(SRC-049)
```

`APPROVED`, `ACTIVE`, `RETIRED` 정책과 상세 규칙은 수정·삭제하지 않는다. 변경은 새 `version_no`로 만든다. 승인 뒤에는 적용기간(`effective_to`)도 바꿀 수 없다.

**2차 승인 흐름(IF-API-75, FUN-017 최소 범위 — FUN-067 Must의 필수 의존)**: 제출은 정산담당자·GA관리자, 승인·반려·활성화는 GA관리자가 한다. 작성자와 승인자는 달라야 하고(`FGC-POL-001`), 적용기간이 겹치면 활성화를 막고(`FGC-POL-002`), 화면이 본 상태를 함께 보내 동시 승인 경합을 막는다(`FGC-POL-003`). 모든 동작은 `policy_approval_action`과 `audit_log`에 사유와 함께 남긴다(REG-22). 현재 정책 API는 조회만 있다(미구현).

**갱신·승계 규칙**: 같은 정책코드의 내용을 바꾸려면 새 `version_no`를 `DRAFT`로 만들고 **이전 버전의 유효 상세 행을 모두 포함한 전체 대체본**으로 채운다. 기간을 나눠야 하면 새 버전 안에서 상세 행(예: `refund_rate_table.effective_from/to`)으로 나눈다. 활성화는 한 트랜잭션에서 ① 새 버전 `APPROVED` 확인 ② 같은 정책코드의 이전 `ACTIVE`를 `RETIRED` ③ 새 버전 `ACTIVE` 순서로 한다(데모 V46·V52·V56과 같은 순서). 적용기간 중복 검사(`FGC-POL-002`)는 **활성화가 끝난 뒤 남는 `ACTIVE` 집합**에서 같은 정책 유형·상품·납입기간이 겹치는지로 판정한다. 과거 검증 실행은 당시 정책버전 ID를 계속 참조하므로 결과가 바뀌지 않는다. 이 규칙은 **업무 규칙 아님 — 가상 GA 정책으로 정함**(구현 규칙, 근거: 데모 승계 패턴과 정책 불변 트리거).

## 제50조 1차 정책관리 방식

1차에는 정책 CRUD 화면을 만들지 않는다.

- 정책은 Flyway 시드로 적재하되, `DRAFT`로 INSERT하고 규칙 행을 모두 넣은 다음 `DRAFT → APPROVED → ACTIVE` 두 단계로 승격한다. `ACTIVE` 정책 아래에는 규칙 행을 추가할 수 없다.
- `created_by`와 `approved_by`는 모두 필수이며 서로 다른 사용자여야 하고, `APPROVED` 전환 시 `approved_at`과 승인근거를 함께 기록한다. 이 분리는 v2.1.6부터 신규 `APPROVED`·`ACTIVE` 행에 DB CHECK로 강제된다.
- 조회·적용만 가능
- 변경 시 새 마이그레이션과 새 정책버전 생성
- 2차: 최소 승인·활성화 흐름(IF-API-75, POL-W02)을 먼저 제공하고, 전체 작성·편집 화면은 FUN-017(S) 범위로 둔다. AI 문서함에서 확정한 환급률표·수수료율표 `DRAFT`는 이 흐름을 거쳐야 계산에 쓰인다(제55조).

예외적으로 `db/migration/V2__batch_watermark_and_schedule_eligibility.sql`이 만든 `STATUS-MONTH-RULE-2026` v1은 작성자·승인자 없이 `ACTIVE`로 직접 삽입된 유산 행이다. v2.1.6의 `ck_policy_authorship`가 `NOT VALID`인 이유도 이 행을 보존하기 위해서다. `db/demo/V3`가 로드되면 v1을 `RETIRED`하고 정상 절차의 v2를 발행하지만, 기본 `db/migration`만 적용한 DB에는 유산 행이 남을 수 있다. 운영 전 해당 행을 폐기·재발행하고 제약을 `VALIDATE`하기 전까지 정책 저작통제가 완결되었다고 표시하지 않는다.

# 제16장 2차 확장 업무 (요구사항 v2.2.2-r19 초안 — 팀 승인 시 확정)

## 제55조 AI 문서 입력의 운영원칙

근거분류: `PROJECT_ASSUMPTION`(OI-021 결정, 2026-10-22). 보험사가 해약환급률표·정산데이터를 GA에 문서로 준다는 사실은 SRC-025 Q12-2가 뒷받침한다.

1. **허용 서식** — 구현된 서식만 받는다. 추출 Must는 ① 예상 해약환급률표(FUN-067) ② 보험사 정산데이터(FUN-068) ⑤ 협회 수수료 등급자료(FUN-078)다. ③ 수수료율표·시책(FUN-070) ④ 증권·청약서(FUN-071)는 구현 전까지 '지원 예정'으로만 분류한다. 개인정보가 없는 합성·가상 문서만 받는다.
2. **사람 확정만 반영** — AI 출력은 원장·지급확정·정책 활성화에 자동으로 들어가지 않는다(COR-007). 확정의 뜻은 서식마다 다르다: 정산데이터는 원천 명세 적재, 환급률표·수수료율표는 정책 `DRAFT` 저장(활성화는 제49조 승인 흐름), 협회 등급자료는 자료 기준일 버전 적재, 증권은 계약 등록 폼 채움.
3. **정산데이터 확정은 지급 승인이 아니다** — 확정하면 문서 단위 `statement_batch`와 `source_type='INSURER_STATEMENT'`·`payment_stage='INSURER_TO_GA'` 원천 행으로 넣는다. `GA_MANUAL_PAYMENT`로 넣지 않는다. 1,200% 사전검증·계약상태 조건으로 거르지 않는다(제31조). 한도 초과·해지 후 지급·원본 내 중복·모집자 불일치는 보험사가 보낸 사실이므로 그대로 적재하고 기존 기표·대사·예외가 판정한다.
4. **명세 종류별 처리 범위** — (가) 수수료 명세(`INSURER_COMMISSION`)의 지급(`PAYMENT`) 행만 월 통합검증에서 `ACTUAL_INSURER_STATEMENT`로 기표되고 대사된다. (나) 차감(`DEDUCTION`) 행과 조정·환수 명세(`INSURER_ADJUSTMENT`·`INSURER_CLAWBACK`)는 원천으로 보존만 하고 '후속 검증 대기'로 표시한다. 이 명세의 대사 규칙은 근거 없음 — 확인 필요이며 완료로 표시하지 않는다. (다) 월 검증 대상(`validation_target` SELECTED)에 들지 않은 계약의 원천은 '검증 실행 미선정'으로 표시한다.
5. **보험사 정정 명세** — 2차는 '전체 대체본'만 받는다. 담당자가 정정 유형과 대체 대상 묶음을 지정한다(AI가 추론하지 않음). 부분 확정·행 제외를 허용하지 않고, 모든 행이 통과했을 때 한 트랜잭션으로 전환한다: 새 묶음(다음 판) 적재 → 이전 묶음 `SUPERSEDED` → 이전 원천 `CANCELLED` → 이전 `POSTED` 실제 분개 역분개(제40조). 하나라도 실패하면 전부 원복한다. 같은 이전 판에 대한 동시 대체는 하나만 성공한다. **이전 원천의 분개가 `FINALIZED` 검증 실행에 연결돼 있으면 전환 전에 거절**하고 검토 대기로 둔다 — 마감 후 정정은 2차 범위 밖이다. '차액 추가본'은 자동 확정하지 않는다.
6. **중복·멱등** — 같은 파일(SHA-256)은 새 문서를 만들지 않는다. 원천 업무키 `(source_type, source_business_key)`로 중복을 막는다. 원본 안에 실제로 두 번 찍힌 행은 둘 다 보존해 대사에서 `DUPLICATE`로 판정되게 한다. 한 행이라도 확정된 문서는 거절·재추출할 수 없고 남은 행은 사유를 적어 제외한다(전체 대체본은 제외 불가).
7. **원본 보존** — 원본 파일은 확정·거절 뒤 또는 `FAILED`·장기 미처리 시 `purge_after`에 삭제하고, 추출 행·확정 기록은 반영된 업무 자료와 같은 기간 보존한다(DB설계서 v1.3 `intake_document`). 기본값: 거절·실패 문서 원본은 30일 뒤, `REVIEW` 상태로 30일 넘게 방치된 문서는 알림 뒤 60일에 삭제한다 — **업무 규칙 아님 — 가상 GA 정책으로 정함**(FUN-066이 가상 GA 정책으로 정하라고 넘김, 팀 확정 필요. 개인정보보호법 제21조의 불필요 시 파기 취지, SRC-043. 합성 문서만 받으므로 법정 보존 대상이 아님).
8. **외부 LLM** — OpenAI API, 기본 모델 `gpt-4o-mini`(설정값), 서버 게이트웨이 한 곳, `store=false`, Files API 미사용, 총 예산 10달러(개발·평가 약 8달러, 발표 예비 약 2달러). xlsx·csv의 행·금액은 결정론 파서가 보존하고 LLM은 열 의미·비정형 셀만 해석한다. 문서 행·전체 계약에 대한 대량 반복 호출과 같은 문서 재확정 시 재추출을 하지 않는다(사용자가 고른 계약 1건에 대한 피코 질문은 정상 흐름). 401·403·쿼터 소진은 재시도하지 않고 규칙형으로 대체한다(OI-023 r19, SER-013, SRC-059·060).
9. 데이터 구조 변경(`statement_batch.data_origin='AI_INTAKE'`, 판 번호·대체 관계 컬럼, `SUPERSEDED` 상태)은 DB설계서 v1.3 제안이며 현재 DDL에는 없다. 구현 착수 때 Flyway(V57 이후)로 추가한다.

## 제56조 대형 GA 비교설명 (FUN-078·079 — r19 초안, OI-024·025 검토중)

1. FGC금융서비스는 직전 분기 일평균 소속 설계사 600명(프로젝트 가정)으로 대형 GA다. 별표 5의6 제5호의 비교·설명 의무가 적용된다(SRC-022 제4-11조①, SRC-056).
2. **협회 자료가 정본** — 수수료 등급·순위는 보험협회가 산출해 GA에 준 자료를 쓴다(SRC-025 Q19·Q20). 협회 자료는 정책버전이 아니라 **자료 기준일 버전의 참조 자료**이며 GA관리자가 확정해 적재한다. FGC가 계산한 등급(유사상품군 평균 대비 5단계, SRC-002)은 '검증용'으로만 표시하고 협회값과 다르면 차이를 보인다.
3. **등급과 순위를 구분** — 순위는 비교·추천 대상 안에서 매기며 1순위가 수수료가 가장 낮다(SRC-002, FAQ 2차 확인서 표준안). 순위는 협회 자료의 비교 집합·기준일과 함께 보존하고 다른 부분 집합에 옮겨 쓰지 않는다. 비교 표의 상품 집합에 맞는 순위 자료가 없으면 순위를 '자료 없음'으로 두고 확인서를 만들지 않는다.
4. **비교 대상** — 같은 상품군(Q17 분류 기준표, 심사방식·해약환급금 유형 구분) 안의 다른 보험회사 상품 3개 이상(제5호 가목). 계약자가 고른 상품은 비교 대상에 반드시 들어간다(나목). 권유 가능한 동종·유사상품을 판매하는 모든 보험회사 목록을 준다(나목, Q23). 제휴 상품이 3개 미만이면 확인서 생성을 막고 판매 제한을 안내한다(Q18). '업권 전체 동종·유사 상품 2개 이하' 예외는 우리 DB 건수가 아니라 협회 자료 등 증빙과 확인자(GA관리자) 기록이 있을 때만 인정한다.
5. **설명 항목과 추천사유** — 상품 선정 기준·추천사유·수수료등 수준을 설명한다(다목). 추천사유는 동종·유사 상품과 비교한 권유 상품의 구체적 장점으로 쓰고, 보장성 상품을 '환급금'만으로 추천하는 문장은 저장을 막는다(Q24). AI는 추천사유 초안만 쓰며 등급·순위 값을 바꾸지 않는다.
6. **확인서** — 설명내용에 대한 확인서를 받아야 한다(제5호 본문). 서버에 저장된 비교설명 초안(판 번호)으로만 PDF를 만들고, 화면이 보낸 목록을 그대로 믿지 않는다. PDF 생성은 수령 완료가 아니다. 수령은 PDF 판마다 수령일·확인자·서명본 보관 위치로 따로 기록하고, 새 판을 만들어도 이전 판 수령 이력은 남긴다. 고객 이름·서명 이미지는 저장하지 않는다(SRC-027 D-05).
7. **예외** — 제5호 단서의 4가지뿐이다: 통신수단 모집(FGC 해당 없음, SRC-036), 기업성 보험(Q21), 보험협회 보험료 비교·공시 조회 결과를 계약자가 확인한 자동차보험(확인 여부 기록), 간단보험대리점의 간단보험(Q22 — FGC는 해당 없음). 상품 선택은 설계사와 고객이 하며 FGC는 추천을 확정하지 않는다.
8. 협회 실제 파일·API 명세는 근거 없음 — 확인 필요이므로 시연은 가상 양식으로 한다(OI-025).

## 제57조 환수 통지·이의 (FUN-084·056·083 — r19 초안)

1. 환수 통지서에는 계약번호, 환수 사유와 사유 발생일, 대상 수수료 항목, 기지급액, 적용 환수 정책버전·환수율·계산 근거, 이의 방법과 기한, 상계 등 회수 방법을 넣는다(SRC-025 Q11 ①②). 계약자 개인정보는 넣지 않는다(SRC-027 D-05). 양식에 '가상 양식'을 표시한다.
2. **문서 생성과 통지는 다르다.** PDF 생성은 문서번호·판·해시·생성자·시각만 남기고 환수 건 상태를 바꾸지 않는다. 통지 등록은 수신 설계사·통지일·방법·증빙을 따로 입력한다.
3. 첫 통지는 환수 건이 `CALCULATED`일 때만 하며, 최초 통지일을 기록하고 `NOTIFIED`로 바꾼다. 추가 통지(`NOTIFIED`·`OBJECTED`·`CONFIRMED`·`RECOVERING`)는 통지 이력만 더하고 상태·최초 통지일·이의 접수시각을 바꾸지 않는다. `CLOSED`·`CANCELLED` 건에는 통지를 등록할 수 없다(`FGC-CLAW-002`).
4. **이의기간: 최초 통지일 다음 날부터 14일.** 기간 안에 이의(FUN-083)가 접수되면 `OBJECTED`로 바꾸고 정산담당자가 답한다. 기간이 지나도 자동 확정하지 않고 담당자가 `CONFIRMED`로 전환한다. 문의·이의 답변 처리기한은 접수 후 5영업일이다. 두 값 모두 **업무 규칙 아님 — 가상 GA 정책으로 정함**(FUN-083·084가 가상 GA 정책으로 정하라고 넘김, 법정·협회 기준 없음 — SRC-025 Q11은 기록·안내만 요구, 팀 확정 필요). `policy_parameter`로 두고, GA협회 표준내부통제기준 원문이나 제3차 FAQ가 기한을 정하면 다시 연다.
5. 정정이 필요하면 게시판에서 금액을 바꾸지 않고 기존 정정 경로(지급 건 정정·원장 역분개, 제40조)로만 처리한다.

## 제58조 설계사 역할과 본인 데이터 경계 (FUN-085 — r19 초안)

1. 설계사 계정(`AGENT`)은 `app_user.agent_id`로 설계사 1명과 연결한다(대표 계정 1개).
2. 볼 수 있는 범위: 본인이 모집자이거나 현재 유지관리 담당인 계약, 본인이 수령인인 지급·환수 건, 본인이 작성한 비교설명·문의, 본인 대상 통지서.
3. 목록·상세·다운로드·PDF·AI 도구 모두 서버에서 같은 범위를 적용한다. URL의 ID를 바꿔도 거절한다. 메뉴 숨김만으로 처리하지 않는다.
4. AI 문서함 원본·추출 행은 여러 설계사 정보가 섞이므로 내부 역할(정산담당·GA관리자·준법)만 본다. 설계사에게는 본인용으로 정제한 명세·PDF만 준다.
5. 비교설명용 상품·등급 자료는 업무 자료라 전 역할이 본다.
6. 고객관리(CRM)·생일 고객 조회는 하지 않는다(OI-022, SRC-027 D-05).
