# 대시보드 JPA 전환 검증 (#382)

검증일: 2026-09-27. 관련 이슈: #382, #366.

## 변경 내용과 선택 이유

`DashboardServiceImpl`의 카드 집계 6개와 최근 목록 2개를
`DashboardQueryRepository`로 전환하고, 사용처가 없어진 `DashboardMapper`와 XML을 제거했다.
예외함의 미처리 건수 비교 테스트도 새 Repository를 사용한다.

PostgreSQL의 `DISTINCT ON`, 월별 표현식 인덱스, 여러 영역을 연결하는 집계 조건을
유지하기 위해 `EntityManager` 기반 네이티브 SQL과 DTO projection을 사용했다.
집계를 위한 중복 엔티티나 다른 영역의 엔티티 의존을 추가하지 않았다.
한도 위반·주의 쿼리는 상태 파라미터를 받는 공통 메서드로 묶었다.

월 필터 후 최신 판정 선택, 대사 그룹별 최신 실행, 전역 원장·예외 집계,
생성시각과 ID 보조 정렬, LEFT JOIN의 null, 목록 제한을 유지했다.
서비스의 읽기 전용 트랜잭션 하나에서 조회 8개가 실행되며,
Repository의 읽기 전용 트랜잭션은 호출한 서비스 트랜잭션에 참여한다.
DB 스키마와 기존 Flyway 파일은 변경하지 않았다.

## 실행 환경과 자동화 결과

- Windows, Java 21, Gradle 9.7.0, PostgreSQL 17.10.
- 작업 폴더에 만든 독립 임시 PostgreSQL 클러스터를 별도 루프백 포트로 실행했다.
  기본 테스트 설정은 Testcontainers를 그대로 사용하며, 이번 실행에만
  `SPRING_DATASOURCE_URL`, `SPRING_DATASOURCE_USERNAME`, `SPRING_DATASOURCE_PASSWORD`로
  임시 DB를 지정했다. Flyway migration/demo를 적용하고 예약 배치는 비활성화했다.
- 아래 명령의 관련 테스트 **39개 전부 통과**, `assemble` 성공.

```powershell
.\gradlew.bat test --tests 'com.susukkang.fgc.dashboard.*' --tests 'com.susukkang.fgc.exceptioncase.mapper.ExceptionCaseQueryMapperIntegrationTest' assemble
```

기존 통합 테스트 14개에 지급단계·보험사별 분리, 월 우선 필터,
동일 시각 ID 정렬, 최근 목록의 전체 필드·날짜·null 매핑 등을 보강했다.
Hibernate statistics로 요약 조회의 쿼리 실행 수와 준비된 SQL 수가 각각 **8회**임을 확인했다.
API/화면 테스트는 서비스 mock을 사용하고, 서비스 통합 테스트는 실제 PostgreSQL을 사용한다.

빌드한 실행 가능 WAR를 임시 DB와 별도 로컬 HTTP 포트로 기동했다.
`Started FgcApplication` 로그와 `GET /login`의 HTTP 200 응답을 확인했다.
이 HTTP 확인은 서버 기동 확인이며, 로그인 후 대시보드의 수동 UI 검증은 아니다.

## 기존 SQL과 비교

삭제 전 XML의 SQL과 새 Repository의 SQL을 같은 트랜잭션·입력으로 비교했다.
조회 월은 2038-07, 계약 20개에 한도 판정 200개, 차익 판정 200개,
대사 실행 10개와 결과 200개, 예외 20개, 검증 실행 5개,
불균형 원장 헤더·라인 각 1개를 구성했다. 비교 후 fixture는 롤백했다.

조회 8개의 결과와 순서가 모두 일치했고 실행계획 구조·추정값도 같았다.
`EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`을 전후 교대로 각각 3회 실행한
DB 실행시간 중앙값은 다음과 같다. 계획 시간은 아래 수치에 포함하지 않았다.

| 조회 | 기존 SQL (ms) | 새 SQL (ms) |
| --- | ---: | ---: |
| 한도 위반 | 0.048 | 0.045 |
| 한도 주의 | 0.048 | 0.048 |
| 차익 후보 | 0.044 | 0.048 |
| 대사 불일치 | 0.058 | 0.053 |
| 원장 불균형 | 0.028 | 0.029 |

작은 합성 데이터와 캐시가 적용된 DB에서의 동등성·실행계획 확인이다.
이 시간 차이로 성능 개선을 주장하지 않으며, 애플리케이션 전체 응답시간이나
운영 규모의 부하 성능을 측정한 결과도 아니다.

## PR 확인 항목

실행 코드와 테스트에 대시보드 Mapper 참조가 남아 있지 않다.
Flyway V23/V33의 과거 Mapper 이름이 적힌 주석은 마이그레이션 이력 보존을 위해 유지했다.
전체 프로젝트 CI, 리뷰어 지정과 리뷰 완료는 PR 단계에서 확인해야 한다.

## 수동 검증 시나리오 (작성 완료, 실행 전)

자동 테스트와 별도로 실제 로그인 세션에서 화면·API·DB가 연결되는 흐름을 확인한다.
아래 항목은 수동 검증 계획이며 아직 실행 결과가 아니다.
데이터가 있는 테스트 DB에서 진행하고, 비교 중에는 데이터를 변경하지 않는다.
예시의 2026-07/08은 해당 환경에서 결과가 존재하는 인접 월로 바꿔도 된다.
표시·정렬 검증에는 최근 예외 6건 이상, MONTHLY 실행 4건 이상과
계약/실행자 참조가 없는 행이 있으면 좋다. 해당 데이터가 없으면 그 항목은 미실행으로 기록한다.

M01의 카드/API 대응은 `capViolation`, `capWarning`, `arbitrageCandidate`,
`reconMismatch`, `journalImbalance`, `openException`이다.
최근 목록은 `recentExceptions`, `recentRuns`로 비교한다.
화면은 서버 렌더링이므로 대시보드를 열 때 요약 API의 AJAX 요청이 없어도 정상이다.

카드와 이동한 상세 목록은 최신 결과 선택·전역/월별 범위·이력 표시 기준이 다를 수 있다.
목록 전체 건수와 카드 값을 무조건 동일하다고 판정하지 않는다.
차이가 있으면 동일한 데이터의 전환 전 결과와 비교해 기존 동작인지 확인한다.

월 내 재실행과 다음 월 결과 공존, 보험사·지급단계별 최신 대사,
동일 시각 ID 정렬은 PostgreSQL 자동 테스트로 확인했다.
수동 검증 기록에는 ID, 기준월/계정 역할, 기대값/실제값, PASS/FAIL/미실행,
화면 캡처 또는 API 응답을 남긴다.
