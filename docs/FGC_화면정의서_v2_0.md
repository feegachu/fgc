# FGC 화면정의서 v2.0

**팀명 수수깡 · 프로젝트 FeeGaChu(FGC) · 작성 예소(PM) · 2026-08-03 배포**

> 이 문서 하나만 보고 화면을 만들 수 있게 썼습니다.
> 모르는 말이 나오면 **부록 B 용어 한 줄 사전**을 먼저 보세요.

## 0. 이 문서를 읽는 법 (5분)

### 0-1. 이 문서는 무엇인가

화면 하나하나에 대해 **무엇을 보여주고, 무엇을 입력받고, 무엇을 막는지**를 적은 문서입니다.

- 프론트엔드 담당은 이 문서로 화면을 만듭니다.
- 백엔드 담당은 이 문서로 API(화면이 서버를 부르는 주소)를 만듭니다.
- QA 담당은 이 문서의 "막아야 할 것"으로 테스트를 만듭니다.

### 0-2. 화면 하나는 이렇게 적혀 있습니다

| 칸 이름 | 무슨 뜻인가 |
|---|---|
| **이 화면은 무엇인가** | 화면의 목적. 두세 문장. |
| **화면 구성** | 위에서 아래로 어떤 영역이 있는지. ①②③ 순서. |
| **항목 정의** | 화면에 나오는 칸 하나하나의 이름·형식·필수 여부. |
| **주요 기능·버튼** | 버튼을 누르면 무슨 일이 일어나는지. |
| **막아야 할 것** | 사용자가 하면 안 되는 일. **여기가 이 프로젝트의 핵심입니다.** |
| **권한** | 어떤 역할이 보고, 어떤 역할이 처리하는지. |
| **데이터** | 어느 테이블을 읽고 쓰는지. API 주소 초안. |
| **관련 요구사항** | 요구사항명세서 ID(FUN-xxx)와 규제 근거(REG-xx). |
| **만들 때 주의** | 개발하면서 틀리기 쉬운 부분. |

### 0-3. 화면 ID 읽는 법

```
FGC-UI-CAP-W01
 │   │   │   └─ 화면 번호
 │   │   └───── 업무 구역 (CAP = 1,200% 한도)
 │   └───────── 화면(User Interface)
 └───────────── 프로젝트
```

### 0-4. v1.0에서 크게 바뀐 3가지

| # | 무엇이 | 왜 |
|---|---|---|
| 1 | **업로드 화면 3개를 완전히 삭제**(IMPORT-W01·W02·W03) | 원수사 데이터는 이미 정규화되어 DB에 있다는 전제로 바꿨습니다(COR-010). 파일 업로드·컬럼 매핑 기능은 만들지 않습니다. |
| 2 | **화면이 읽는 테이블 이름을 전부 교체** | 옛 이름 `TB_FGC_VCP` → 새 이름 `cap_check`. 스키마 v2.1.2 기준입니다. |
| 3 | **1차·2차 나누는 기준을 "규제 시행일"로 변경** | 1차 = 2026년에 이미 시행 중인 규제. 2차 = 2027년부터 시행되는 규제. |

## 1. FGC가 하는 일 (1분)

```
원수사 ──(돈)──> GA ──(돈)──> 설계사
                  │
                  └─ FGC는 이 돈의 흐름을 "검증"만 합니다.
                     송금은 하지 않습니다. (COR-001)
```

FGC가 하는 검증은 4가지입니다.

| # | 검증 | 한 줄 설명 | 릴리스 |
|---|---|---|---|
| 1 | **1,200%룰** | 계약 1건에 첫 1년 동안 준 돈이 월보험료의 12배를 넘었는가 | 1차 |
| 2 | **차익거래** | 준 수수료 + 해약환급금이 받은 보험료보다 많아졌는가 | 1차 |
| 3 | **원장·대사** | 줄 예정이던 돈과 실제로 준 돈이 딱 맞는가 | 1차 |
| 4 | **분급 한도** | 4년·7년에 나눠 주는 돈이 정해진 한도 안인가 | 2차 |

**그래서 화면의 목표는 하나입니다.**
"이 금액이 왜 이렇게 나왔는지"를 3초 안에 보여줄 것.

## 4. 전 화면 공통 규칙 (12개)

이 12개는 **모든 화면에 똑같이 적용**됩니다. 화면별 상세에서 다시 쓰지 않습니다.

| # | 규칙 | 구체적으로 |
|---|---|---|
| 1 | **금액 표기** | 원 단위, 천 단위 콤마. 소수점 없음. 음수는 빨강 + 괄호. 예: `(1,517,944)` |
| 2 | **반올림** | 화면에서 반올림하지 않습니다. 서버가 이미 원 단위 `HALF_UP`(0.5 이상 올림)으로 계산해서 보냅니다. 화면은 받은 숫자를 그대로 씁니다. |
| 3 | **요율 표기** | 소수점 넷째 자리까지. 예: `650.0000%`. 화면에서 반올림 금지. |
| 4 | **상태 배지** | 색만 쓰지 않고 **색 + 글자**를 같이 씁니다. 정상=초록, 주의=주황, 위반·차단=빨강, 검토필요=회색, 진행중=파랑. |
| 5 | **근거 표시** | 요율·한도·판정이 나오는 곳에는 마우스를 올리면 근거가 뜹니다. 예: `REG-08 · 제4-32조제11항`. 근거 없는 숫자는 화면에 띄우지 않습니다. |
| 6 | **계산근거 열기** | 금액을 클릭하면 `입력값 → 계산식 → 항목별 금액 → 합계` 순서의 팝업이 뜹니다. DB의 `calculation_snapshot`(계산 당시 값을 통째로 저장한 JSON)을 표로 풀어 보여줍니다. |
| 7 | **목록 공통** | 서버에서 20행씩 나눠 보냅니다. 검색조건은 주소창(URL)에 남깁니다. 정렬 화살표 표시. |
| 8 | **확정 후 잠금** | `FINALIZED`(확정) 된 검증 실행의 데이터는 전 화면에서 읽기 전용 + 자물쇠 아이콘. 고치려 하면 "새 실행을 만드세요" 안내창이 뜹니다. |
| 9 | **사유 필수** | 예외 처리·역분개·수동 조정은 **사유를 안 쓰면 저장 버튼이 눌리지 않습니다.** 저장하면 감사로그에 이전값·이후값이 자동으로 남습니다. |
| 10 | **에러 문구 3요소** | `무엇이 · 왜 · 어떻게`. 예: "지급 확정 불가 — 1,200% 한도 초과(사용률 104.2%). 예외함에서 정정·감액·취소를 선택하세요." |
| 11 | **개인정보** | **계약자 개인정보를 아예 저장하지 않습니다**(SRC-027 D-05). 계약 식별은 계약번호(`contract_no`)로 합니다. 이름·주민번호 모두 저장·표시·전송하지 않으므로 마스킹 규칙 자체가 필요 없습니다. |
| 12 | **교육용 표시** | 화면에는 표기하지 않는다 — 시연 사실감을 위한 팀 결정(2026-08-12, 근거대장 "COR-009 화면 표기 개정" 기록). 교육용 고지는 산출물 문서·README 수준으로 유지한다(COR-009) |

### 4-1. 역할 4종과 기본 권한

| 역할 코드 | 이름 | 할 수 있는 일 |
|---|---|---|
| `SYSTEM_ADMIN` | 시스템관리자 | 전부 |
| `GA_ADMIN` | GA관리자 | 정책·조직 조회, 검증 실행 확정 |
| `SETTLEMENT` | 정산담당자 | 계약·지급 건 등록, 검증 실행, 예외 처리 |
| `COMPLIANCE` | 준법·감사 | **조회만.** 모든 처리 버튼이 회색 |

> 표기 규칙: `SYSTEM_ADMIN`은 "전부"이므로 아래 개별 화면의 **권한** 줄(그리고 인터페이스정의서 §4-2 역할 열)에는 따로 적지 않는다. 예: "등록 버튼은 `SETTLEMENT`" = SETTLEMENT + SYSTEM_ADMIN.

시연용 계정: `admin` / `gaadmin` / `settle01` / `audit01` (비밀번호는 시드 스크립트 참고)

### FGC-UI-TRAN-W02 · 지급 건 등록·귀속·확정  ★핵심

| 메뉴경로 | 계약·지급 > 수수료 지급 건 > 등록 | 유형 | 입력 폼 + 하위 표 | 역할 | SETTLEMENT | 우선순위 | 필수 |

**이 화면은 무엇인가**
**이 프로젝트에서 가장 중요한 화면입니다.**

**확정 순서 (운영정책서 제31조 — 이 순서를 반드시 지킵니다)**

```
1. 작성중(DRAFT)으로 저장
2. "이 돈이 어느 계약 몫인가" 귀속행 입력
3. 귀속행 합계 = 지급액 인지 검사
4. 검토필요(REVIEW_REQUIRED) 귀속이 있는지 검사
5. 1,200% 사전검증
6. 전부 통과해야 확정(CONFIRMED)
```

**화면 구성**
① 지급 건 입력 영역
② 귀속행 표 (여러 줄 추가 가능)
③ 검증 결과 패널 — 한도 게이지 + 통과/차단
④ 버튼 영역 — 임시저장 / 확정

**항목 정의 — ① 지급 건**

| 항목 | 구분 | 필수 | 설명 |
|---|---|---|---|
| 지급단계 | 선택 | O | 원수사→GA / GA→설계사 |
| 원천유형 | 선택 | O | 수기지급이 기본 |
| 업무키 | 입력 | O | 중복 불가. 예: `GA-2026-07-0001` |
| 정산월 | 선택 | O | 매월 1일로 저장 |
| 수령 설계사 | 선택 | 조건부 | GA→설계사면 필수. **관리자수수료는 계약 모집설계사가 아니라 그 계약 조직 계층의 팀장·지사장·본부장을 지정합니다**(운영정책서 제20조). 서버가 계약일 기준으로 그 조직의 해당 직급 관리자인지 확인하며, 관리자 직급을 고르면 계약 목록을 모집설계사로 좁히지 않습니다 |
| 수수료 항목 | 선택 | O | `commission_item` |
| 금액 | 입력 | O | 0 이상 |
| 흐름 | 선택 | O | 지급 / 차감 |
| 증빙 | 입력 | 조건부 | 제외 항목이면 필수 |

- API: `POST /api/v1/transactions` (작성중 저장) / `POST /api/v1/transactions/{id}/confirm` (확정)

⑤ 확정 조건 체크리스트
⑥ [확정] 버튼

**항목 정의 — ① 실행 헤더 · ② 진행 단계**

| 항목 | 출처 | 비고 |
|---|---|---|
| 검증월 · 회차 | `validation_run.validation_month` · `run_no` | |
| 실행 상태 | `validation_run.status` | `CREATED`·`RUNNING`·`COMPLETED`·`FAILED`·`FINALIZED` **5개** |
| **진행 단계 (1~10)** | **`validation_run.current_step`** | ★ 아래 설명 |
| 진행률 % | `current_step / 10 × 100` | 화면에서 계산 |
| 실패 단계 | `status='FAILED'` 일 때의 `current_step` | 실패 사유는 `failure_message` |
| 단계 이름 | **DB 아님 — 화면 상수** | `화면_MVP/assets/fgc-seed.js` 의 `validationSteps` |
| 실행자 · 시작 · 완료 | `triggered_by` · `started_at` · `completed_at` | |
| 확정자 · 확정시각 | `finalized_by` · `finalized_at` | |

> **★ `status` 5개와 10단계는 서로 다른 축입니다.** 헷갈리기 쉬운 지점입니다.
> `status` 는 실행의 거친 생명주기이고, `current_step` 은 그 안에서의 진행 위치입니다.
> 둘의 관계는 DB 제약 `ck_validation_run_step` 이 강제합니다 —
> `CREATED`=0 / `RUNNING`·`FAILED`=0~8 / `COMPLETED`=8 / `FINALIZED`=10.
>
> **9단계(담당자 검토)에는 별도 값이 없습니다.** `COMPLETED` + `current_step=8` 이
> 곧 "배치 끝, 사람 검토 대기"입니다. 스텝퍼는 1~8 초록 / 9·10 회색으로 그려집니다.
>
> **진행률을 Spring Batch 메타테이블(`batch_step_execution`)에서 읽지 마세요.**
> Step 8개가 10단계와 1:1이 아니고(6단계=Step 2개, 4단계=partition 2개, 7단계=2회),
> 9·10단계는 Spring Batch 에 Step 자체가 없습니다. `validation_run` 에 `job_execution_id`
> 도 없어 조인할 키가 없습니다. 각 Step 이 `current_step` 을 갱신하고 화면은 그것만 읽습니다.

**⑤ 확정 조건 체크리스트 (운영정책서 제44조 — 6개 전부 초록이어야 확정 가능)**

> 제44조에는 항목이 7개 적혀 있지만 마지막 `확정 사용자와 시각 기록` 은 **사전조건이 아니라
> 확정의 사후효과**입니다(`finalized_by`·`finalized_at` 에 자동 기록). 게이트는 앞의 6개입니다.
> **이 목록·순서를 바꾸지 마세요** — 예전에 정책서·쿡북·이 문서가 서로 다른 6개를 갖고
> 있었습니다(SRC-027 감사). SQL 정본은 `08_화면별_SQL_쿡북_v1_0.md` IF-API-50 입니다.

화면에 표시하는 문구는 아래 그대로 씁니다. **쿡북 SQL 의 `label` · MVP 목업과 문자열이 같아야 합니다**(API 가 `conditions[].label` 로 그대로 내려보냅니다).

| # | 조건 (화면 표시 문구) | 확인 방법 |
|---|---|---|
| 1 | 검증 실행 상태가 계산완료(COMPLETED)인가 | `validation_run.status='COMPLETED' AND current_step=8` |
| 2 | 원장 불균형(차변≠대변)이 0건인가 | `vw_journal_imbalance` ⋈ `journal_header` **WHERE `validation_run_id`** |
| 3 | 심각도 긴급(CRITICAL) 미처리 예외가 0건인가 | `exception_case` — **`severity='CRITICAL'` 필터 필수** |
| 4 | 정책 없음 · 정책 중복이 0건인가 | `exception_case.exception_type IN ('POLICY_MISSING','POLICY_DUPLICATE')` |
| 5 | 귀속합계 오류가 0건인가 | `vw_transaction_attribution_balance` ⋈ `commission_transaction` **WHERE `settlement_month` = 검증월** |
| 6 | 계약별 상세 합계 = 실행 요약 합계인가 | `cap_check.included_amount` vs `SUM(cap_check_detail.amount WHERE INCLUDED)` |

> **2·5번은 반드시 실행 범위로 좁혀야 합니다.** 뷰를 그냥 세면 다른 실행의 불균형까지
> 세어 확정이 영영 막힙니다. 뷰에 `validation_run_id` 가 없어 부모 테이블로 되짚어야 하고,
> `commission_transaction` 에는 실행 연결이 아예 없어 정산월로 맞춥니다.

각 항목마다 "바로가기" 링크를 붙입니다. 실패하면 어디를 고쳐야 하는지 바로 알 수 있게요.

가장 헷갈리는 화면입니다. **계약체결비용은 나눠 쓰는 통장이 아닙니다.**

```
하지 마세요
계약체결비용 − 선지급 − 유지관리 = 남은 한도   ✗

이렇게 하세요 — 사용률 4개를 따로 계산합니다
선지급 총액   ÷ 계약체결비용                → 사용률 1
유지관리 월액 ÷ (계약체결비용 × 월 상한율)  → 사용률 2
유지관리 총액 ÷ 계약체결비용                → 사용률 3
장기유지 월액 ÷ (계약체결비용 × 0.4%)       → 사용률 4
```

네 한도는 각각 따로 봅니다. 서로 빼지 않습니다. 화면에도 게이지 4개를 나란히 놓습니다.

## 부록 A. 에러·안내 문구 표준

문구는 이 표에서 그대로 복사해 쓰세요. 사람마다 다르게 쓰면 QA가 힘들어집니다.

| 상황 | 문구 |
|---|---|
| 1,200% 초과로 확정 차단 | 지급 확정 불가 — 1,200% 한도 초과(사용률 {n}%). 예외함에서 정정·감액·취소를 선택하세요. |
| 귀속행 없음 | 지급 확정 불가 — 이 돈이 어느 계약 몫인지 먼저 입력하세요. |
| 귀속합계 불일치 | 지급 확정 불가 — 귀속금액 합계({a}원)가 지급액({b}원)과 다릅니다. 차액 {c}원. |
| 증빙 없는 제외 | 저장 불가 — "제외"를 선택하면 증빙을 입력해야 합니다. |
| 확정 스케줄 수정 시도 | 수정 불가 — 확정된 스케줄은 고칠 수 없습니다. [새 버전 만들기]를 누르세요. |
| 확정 스케줄 되돌리기 시도 | 되돌릴 수 없습니다 — 확정된 스케줄은 새 버전으로만 바꿉니다. |
| 원장 수정 시도 | 수정 불가 — 분개는 고치지 않습니다. [역분개]로 바로잡으세요. |
| 확정 조건 미충족 | 확정 불가 — {n}개 조건이 남았습니다. 아래 체크리스트를 확인하세요. |
| 확정된 실행 수정 시도 | 수정 불가 — 확정된 검증 결과입니다. 새 실행을 만드세요. |
| 계약번호 중복 | 저장 불가 — 이미 등록된 계약번호입니다. |
| 업무키 중복 | 저장 불가 — 이미 등록된 지급 건입니다. |
| 사유 미입력 | 저장 불가 — 처리 사유를 입력하세요. |
| 권한 없음 | 이 작업을 할 권한이 없습니다. |
| 조회 결과 없음 | 조건에 맞는 자료가 없습니다. 검색 조건을 바꿔 보세요. |
