# FGC 화면정의서 v2.0

**팀명 수수깡 · 프로젝트 FeeGaChu(FGC) · 작성 예소(PM) · 2026-08-03 배포**

> 이 문서 하나만 보고 화면을 만들 수 있게 썼습니다.
> 모르는 말이 나오면 **부록 B 용어 한 줄 사전**을 먼저 보세요.

## 0. 이 문서를 읽는 법 (5분)

### 0-1. 이 문서는 무엇인가

화면 하나하나에 대해 **무엇을 보여주고, 무엇을 입력받고, 무엇을 막는지**를 적은 문서입니다.

- 프론트엔드 담당은 이 문서로 화면을 만듭니다.
- 백엔드 담당은 이 문서로 API(화면이 서버를 부르는 주소)를 만듭니다.
- QA 담당은 이 문서의 "막아야 할 것"으로 테스트를 만듭니다.

### 0-2. 화면 하나는 이렇게 적혀 있습니다

| 칸 이름 | 무슨 뜻인가 |
|---|---|
| **이 화면은 무엇인가** | 화면의 목적. 두세 문장. |
| **화면 구성** | 위에서 아래로 어떤 영역이 있는지. ①②③ 순서. |
| **항목 정의** | 화면에 나오는 칸 하나하나의 이름·형식·필수 여부. |
| **주요 기능·버튼** | 버튼을 누르면 무슨 일이 일어나는지. |
| **막아야 할 것** | 사용자가 하면 안 되는 일. **여기가 이 프로젝트의 핵심입니다.** |
| **권한** | 어떤 역할이 보고, 어떤 역할이 처리하는지. |
| **데이터** | 어느 테이블을 읽고 쓰는지. API 주소 초안. |
| **관련 요구사항** | 요구사항명세서 ID(FUN-xxx)와 규제 근거(REG-xx). |
| **만들 때 주의** | 개발하면서 틀리기 쉬운 부분. |

### 0-3. 화면 ID 읽는 법

```
FGC-UI-CAP-W01
 │   │   │   └─ 화면 번호
 │   │   └───── 업무 구역 (CAP = 1,200% 한도)
 │   └───────── 화면(User Interface)
 └───────────── 프로젝트
```

### 0-4. v1.0에서 크게 바뀐 3가지

| # | 무엇이 | 왜 |
|---|---|---|
| 1 | **업로드 화면 3개를 완전히 삭제**(IMPORT-W01·W02·W03) | 원수사 데이터는 이미 정규화되어 DB에 있다는 전제로 바꿨습니다(COR-010). 파일 업로드·컬럼 매핑 기능은 만들지 않습니다. |
| 2 | **화면이 읽는 테이블 이름을 전부 교체** | 옛 이름 `TB_FGC_VCP` → 새 이름 `cap_check`. 스키마 v2.1.2 기준입니다. |
| 3 | **1차·2차 나누는 기준을 "규제 시행일"로 변경** | 1차 = 2026년에 이미 시행 중인 규제. 2차 = 2027년부터 시행되는 규제. |

## 1. FGC가 하는 일 (1분)

```
원수사 ──(돈)──> GA ──(돈)──> 설계사
                  │
                  └─ FGC는 이 돈의 흐름을 "검증"만 합니다.
                     송금은 하지 않습니다. (COR-001)
```

FGC가 하는 검증은 4가지입니다.

| # | 검증 | 한 줄 설명 | 릴리스 |
|---|---|---|---|
| 1 | **1,200%룰** | 계약 1건에 첫 1년 동안 준 돈이 월보험료의 12배를 넘었는가 | 1차 |
| 2 | **차익거래** | 준 수수료 + 해약환급금이 받은 보험료보다 많아졌는가 | 1차 |
| 3 | **원장·대사** | 줄 예정이던 돈과 실제로 준 돈이 딱 맞는가 | 1차 |
| 4 | **분급 한도** | 4년·7년에 나눠 주는 돈이 정해진 한도 안인가 | 2차 |

**그래서 화면의 목표는 하나입니다.**
"이 금액이 왜 이렇게 나왔는지"를 3초 안에 보여줄 것.

## 4. 전 화면 공통 규칙 (12개)

이 12개는 **모든 화면에 똑같이 적용**됩니다. 화면별 상세에서 다시 쓰지 않습니다.

| # | 규칙 | 구체적으로 |
|---|---|---|
| 1 | **금액 표기** | 원 단위, 천 단위 콤마. 소수점 없음. 음수는 빨강 + 괄호. 예: `(1,517,944)` |
| 2 | **반올림** | 화면에서 반올림하지 않습니다. 서버가 이미 원 단위 `HALF_UP`(0.5 이상 올림)으로 계산해서 보냅니다. 화면은 받은 숫자를 그대로 씁니다. |
| 3 | **요율 표기** | 소수점 넷째 자리까지. 예: `650.0000%`. 화면에서 반올림 금지. |
| 4 | **상태 배지** | 색만 쓰지 않고 **색 + 글자**를 같이 씁니다. 정상=초록, 주의=주황, 위반·차단=빨강, 검토필요=회색, 진행중=파랑. |
| 5 | **근거 표시** | 요율·한도·판정이 나오는 곳에는 마우스를 올리면 근거가 뜹니다. 예: `REG-08 · 제4-32조제11항`. 근거 없는 숫자는 화면에 띄우지 않습니다. 판정식·계산식 근거는 해당 값 옆 툴팁으로 제공하며 화면 상단 배너로 두지 않습니다(2026-08-21 팀 결정, 근거대장 "화면 설명문 표기 개정" 기록). |

**React 표 컬럼별 오름차순·내림차순 정렬 (#604)** — 목록 표의 정렬 가능한 컬럼 머리글을 누르면 그 컬럼 기준 오름차순(↑) → 내림차순(↓)으로 번갈아 바뀝니다. 정렬 가능한 컬럼은 머리글 오른쪽에 `↕`가 보이고, 현재 정렬 중인 컬럼은 방향 화살표로 바뀌며 `aria-sort`(ascending·descending)를 제공합니다. 머리글은 버튼이라 Tab으로 이동해 Enter·Space로 바꿀 수 있고, 머리글 옆 도움말 버튼과는 분리되어 서로 영향을 주지 않습니다.
- **서버 전체 기준** — 페이지가 나뉜 목록은 현재 페이지가 아니라 검색된 전체 데이터를 서버가 정렬한 뒤 해당 페이지를 보냅니다. 정렬을 바꾸면 **첫 페이지로 이동**하고 검색 조건(정산월 포함)은 그대로 유지합니다. 정렬은 주소창 `sort=컬럼,asc|desc`에 남기며, 검색을 다시 조회해도 유지하고 [초기화]에서는 서버 기본 정렬로 돌아갑니다. 허용되지 않은 값은 무시하고 기본 정렬을 씁니다.
- **값·동률 규칙** — 금액·건수·ID·날짜는 표시 문자열이 아니라 실제 값으로 비교합니다. 값이 비어 있는 행은 오름·내림 어느 쪽에서도 맨 뒤에 둡니다. 값이 같은 행은 각 목록의 기존 기본 순서(최신순 등)로 고정해 같은 요청은 항상 같은 순서가 됩니다.
- **정렬 가능한 컬럼** — 금액(보험료·지급액·예상액·실제액·차액·한도·산입금액·잔여)·ID·계약번호·이름·보험회사·상품명·날짜·발생시각·건수·사용률은 정렬합니다. 지급단계·상태·판정·유형·원천·출처·사유처럼 **비교 기준이 정해지지 않은 코드·표시 전용 컬럼과 작업·링크 컬럼은 정렬하지 않습니다**(상태 순서를 정의하는 것은 별도 결정 사항이며, 예외함의 심각도만 `치명 > 높음 > 경고 > 그 밖` 순으로 정렬합니다). 대사 실행 이력과 결과 목록은 서로 독립이라 각자 `sort`·`resultSort`를 가지며, 한쪽 정렬이 다른 쪽 페이지·정렬을 바꾸지 않습니다. 기준정보는 탭마다 정렬을 따로 기억합니다.
- **적용 목록과 허용 컬럼** — 계약(CONT-W01), 예상 스케줄(SCHE-W01), 수수료 지급 건(TRAN-W01), 한도 검증(CAP-W01 계약별 판정), 검증원장(LEDG-W01), 대사 실행 이력·결과(RECO-W01), 예외함(EXCP-W01), 감사로그(AUDT-W01), 월 통합검증(VRUN-W01), 차익거래(ARB-W01), 기준정보 조직·보험회사·상품·설계사(BASE-W01). 컬럼별 허용 key는 인터페이스정의서 §2-3A에 있습니다. 수수료 항목 탭은 한 번에 전체를 보여 주는 목록이라 이번 범위에서 제외합니다. 1차 Thymeleaf 화면은 정렬 화살표를 제공하지 않습니다.

**React 표 컬럼 정렬 (#597)** — 태그(상태·유형·판정·사용 여부 등)로 표시하는 컬럼은 머리글과 값을 가운데 정렬합니다. 금액 컬럼은 오른쪽 정렬하며, 그 외 텍스트·날짜·번호·회차·건수·버전·비율·배수와 일반 링크·작업 버튼 컬럼은 왼쪽 정렬합니다.

**React 표 너비 조절 (#597)** — 공통 표의 헤더 오른쪽 경계를 드래그하여 컬럼 너비를 조절합니다(일반 컬럼 64~1,200px). 태그 컬럼의 최소 너비는 현재 페이지에서 가장 긴 태그와 헤더가 좌우 여백을 포함해 들어가는 너비로 계산합니다. 저장된 너비가 이 최소값보다 작으면 표시 시 보정하며, 조회 결과나 글꼴 크기가 바뀌면 다시 계산합니다. 컬럼 너비 합계가 카드보다 좁으면 마지막 컬럼이 남은 공간을 채우며, 앞쪽 컬럼은 지정한 너비를 유지합니다. 마지막 컬럼의 자동 확장은 1,200px을 초과할 수 있습니다. 표가 카드보다 넓어지면 카드 안에서 가로 스크롤합니다. 손잡이에 초점을 두고 좌우 방향키로 16px씩, Shift와 함께 누르면 80px씩 조절할 수 있습니다. 손잡이를 두 번 클릭하거나 Home을 누르면 해당 표 전체의 기본 컬럼 너비로 복원합니다. 조절값은 화면·표·컬럼 구성별로 브라우저에 저장하며, 정렬·페이지 이동·새로고침 후에도 유지합니다. 브라우저 저장을 사용할 수 없어도 현재 화면의 조절은 동작합니다. 셀의 전체 보기·접기 버튼은 제거하며, 원문과 링크는 유지하고 컬럼 너비를 늘려 확인합니다. API·업무 데이터는 변경하지 않습니다.

**React 좌우 카드 너비 조절 (#597)** — 예외함(예외 목록 / 검출·처리 이력), 검증원장 조회(분개 목록 / 분개 상세), 차익거래 검증(계약별 판정 / 상세), 수수료 지급(지급 건·귀속행 / 확정 게이트 6단계·한도 미리보기·실행), 감사로그 조회(감사 기록 / 변경 내용 비교)에 적용합니다. 카드 사이 세로 구분선을 드래그하여 좌우 너비를 배분하며 화면별 비율을 브라우저에 저장합니다. 기본 왼쪽 비율은 각각 60%, 55%, 56%, 61%, 60%입니다. 조절 범위는 25~75%, 각 영역 최소 너비는 16rem이며, 좌우 방향키로 2%p(Shift와 함께 10%p)씩 조절합니다. 두 번 클릭 또는 Home으로 해당 화면의 기본 비율을 복원하고, 1,024px 미만에서는 세로 배치합니다.

### FGC-UI-CAP-W01 · 1,200% 한도 검증 현황  ★핵심

| 메뉴경로 | 규제 검증 > 1,200% 한도 | 유형 | 목록·게이지 | 역할 | 전체 조회 | 우선순위 | 필수 |
|---|---|---|---|---|---|---|---|

**이 화면은 무엇인가**
계약 1건이 첫 1년 동안 받은 돈이 한도를 넘었는지 보여줍니다.

```
규정 판정식: 산입금액 + 12차월 예상 해약환급금 − 준법경영비 공제 ≤ 월납환산 초회보험료 × 12

한도 = 월납환산 초회보험료 × 12
       (− 대상 상품이면 12차월 예상 해약환급금)
       (+ 준법경영비 공제 : 원수사→GA 게이지에만)
       (0 미만이면 0)

산입금액 = 지급 합계(산입 대상)

사용률 = 산입금액 ÷ 한도 × 100

주의   = 1,200% 예산 (산입금액 + 해약환급금 − 준법경영비 공제) ÷ (월납환산 초회보험료 × 12) ≥ 90%
         해약환급금 대상이면 사용률 90%보다 앞에서 켜진다 — 게이지 주의 표시선도 그 위치 (운영정책서 제30조, #490)
```

해약환급금은 수수료등에 합산하고(SRC-022 제4-32조⑤ "합산한다", SRC-025 FAQ 2차 Q1-1) 준법경영비는 수수료등 계산에서 제외한다(SRC-022 ⑭ "제외할 수 있다", REG-08·10). 화면·저장값은 이 판정식을 **한도 쪽으로 옮긴 형태**라 판정 결과는 같고, 산입금액은 ③ 상세 합계와 그대로 일치한다. 예: 월납 100,000원·해약환급금 288,000원이면 한도 912,000원, 준법경영비 증빙 3,000원이면 한도 1,203,000원. (2026-10-11 정정: 이전 판은 해약환급금을 한도에 더하고 준법경영비를 한도에서 뺐다. 구현 수정 #468)

**꼭 알아야 할 것: 게이지는 2개입니다**

| 게이지 | 뜻 | 준법경영비 3% 공제 |
|---|---|---|
| 원수사 → GA | 보험사가 GA에 준 돈 | **적용함** |
| GA → 설계사 | GA가 설계사에게 준 돈 | **적용 안 함** |

두 게이지를 절대 합치지 마세요. 따로 계산하고 따로 보여줍니다.

**화면 구성**

- **보장하는 것**: ① 같은 항목의 행이 한데 모인다 ② 항목 안에서는 계약월차 순이다 ③ 같은 환경에서 같은 입력을 다시 계산하면 순번이 같다(#501).
- **보장하지 않는 것**: 항목 **사이**의 순서. 업무 규칙이 아닙니다 — 공식 규정·FAQ, 협회 설명회(SRC-035), 언론, 회사 영업규정(SRC-019·020) 어디에도 표시 순서가 없어 정하지 않습니다. `commission_item_id`는 항목 등록 순서로 매겨지는 PK라 환경마다 다를 수 있고, 위 예시 순서(FC 기본 → 팀장 → … )는 설명용입니다.
- 항목을 모은 이유: "수수료 등" 범위가 비용 항목 단위로 정해지고(SRC-035, REG-09) 산입·제외 판정이 룰셋의 **항목 단위**이므로(FUN-013, REG-11) 판정과 항목별 금액을 한눈에 대조할 수 있습니다(FUN-035 "항목별 귀속금액").
- 월차·월별 누계 열을 두지 않는 이유: 실무 요구는 "1150~1200% 근접 계약을 고위험군으로 분류해 매월 모니터링"(SRC-035)하는 **계약 단위 월 점검**입니다. 이는 월 검증 실행(`MONTHLY`)의 계약별 판정과 주의 90%(운영정책서 제30조)가 맡고, "한 차례라도 초과하면 위반"(SRC-025 Q1-1)은 지급확정 게이트(제31조)가 막습니다. 판정 근거 팝업에 월별 누계 열을 요구하는 자료는 없습니다.

**막아야 할 것**

② 검색 — 유형, 상세 원인, 심각도, 상태, 담당자(미배정 포함), 검증월, 계약번호

**상태 흐름**

```
신규(NEW) → 검토중(IN_REVIEW) → 해결(RESOLVED)
                              → 오탐·반려(REJECTED)
오탐·반려(REJECTED) → 재검토(REOPEN) → 검토중(IN_REVIEW)
```

`REOPEN`은 오탐·반려 오조작 또는 추가 증빙이 확인된 경우에만 사유를 필수로 입력해 수행한다.
원장 정정이 끝난 `RESOLVED`는 기존 원분개에 대한 중복 역분개를 막기 위해 직접 재오픈하지 않고,
추가 정정이 필요하면 직전 재기표 분개를 대상으로 새 정정 예외를 생성한다.

(#331 추가) 「참조」와 별개로, CAP 계열 예외에는 **「1,200% 계산근거 열기」** 버튼을 둡니다 — `/cap-checks?capCheckId={id}` 로 CAP-W02 팝업을 바로 엽니다. `CAP_CHECK` 를 「참조」 목록에 넣지 않는 이유는 같은 목적지 버튼이 두 개가 되기 때문입니다. 실시간 확정 경로(FUN-034)는 `exception_case.cap_check_id` 를, 배치 경로는 `source_entity` 를 쓰며 컬럼이 우선합니다.

**이 버튼이 필요한 이유** — 확정이 거절된 DRAFT 후보의 `cap_check` 은 CAP-W01 과 CONT-W02 「1,200%」 탭 목록에서 제외됩니다(거절된 후보가 계약의 현재 판정을 덮지 않게 하려는 것). 그래서 그 판정의 계산근거에 도달할 수 있는 곳은 예외함뿐입니다. IF-API-31 은 제외 조건이 없어 팝업 자체는 정상 동작하므로, CAP-W01 목록이 0건이어도 이 링크로는 계산근거가 열립니다.

### FGC-UI-VRUN-W02 · 월 통합검증 상세·확정  ★핵심

| 메뉴경로 | 월 통합검증 > 상세 | 유형 | 단계형 상세 | 역할 | 전체 조회 | 우선순위 | 필수 |
|---|---|---|---|---|---|---|---|

**이 화면은 무엇인가**
검증 10단계가 어디까지 갔는지 보여주고, 마지막에 결과를 **확정(잠금)** 합니다.

**검증 순서 10단계 (운영정책서 제43조)**

```
1. 대상월 실행 생성
2. 계약·상품버전·환급률표 선별
3. 현행 예상 스케줄 생성·재검증
4. 지급단계별 1,200% 검증
5. 차익거래 검증
6. 검증원장 기표·균형검사
7. 양방향 대사
8. 예외 생성
9. 담당자 검토
10. 확정(FINALIZED)
```

**화면 구성**
① 실행 헤더 — 검증월, 회차, 상태, 실행자
② 진행 단계 표시 — 10단계를 가로 스텝퍼로. 완료=초록, 진행중=파랑, 실패=빨강
③ 대상 선별 결과 — 선정 / 제외 / 검토필요 건수 (`validation_target`)
④ 결과 요약 4블록 — 1,200% / 차익거래 / 원장 / 대사
④-1 예외 생성 결과 — 이번 실행 검출 / 신규 / 재검출 / 재발 / 미검출 / 미처리 업무건
   (SRC-032 2026-08-18 추가: 실행별 검출과 관리자 업무건을 구분해 보여준다. 예외함 열기
   링크는 검증월 필터로 연결)
   확정된 달의 재검증 실행이면 아래에 "확정 실행 #N과 1,200% 판정·한도액이 다른 건 K건"과
   확정 실행 링크, 예외함 바로가기(유형 `CAP_REVIEW_REQUIRED`·상세 원인 `FINALIZED_RESULT_DIFF`·검증월)를
   보인다. 비교 기준(이 실행보다 먼저 확정된 같은 달 실행)이 없으면 이 줄은 보이지 않는다
   (#498, FUN-044 "이전 결과와 비교", 운영정책서 제44조)
⑤ 확정 조건 체크리스트
⑥ [확정] 버튼

**항목 정의 — ① 실행 헤더 · ② 진행 단계**

| 항목 | 출처 | 비고 |
|---|---|---|
| 검증월 · 회차 | `validation_run.validation_month` · `run_no` | |
| 실행 상태 | `validation_run.status` | `CREATED`·`RUNNING`·`COMPLETED`·`FAILED`·`FINALIZED` **5개** |
| **진행 단계 (1~10)** | **`validation_run.current_step`** | ★ 아래 설명 |
| 진행률 % | `current_step / 10 × 100` | 화면에서 계산 |
| 실패 단계 | `status='FAILED'` 일 때의 `current_step` | 실패 사유는 `failure_message` |
| 단계 이름 | **DB 아님 — 화면 상수** | `화면_MVP/assets/fgc-seed.js` 의 `validationSteps` |
| 실행자 · 시작 · 완료 | `triggered_by` · `started_at` · `completed_at` | |
| 확정자 · 확정시각 | `finalized_by` · `finalized_at` | |

> **★ `status` 5개와 10단계는 서로 다른 축입니다.** 헷갈리기 쉬운 지점입니다.
> `status` 는 실행의 거친 생명주기이고, `current_step` 은 그 안에서의 진행 위치입니다.
> 둘의 관계는 DB 제약 `ck_validation_run_step` 이 강제합니다 —
> `CREATED`=0 / `RUNNING`·`FAILED`=0~8 / `COMPLETED`=8 / `FINALIZED`=10.
>
> **9단계(담당자 검토)에는 별도 값이 없습니다.** `COMPLETED` + `current_step=8` 이
> 곧 "배치 끝, 사람 검토 대기"입니다. 스텝퍼는 1~8 초록 / 9·10 회색으로 그려집니다.
>
> **진행률을 Spring Batch 메타테이블(`batch_step_execution`)에서 읽지 마세요.**
> Step 8개가 10단계와 1:1이 아니고(6단계=Step 2개, 4단계=partition 2개, 7단계=2회),
> 9·10단계는 Spring Batch 에 Step 자체가 없습니다. `validation_run` 에 `job_execution_id`
> 도 없어 조인할 키가 없습니다. 각 Step 이 `current_step` 을 갱신하고 화면은 그것만 읽습니다.

**⑤ 확정 조건 체크리스트 (운영정책서 제44조 — 8개 전부 초록이어야 확정 가능)**

> 제44조에는 항목이 10개 적혀 있지만 `확정할 수 있는 실행 유형` 은 체크리스트가 아니라 **사전조건**(계약수동 실행은
> 체크리스트 대신 "확정 대상 아님")이고, 마지막 `확정 사용자와 시각 기록` 은 **확정의 사후효과**입니다
> (`finalized_by`·`finalized_at` 에 자동 기록). 게이트는 앞의 8개입니다.
> **이 목록·순서를 바꾸지 마세요** — 예전에 정책서·쿡북·이 문서가 서로 다른 6개를 갖고
> 있었습니다(SRC-027 감사). SQL 정본은 `08_화면별_SQL_쿡북_v1_0.md` IF-API-50 입니다.

화면에 표시하는 문구는 아래 그대로 씁니다. **쿡북 SQL 의 `label` · MVP 목업과 문자열이 같아야 합니다**(API 가 `conditions[].label` 로 그대로 내려보냅니다).

| # | 조건 (화면 표시 문구) | 확인 방법 |
|---|---|---|
| 1 | 검증 실행 상태가 계산완료(COMPLETED)인가 | `validation_run.status='COMPLETED' AND current_step=8` |
| 2 | 원장 불균형(차변≠대변)이 0건인가 | `vw_journal_imbalance` ⋈ `journal_header` **WHERE `validation_run_id`** |

| 5 | 귀속합계 오류가 0건인가 | `vw_transaction_attribution_balance` ⋈ `commission_transaction` **WHERE `settlement_month` = 검증월** |

**1차 지표 이관 — 제거 대상 없음** (FUN-057·080, SRC-054·032)

아래 6개 지표는 모두 ③에 유지한다. 검증 결과 5개는 IF-API-03의 기존 집계 범위·조건을 그대로 쓰고, 미처리 예외만 IF-API-69로 조회한다. 같은 기준 정산월과 각 상세 화면의 조회 범위로 세며, 검증 결과를 `exception_case`의 존재 여부나 `NEW`·`IN_REVIEW` 상태로 제한하지 않는다. 예외가 없거나 해결·반려돼도 원천 결과가 조건에 맞으면 포함한다. 검증 결과와 미처리 업무건은 단위가 다르고 서로 겹칠 수 있으므로 합산하지 않는다.

**주요 기능·버튼**

| 버튼 | 하는 일 |
|---|---|
| 칸 수정 | 값을 고치면 수정 전·후·수정자를 남기고 그 행의 사전검증을 다시 한다 |
| 행 제외 | 남은 행을 사유와 함께 '제외'로 마감한다(확정된 행은 제외 불가). 모든 행이 확정·제외되면 문서가 '확정'이 된다(FUN-069) |
| 매칭 후보 고르기 | 확인 필요 행에서 계약·설계사 후보를 검색형 선택(CMN-C02)으로 고른다 |
| 사전검증 다시 실행 | 최신 DB 기준으로 전체 행을 다시 검사 |

| 거절 | 사유 필수, 업무 데이터 변화 없음. 한 행이라도 확정된 문서는 거절·재추출할 수 없고 남은 행 제외로 마감한다(`FGC-INTK-009`) |

**막아야 할 것**
- '확인 필요'·'오류' 행을 확정하기 → 일괄 확정 대상에서 빠진다.
- AI가 뽑은 금액을 서버 검증 없이 확정하기 → 확정 API가 기존 저장 경로(지급 건·환급률표·정책)로만 반영한다(COR-007).
- 확정 버튼을 두 번 눌러 두 번 반영되기 → Idempotency-Key, 같은 원본 행은 업무키로 한 번만(SAR-001). 같은 키로 다른 내용을 보내면 거절(`FGC-INTK-008`).
- 부분 확정 뒤 남은 행을 다시 확정하면서 앞서 확정한 행을 또 만들기 → 행 상태로 막는다(FUN-069).
- 부분 확정 문서를 통째로 거절·재추출해 이미 반영한 행을 취소하거나 두 번 반영하기 → 막는다(`FGC-INTK-009`).
- 차감·환수 행이나 검증 실행에 선정되지 않은 계약의 원천을 '검증 완료'로 보이기 → '후속 검증 대기'·'검증 실행 미선정'으로 따로 표시한다(FUN-068).
- 정정 명세를 원본과 둘 다 유효한 원천으로 넣어 금액을 두 번 세기 → 전체 대체본만 받고 이전 묶음을 SUPERSEDED로 바꾼다. 정정 유형·대체 대상을 담당자가 지정하지 않으면 확정 불가(`FGC-INTK-010`).
- 전체 대체본을 일부 행만 확정하거나 행을 제외해 전환하기 → 막는다(`FGC-INTK-012`). 모든 행을 검토한 뒤 [일괄 확정] 한 번으로 전환하고, 중간에 실패하면 전부 원복되어 이전 명세가 그대로 유효하다(r19).
- 이미 마감(FINALIZED)된 검증 실행에 반영된 명세를 정정하기 → 이번 버전에서는 지원하지 않는다. 확정을 막고 검토 대기로 남긴다(`FGC-INTK-011`). 화면에 '정정 완료'로 보이지 않게 한다.
- 36개 차월 중 하나라도 빠진 환급률표 확정 → 확정 불가(FUN-067).
- 정산데이터 행을 1,200% 사전검증·계약 상태로 걸러 버리기 → **하지 않는다.** 한도 초과·해지 후 지급·중복·모집자 불일치는 보험사가 이미 보낸 사실이라 그대로 적재하고, 기존 대사(RECO-W01)·예외함(EXCP-W01)이 판정한다(FUN-068). 걸러 버리면 대사로 찾아야 할 이상이 사라진다.
- 환급률표를 확정하자마자 차익거래 계산에 쓰기 → DRAFT까지만. 승인·활성화(작성자≠승인자) 전에는 쓰지 않는다(FUN-067, SRC-049).
- 정산담당자가 정책·등급 자료를 확정하기 → GA_ADMIN만.
- 증권 이미지에서 계약자 이름·주민번호 등을 화면·DB·로그에 남기기 → 추출 스키마에 그 칸이 없다(D-05). 다만 원본 이미지에는 남으므로 2차 MVP는 합성 양식만 받는다(FUN-071).

**권한** SETTLEMENT: 해약환급률표·정산데이터·증권 확정 / GA_ADMIN: 전부 / COMPLIANCE: 조회.

엑셀은 AI 없이 열 위치 규칙으로 읽을 수 있는 것은 그렇게 읽는다(SRC-058). xlsx·csv의 행과 금액은 결정론 파서로 보존하고 AI는 열 의미 판별에만 쓴다(SRC-057). 원본 행 위치(쪽·시트·행)를 적재된 원천 명세 행의 증빙에 남겨, 나중에 수수료 영수증(CMN-C03)에서 원본까지 거슬러 올라갈 수 있게 한다.

### FGC-UI-CMPR-W01 · 대형 GA 비교설명

| 메뉴경로 | 규제 검증 > 대형 GA 비교설명 | 유형 | 비교 표·작성 | 역할 | AGENT 작성, GA_ADMIN·COMPLIANCE 조회 | 우선순위 | 필수 |
|---|---|---|---|---|---|---|---|

**이 화면은 무엇인가**
설계사가 고객에게 상품을 권하기 전에, 감독규정 별표 5의6 제5호가 요구하는 비교·설명을 준비하는 화면이다(설계사 500명 이상 대형 GA — 가상 GA는 600명, OI-024). 다른 보험회사의 같은 종류 상품 3개 이상을 수수료 등급·순위와 함께 비교하고, 추천사유를 쓰고, 비교·설명 확인서를 PDF로 만든다. **어느 상품을 팔지는 설계사와 고객이 정한다. FGC는 추천을 확정하지 않는다.**

**화면 구성**
① 상품군 고르기 — 업권·대분류·중분류(2차 FAQ Q17 분류표), 심사방식(간편·일반), 해약환급금 유형(일반·순수보장·만기환급·무해지·저해지), 권유 상품
② 비교 표 — 보험사 · 상품명 · 주요 보장(가상 상품 데이터) · 보험료(가상) · 수수료 등급(5단계 배지) · 순위 · 자료 기준일
③ 권유 가능한 보험회사 전체 목록 — 계약자가 고른 상품을 비교 표에 추가(고른 상품이 있으면 포함 여부를 검사)
④ 설명 항목 — 상품 선정 기준 · 추천사유([AI 초안] 버튼, 금지 표현 검사 결과 표시, 설계사가 직접 고쳐 저장) · 수수료등 수준(제5호 다목)
⑤ [비교설명 저장] — 비교 상품·계약자 선택 상품·선정 기준·추천사유·수수료 수준·자료 기준일을 서버 초안으로 저장(판 번호, IF-API-66A) → ⑥ [확인서 PDF 만들기] — 저장된 초안의 같은 판으로 서버가 검사·생성 → ⑦ [확인서 수령 확인] — PDF 판마다 기록(새 판을 만들어도 이전 판 수령 이력 유지, r19) — 수령일·확인자·서명본 보관 위치 기록. PDF 생성만으로는 '수령 미확인'

**항목 정의**

| 항목 | 형식 | 설명 |
|---|---|---|
| 수수료 등급 | 배지(5단계) | 매우높음(유사상품 평균의 130% 초과) / 높음(110~130%) / 보통(90~110%) / 낮음(70~90%) / 매우낮음(70% 이하) — SRC-002. **협회 자료 값만 표시** |

| 자체 계산 등급 | 회색 작은 글씨 | FGC가 계산한 검증용 값. 협회 값과 다르면 "차이 있음" 표시(OI-025) |

**주요 기능·버튼**

| 버튼 | 하는 일 |
|---|---|

| AI 초안 | 비교 표 값만 근거로 추천사유 초안을 만든다. 금지 표현 검사를 통과한 초안만 보여준다 |

| 확인서 수령 확인 | 고객이 서명한 확인서를 받았음을 기록(수령일·확인자·서명본 보관 위치). 고객 이름·서명 이미지는 저장하지 않는다(D-05). 이후 상태 '확인서 수령' |

**막아야 할 것**
- 다른 보험회사 상품이 3개 미만인데 확인서 만들기 → 막고 판매 제한을 안내한다(제5호 가목, Q18). '업권 전체 동종·유사 상품 2개 이하' 예외는 **우리 DB 건수로 판단하지 않고**, 협회 자료 등 증빙과 확인자(GA_ADMIN) 기록이 있을 때만 연다.
- 계약자가 고른 상품이 비교 표에서 빠진 채 확인서 만들기 → 막는다(제5호 나목, `FGC-CMPR-003`).
- PDF를 만든 것을 확인서 수령으로 보기 → 수령 확인을 따로 기록해야 '확인서 수령'이 된다.
- 같은 회사 상품끼리만 비교 → 비교 대상은 다른 보험회사 상품이다.
- 수수료 등급·순위를 화면에서 고치거나 AI가 바꾸기 → 읽기 전용.
- 보장성 상품을 '환급금'만으로 추천하는 사유 저장 → 금지 표현 검사로 막는다(Q24).
- 고객 이름·연락처 입력칸 두기 → 두지 않는다(D-05). 서명은 출력물에 직접.
- 제외 대상을 넓게 잡기 → 원문 조건 그대로만 뺀다(제5호 단서): 기업성 보험(계약자가 개인이 아닌 일반손해보험, Q21) / 자동차보험은 보험협회 보험료 비교·공시 조회 결과를 계약자가 확인할 수 있도록 한 경우만(확인 여부를 기록) / 간단보험은 **간단보험대리점이 간단보험을 모집하는 경우만**(Q22 — FGC 가상 GA는 간단보험대리점이 아니므로 해당 없음). '간단보험 상품'이라는 이유만으로 빼지 않는다.

**권한** AGENT(본인 작성분), GA_ADMIN·COMPLIANCE 조회.

## #482 시행 전 계약의 1,200% 적용대상 판정

`NOT_APPLICABLE`은 시행 전 계약으로 계산 대상이 아닌 결과다. 원수사→GA는 2021-01-01, GA→설계사는 2026-07-01 계약일부터 적용한다. CAP 목록/계약 한도 탭/계산근거에서 조회할 수 있으며 계산 금액·사용률·룰셋 ID는 null(화면 —)이다. 정상 건수 및 금액 모니터링에는 포함하지 않는다. 계산근거 `calculationSnapshot.applicability`에 계약일·시행 기준일·사유 코드·문구·기준 버전을 보존한다. 사전검증은 applicabilityReasonCode/applicabilityReason을 반환하고 저장하지 않는다. 지급확정은 판정과 후보 귀속 사유를 저장한다. 자세한 결정은 `FGC_482_적용대상판정_설계.md`를 따른다.
