# #478 1,200% 지급 누계와 환수 분리

## 변경 전/후

기존 CAP 집계는 확정 환수를 음수로 더해 지급 한도를 복원했다. 현재 환수 후보도 CAP 검사에 들어가 한도 초과 또는 스케줄 검토필요 때문에 회수를 막을 수 있었다.

CAP 지급 누계·기존 확정 상세·지급 전 집계는 PAYMENT만 행별 원 단위 HALF_UP으로 합산한다. 기존 날짜 경계(계약일 이상, 1주년 미만), 지급단계·확정 상태·산입 스냅샷 조건은 유지한다. CAP 준법경영비 증빙액 조회도 PAYMENT만 합산한다. 환수는 CAP 산입을 늘리지도 줄이지도 않는다.

환수의 사전검증/확정은 CAP 룰·스케줄·미해결 CAP 위반 게이트만 건너뛴다. 귀속 합계·귀속계약·계약일 전 귀속·검토필요·배부 근거·제외 증빙·정책 참조·권한·DRAFT 상태·계약 잠금·멱등 키·감사 기록 검사는 유지한다. CAP 체크 ID는 빈 목록으로 반환한다. 기존 환수에 잘못 생성된 CAP 위반 예외는 자동 삭제하지 않으며, 정식 예외 처리 워크플로로 정리해야 한다.

차익거래의 PAYMENT−DEDUCTION 순액은 수정하지 않았다. 비교용 JDBC SQL/서비스에도 이번 지급 gross 기준만 반영했다.

## 핵심 회귀 시나리오

월납 100,000원, 일반 상품 한도 1,200,000원:

1. 지급 900,000원 확정: CAP 누계 900,000원.
2. 환수 300,000원 확정: CAP 체크 생성 없음, CAP 지급 누계 여전히 900,000원. 같은 멱등 키 재시도는 같은 결과.
3. 추가 지급 600,000원: 누계 1,500,000원, VIOLATION, 사전검증 불가 및 실제 확정 거절. 지급은 DRAFT 유지.
4. 차익거래 조회: 확정 지급 900,000원, 확정 환수 300,000원, 순액 600,000원 유지.
5. 확정 거절 계산근거 상세 합계도 1,500,000원이며 환수 음수 행을 포함하지 않는다.

통합 테스트는 신규 합성 계약을 롤백 트랜잭션 안에서 만들며 운영/개발 DB를 사용하지 않는다. 환수의 REVIEW_REQUIRED 귀속은 여전히 차단되는 단위 테스트도 추가했다.

## 정책·배포 영향

V46은 데모 전용으로 ACTIVE CAP 정책별 새 버전을 DRAFT 상태에서 복제하고 CLAWBACK 설명만 정정한 후 작성자/승인자 분리하여 APPROVED→ACTIVE로 승격한다. 이전 버전은 정식 RETIRED 처리한다. 기존 정책 자식·귀속 스냅샷·cap_check 이력은 보존한다. CLAWBACK의 과거 분류값은 이력 호환을 위해 유지하지만, 현금흐름 구분이 PAYMENT가 아니면 CAP 검사에 사용하지 않는다.

운영의 승인된 정책 설명은 담당자가 새 버전으로 정정해야 한다. 데모 파일을 운영 승인으로 간주하지 않는다. 기존 결과와 예외는 자동 덮어쓰지 않으며 정상 재검증/예외 처리로 정리한다. 확정월은 당시 이력을 보존한다. 이전 코드로 되돌리면 순액 우회가 재발하므로 배포 롤백 시 지급 확정을 중지하고 후속 정책 결정을 해야 한다.

관련 요구사항: FUN-030·FUN-033, 이슈에 정리된 REG-08·REG-22 및 SRC-025 Q1-1·Q4·Q11. #468의 한도식과 #490의 잔여액 기준 주의 판정은 유지한다.

검증 명령: `gradlew.bat clean build`, 도메인 선택은 `gradlew.bat test --tests '*Cap*' --tests '*CommissionPayment*' --tests '*Arbitrage*'`. Spring Boot 서버·API·권한·잠금/동시 요청·재시도·거절 시 롤백 회귀를 일회성 PostgreSQL로 검증한다.
