# FGC AI 업무 비서 — 설계 방법과 구현 순서

- 작성일: 2026-10-28
- 상태: 1~2단계 명세와 3단계 계약 기반·공통 챗봇 표시 UI·현재 지급 화면의 로컬 가이드 실행기를 부분 구현했다. 15~17장은 구현 기준이다. 4단계 서버 계산 조회 1차 구현은 23장에 기록했다. 전체 가이드/계산 증표·DB 통합·AI 연결은 후속이다.
- 기준: 현재 로컬 FGC 코드 구조와 합의한 피코 목업. 원격 최신 브랜치와 운영 DB를 검증한 문서는 아니다.
- 목표: 질문으로 업무를 찾고, FGC 프로그램이 산출한 금액과 근거를 바탕으로 입력·처리를 추천하며, 권한과 업무 상태에 맞는 화면·입력 위치를 단계별로 안내한다.
- 개정: 계산·추천 요구와 0단계 매핑에 이어, 1단계 입력·분기 규칙 및 2단계 업무 카탈로그·API·금액·계산 유효성·가이드 계약 v1을 구체화했다. 새로운 변경은 이 MD에 먼저 반영한 뒤 코드에 적용한다.
- GitHub 작업 규칙: 코드 작업은 19장의 이슈에 연결해 진행한다. 기존 이슈를 먼저 확인하고 중복 생성하지 않는다. 구현 범위·검증·PR·완료 상태를 이 MD와 이슈에 함께 기록한다.

## 1. 확정할 제품 범위

### 1차 범위

- 대기 중인 피코 마스코트 클릭 → 대화창 열기.
- 질문 → 업무 식별 → 필요한 대상·목적 확인 → 단계별 안내 시작.
- 실제 화면으로 이동하고 입력칸·버튼을 강조한다.
- 이전·다음·중지·복귀·종료를 제공하고, 실제 처리 결과로 단계 완료를 판정한다.
- 현재 업무의 상태가 달라지면 안내를 다시 계산한다.
- 예상 수수료·귀속 차액·한도·지급 후보·대사 차액을 프로그램으로 계산해 근거와 함께 추천한다.
- 추천 금액 확인 → 사용자 선택 → 입력 위치 안내 → 직접 입력·저장·검증으로 연결한다. 추천값 반영 UI를 추가할 경우에도 사용자의 명시적 선택으로만 반영한다.
- 챗봇 창을 닫아도 시작한 가이드는 유지한다.

### 실행 경계

- 비서는 안내를 제공한다. 저장·확정·역분개·재기표는 사용자가 기존 화면에서 직접 실행한다.
- 금액 산술과 정책 적용은 기존 FGC 계산 서비스를 재사용한다. AI는 필요한 계산을 선택하고 검증된 산출 결과를 설명·추천한다.
- 모델이 임의의 계산식·요율·반올림 규칙으로 금액을 만들거나 규제 요약을 업무 정책에 자동 적용하지 않는다.
- 초기부터 설명·절차 검색, 기존 계산 결과 조회, 저장 없는 계산 미리보기, 근거 기반 추천을 제공한다. AI가 SQL·임의 URL·임의 DOM 선택자를 실행할 수 없게 한다.
- 규제 요약·규제 질의응답과 설계사용 상품 추천은 이번 업무 안내 비서와 별도 범위로 관리한다.

### 화면 기준

- 기존 FGC 화면 디자인과 제공받은 마스코트 3종을 사용한다.
- 챗봇의 현재 업무 카드는 표시하지 않는다. `PICO WORKFLOW ASSISTANT` 문구, 대기 마스코트의 초록 알림점, 상단 소개 문구 앞 초록점도 표시하지 않는다. 내부 업무 문맥·상태 추적은 유지한다.
- 챗봇 위치: PC 오른쪽 28px / 아래 26px, 760px 이하 오른쪽 16px / 아래 78px.
- 캐릭터의 둥둥 뜨는 효과, 강조 위치의 펄스, 부드러운 스크롤, 단계 안내 카드를 유지한다.
- 모바일에서는 안내 시작 시 대화창을 접어 실제 입력 영역을 보여준다.
- 운영체제의 동작 줄이기 설정에서는 애니메이션과 부드러운 이동을 끈다.

## 2. 설계 원칙과 책임 분리

| 구성 | 책임 | 맡기지 않을 일 |
|---|---|---|
| AI·검색 | 질문 해석, 승인된 가이드 검색, 허용된 계산 요청 제안, 계산 근거 설명·추천 | 권한 판정, 임의 산술·요율 결정, 처리 상태 확정, 화면 선택자 생성 |
| 업무 비서 백엔드 | 업무·대상 권한 확인, 최신 상태 조회, 계산 서비스 호출·결과 검증, 안내 계획 구성, 검색 범위 제한 | 계산식을 별도 복제하거나 추천 요청으로 실제 지급을 변경 |
| FGC 계산 서비스 | 정책·기준일·상세행 반올림에 따른 금액 산출·후보 검증 | 모델 설명을 계산 근거로 사용 |
| 가이드 엔진 | 화면 이동, 고정 식별자 탐색, 강조·위치 추적, 안내 상태 표시 | 버튼 클릭만 보고 저장 성공으로 판단 |
| 기존 업무 API | 계약·지급·검증·정정 처리와 최종 성공·실패 판정 | AI의 설명을 실행 권한으로 사용 |

권한·처리 가능 여부는 기존 업무 API에서도 계속 검증한다. 비서의 사전 검사는 기존 인가를 대체하지 않는다.

## 4. 전체 처리 흐름

1. 사용자가 질문한다.
2. 프런트가 질문·현재 화면 ID·선택한 대상 식별자를 보낸다. 역할·소속·처리 상태는 신뢰할 입력으로 취급하지 않는다.
3. 서버가 인증 정보로 접근 범위를 확인하고, 필요한 최소 업무 상태를 기존 서비스에서 조회한다.
4. 접근 가능한 활성 가이드에서 업무 후보를 찾는다.
5. 대상이나 의도가 불명확하면 선택지를 제시한다. 임의로 지급 건을 선택하지 않는다.
6. AI가 등록된 업무 ID·계산 종류와 설명을 제안한다. 서버가 허용 목록·가이드 버전·권한·상태·계산 입력을 검증한다.
   - 금액 질문은 기존 결과 조회 또는 읽기 전용 계산 서비스로 처리하고, 실제·예상·가상 결과와 정책·기준일·반올림 근거를 함께 반환한다.
   - 사용자는 추천 근거를 확인한 뒤 안내를 시작한다. 실제 명세 금액과 예상액이 다르면 둘을 구분해 보여준다.
7. 사용자가 안내 시작을 선택하면 서버가 최신 상태를 다시 조회해 계획을 구성한다.
8. 프런트가 화면 이동 → 데이터 로딩 완료 → 대상 요소 등록을 기다린 뒤 강조한다.
9. 사용자가 기존 화면에서 실제 업무를 수행한다.
10. 업무 API 결과와 서버 상태를 확인해 단계 완료·재안내·중단을 결정한다.

모델 응답이 잘못되거나 검색이 실패해도 기존 업무 화면과 수동 처리는 계속 사용할 수 있어야 한다.

## 5. 먼저 설계할 업무·상태·단계

### 첫 번째 개발 시나리오: 지급 초안에서 확정까지

| 상태 | 안내 계획 | 완료 판정 근거 |
|---|---|---|
| 저장 전 변경사항 있음 | 저장 → 사전검증 → 확정 | 저장 성공 및 최신 저장 상태 |
| 저장 완료 | 대상 확인 → 사전검증 → 확정 | 선택 대상 확인, 검증 성공, 확정 상태 |
| 사전검증 통과 | 대상 확인 → 확정 | 현재 저장본에 대한 검증 유효성 |
| 확정 완료 | 월 검증 또는 정정 목적 확인 | 최신 지급 상태와 사용자 선택 |
| 처리 권한 없음 | 조회 가능한 설명 또는 담당자 요청 안내 | 서버의 권한 판정 |

위 표의 실제 지급 상태·권한·검증 무효화 규칙은 13장의 0단계 매핑에서 확인했다. 미저장·수정됨·사전검증 통과는 지급 enum이 아닌 화면/안내 상태로 구분한다.

### 후속 업무

1. 월 통합검증 실행·결과 확인.
2. 금액 차이 예외에서 예상·실제·원천 근거 확인.
3. 확정 건의 정정 절차와 기존 정정 화면으로 연결.
4. 보험계약 등록·예상 스케줄 확인. React 전환 상태에 맞춰 추가한다.

### 가이드 단계 정의 예시

```json
{
  "workflowId": "payment.confirm",
  "guideVersion": "1.0",
  "stepId": "payment.precheck",
  "screenId": "TRAN-W02",
  "targetId": "payment.precheck",
  "instruction": "저장된 지급 건을 사전검증하세요.",
  "completionRule": "PAYMENT_PRECHECK_SUCCEEDED_FOR_CURRENT_REVISION"
}
```

`completionRule`은 서버와 프런트가 구현한 규칙 ID다. 문서에서 읽어온 실행 코드가 아니다.

## 6. 가이드 엔진 설계

### 화면 연결

- `data-guide-target="payment.amount"`처럼 업무 의미가 유지되는 고정 ID를 등록한다.
- 문구·CSS 클래스·DOM 순서·LLM이 생성한 선택자로 요소를 찾지 않는다.
- 화면 이동 후 로딩과 탭·모달 표시를 기다린다. 제한 시간 안에 대상이 없으면 일시 중지하고 재시도를 제공한다.
- 스크롤·화면 크기·패널 열림 변화에 맞춰 강조 영역을 다시 측정한다.
- 대상이 가려지면 위치를 조정한다. 모바일 카드와 런처가 실제 업무 버튼을 막지 않게 한다.

### 안내 세션 상태

`IDLE → RESOLVING → CLARIFYING 또는 READY → GUIDING → COMPLETED`

`GUIDING`에서는 `PAUSED`, `BLOCKED`, `CANCELLED`로 전환할 수 있다. 시스템 실패는 `ERROR`로 구분한다. 사용자 중지, 조건 미충족, 시스템 실패를 같은 상태로 처리하지 않는다.

### 단계 완료와 변경 감지

- 저장: 버튼 클릭이 아니라 API 성공과 저장본 확인으로 판정한다.
- 비동기 검증: 실행 요청 성공만으로 완료하지 않고 실제 실행 ID의 결과를 확인한다.
- 지급액 등 검증 관련 값 수정: 기존 검증의 유효성을 다시 확인하고 저장·검증 단계로 안내한다.
- 대상 변경·권한 변경·다른 탭의 처리: 다음 단계 진입 전에 서버 상태를 다시 확인한다.
- 업무 상태는 되돌릴 수 없다. ‘이전’은 안내 단계만 이동하며 저장·확정을 취소하지 않는다.
- 종료·로그아웃 시 강조, 이벤트 리스너, 타이머, 진행 중 요청을 정리한다.

## 7. 업무 카탈로그와 RAG 설계

### 검색 단위

업무별로 `업무 ID, 업무명, 사용자 표현, 목적, 필요 권한, 적용 화면, 선행 조건, 절차, 주의사항, 출처, 버전, 활성 상태`를 관리한다.

- 사용자 표현 예: ‘지급 마무리’, ‘지급액 입력 다음’, ‘확정하는 방법’ → `payment.confirm` 후보.
- ‘수수료 수정’처럼 여러 업무를 뜻할 수 있는 문장은 후보 선택으로 구분한다.
- 현재 데이터·금액·처리 상태는 검색 문서에 넣어 최신 사실처럼 재사용하지 않는다. 기존 업무 서비스에서 조회한다.

### 검색·생성 순서

1. 승인된 가이드만 검색 대상으로 등록한다.
2. 사용자 권한·업무 범위·활성 버전으로 검색 대상을 제한한다.
3. 키워드 검색 기준선을 만들고, 의미 검색을 결합해 표현이 다른 질문도 찾는다.
4. 후보 가이드의 업무 ID·근거를 모델에 전달하고, 등록된 ID 중에서만 제안하도록 한다.
5. 모델 출력을 구조 검증하고, 등록되지 않은 ID·출처·버전은 거절한다.
6. 모호한 결과는 확인 질문, 근거 없는 결과는 검색 실패로 처리한다.

처음부터 별도 벡터 DB를 도입한다고 확정하지 않는다. 문서 규모·기존 저장 환경·검색 평가 결과를 확인한 뒤 인덱스 방식을 선택한다. 검색 점수의 임계값도 질문 평가셋으로 정한다.

### 응답 구분

- `GUIDE_READY`: 안내할 업무와 단계가 확인됨.
- `CLARIFICATION_REQUIRED`: 목적 또는 대상 확인 필요.
- `PERMISSION_DENIED`: 필요한 처리 권한 없음.
- `PRECONDITION_REQUIRED`: 업무 조건부터 충족해야 함.
- `NO_SUPPORTED_WORKFLOW`: 지원하는 가이드 없음.
- `TEMPORARILY_UNAVAILABLE`: 검색·모델 등 시스템 일시 실패.
- `ANSWER_READY`: 계산·설명이 준비됨. 실행할 가이드가 반드시 필요한 응답은 아니다.

답변에는 적용 가이드의 이름과 버전을 표시한다. 검색 문서와 사용자 입력에 들어 있는 명령은 실행 지시로 취급하지 않는다.

### 금액 계산·추천 범위와 프로그램 연결

계산은 FGC 프로그램에서 수행하고, AI는 계산 종류를 선택해 결과를 설명·추천한다. RAG는 절차·근거 검색에 사용하며 최신 금액 산출을 대신하지 않는다.

| 계산 종류(제안 ID) | 현재 확인한 코드·산출 | 비서 제공 기능 | 준비 상태 |
|---|---|---|---|
| `EXPECTED_COMMISSION` | `ScheduleService.createScheduleLines/calculateExpectedAmount`: 정액 또는 기준 보험료 × 요율/100, 정책 회차별 생성 | 월·회차·항목별 예상액과 기간 합계, 추천 입력값의 근거 | 기존 생성·조회 재사용. 저장 전 계산은 공통 계산부 추출/미리보기 필요 |
| `ATTRIBUTION_BALANCE` | 지급액과 귀속 합계 비교, `requiredValueFailures` | 미귀속·초과 귀속 금액 안내 | 기존 검사 재사용; 자동 배부 규칙은 별도 확정 |
| `CAP_STATUS` | `CapCalculatorImpl`: 룰셋 배수·환급금·준법경영비·산입액·잔여액·사용률 | 한도·잔여액·산입 근거 설명 | 기존 계산기 재사용 |
| `PAYMENT_CANDIDATE` | 지급 사전검증 및 `mergeScheduleAndActualValidation` | 이번 지급을 반영한 계산과 차단 사유, 입력 후보의 적합성 안내 | 저장된 DRAFT 미리보기 존재. 미저장 가상 후보는 신규 읽기 전용 어댑터 필요 |
| `RECONCILIATION_DIFFERENCE` | 보험사→GA·GA→FC 대사기의 예상/실제 행별 반올림 합계와 실제−예상 | 부족·초과 금액·원천 연결·정정 경로 안내 | 기존 대사 결과 조회 재사용 |
| `ARBITRAGE_EXCESS` | `ArbitrageService`: 확정·예정 수수료와 적용 환급금에서 납입보험료를 뺀 양의 초과액 | 현재/예정 초과 구분과 근거 설명 | 기존 결과 재사용. 환급금은 유효성 확인한 금융 스냅샷 사용 |
| `JOURNAL_CORRECTION_REVIEW` | 원장 차변/대변 합계·차액, 정정 라인 원 단위 정규화·균형 검사 | 정정 전후 금액·불균형 설명 | 기존 검증 재사용. 원천 확인 없는 재기표 금액 자동 확정 금지 |

계산 규칙:

- 예상 수수료의 정률식: `월납환산 초회보험료 × 정책 요율 / 100`. 정액은 정책 고정금액 사용.
- 한도 계산의 코드상 구조: `max(0, 월납환산 초회보험료 × 룰셋 배수 − 적용 환급금 + 인정 준법경영비)`.
- 준법경영비 인정액은 `min(반올림한 증빙 실제액, 정책 상한)`이며 증빙 누락을 최대액으로 대체하지 않는다.
- 지급 확정의 유효 산입액은 스케줄 산입액과 실제 후보 반영 산입액의 큰 값이다. 잔여 한도를 바로 추가 지급 추천액으로 표시하지 않는다.
- `MoneyUtil`과 기존 상세행별 원 단위 HALF_UP 규칙을 재사용한다. 프런트 `Number` 기반 귀속 합계 표시는 최종 서버 판정을 대체하지 않는다.
- 실제 명세 지급액과 예상액을 구분한다. 예상액을 추천할 수 있으나 실제 기록을 임의로 맞추지 않는다.
- 예상 100,000원·확정 지급 50,000원이면 차액은 -50,000원이다. 정정할 전체 금액 100,000원과 부족분 50,000원을 별도로 표시하고 원천 확인 후 기존 정정 절차로 연결한다.
- 계산 입력·정책·기준일·지급 이력이 달라지면 이전 추천을 무효화하고 다시 계산한다.
- 저장 없는 계산에는 `calculateAndSave`, 지급 생성, 스케줄 재생성, 확정·정정 API를 사용하지 않는다.

추가 검증 후 지원할 계산:

- 4년·7년 분급: 체계 구분과 84회차 범위 지원은 있으나 `calculateContractMonthNo`는 지급회차를 그대로 반환한다. 정책·지급회차·계약차월의 정확한 매핑과 계산 검증 전에는 비교 추천을 지원 완료로 취급하지 않는다. 총액/48·총액/84로 임의 대체하지 않는다.
- 월납환산 초회보험료: 현재 등록은 `DIRECT_INPUT`이다. 주기별 자동 환산은 별도 업무 규칙 확정 후 추가한다.
- 환수액 자동 산정·계약별 자동 배부: 현재 조사에서 독립 자동 산정/추천 엔진을 확인하지 못했다. 규칙·원천·누적 반영 기준을 확정하기 전에는 임의 계산하지 않는다.

계산 추천 상태는 가이드 상태와 분리한다: `CALCULATED`, `REVIEW_REQUIRED`, `INSUFFICIENT_DATA`, `UNSUPPORTED`, `STALE`. 금액이 존재해도 검토필요이면 ‘지급 가능’ 추천을 차단한다.

## 8. API·데이터 계약 설계안

### 제안 API

| 기능 | 제안 경로 | 역할 |
|---|---|---|
| 질문·업무 후보 조회 | `POST /api/v1/assistant/messages` | 질문 해석·검색·확인 질문·업무 제안 |
| 안내 시작 | `POST /api/v1/assistant/guide-sessions` | 최신 권한·상태로 계획 확정 |
| 안내 상태 재확인 | `POST /api/v1/assistant/guide-sessions/{id}/revalidate` | 진행 조건·현재 단계·계획 유효성 조회 |
| 일시 중지·종료 | `PATCH /api/v1/assistant/guide-sessions/{id}` | 안내 세션 상태만 변경 |
| 계산·추천 미리보기 | `POST /api/v1/assistant/calculations` | 허용된 기존 계산기를 호출하고 근거·유효성·추천값 반환. 업무 저장 없음 |

새 비서 API는 기존 `/api/v1` 규약을 따른다. 세부 요청·응답과 단계 전이는 16장의 계약 v1을 기준으로 구현한다. 금액 변경·저장·확정용 비서 API는 만들지 않는다. 클라이언트가 보낸 ‘완료’ 이벤트만으로 업무 성공을 인정하지 않는다.

### 최소 계약 항목

- 요청: 질문, 현재 화면 ID, 선택 대상 종류·ID, 안내 세션 ID, 요청 식별자.
- 응답: 응답 구분, 설명, 확인 질문·후보, 업무 ID, 가이드 버전·출처, 계획 ID, 단계 목록, 계산 결과·근거·추천값.
- 계산 결과: 계산 ID·종류, 대상, 실제/예상/가상 구분, 기준일, 정책·규칙 버전, 기준 금액·요율, 항목별 원 단위 금액, 합계·차액·한도, 반올림 규칙, 입력·데이터 버전, 계산 시각, 검토 사유, 추천 가능 여부. 금액 전송 형식은 16.1절의 문자열 계약으로 통일하며 프런트 부동소수 연산을 최종 산출로 사용하지 않는다.
- 계획: 사용자·접근 범위, 업무 대상, 가이드 버전, 상태 확인 기준과 시각, 현재 단계, 만료·재검증 조건.
- 단계: 화면 ID, 대상 ID, 안내 문구, 완료 규칙 ID, 진행 가능 여부와 사유.

모델에는 필요한 최소 정보만 전달한다. 인증 토큰, 전체 지급 명세, 불필요한 계약자 개인정보는 전달하지 않는다. 비용·응답 시간·실패 처리·로그 보존 기준은 모델 연결 전에 확정한다.

## 9. DB 관련 사항 — 별도 작업 영역

업무 정의와 가이드 단계는 초기에는 코드와 함께 버전 관리하는 JSON 등 정적 정의로 시작할 수 있다. DB는 운영에서 편집·보존할 필요가 확인된 데이터부터 도입한다.

| 데이터 | 저장 방향 | 주의점 |
|---|---|---|
| 업무·가이드 정의 | 초기 정적 정의, 필요 시 관리 테이블 | 코드의 target ID·조건 규칙과 버전 호환 |
| 승인 문서·검색 인덱스 | 문서 버전·활성 상태·출처와 함께 저장 | 폐기 버전이 검색되지 않도록 갱신 |
| 안내 세션·진행 상태 | 서버 저장 도입 시 별도 테이블 | 사용자·업무 범위·대상·가이드 버전 연결 |
| 계산·추천 이력 | 재현·감사 필요 범위만 저장 여부 결정 | 입력·정책 버전·기준일·결과 연결. 지급·원장에 쓰지 않음 |
| 대화 이력 | 보존 필요성과 기간 결정 후 선택 저장 | 개인정보 최소화·마스킹·삭제 기준 |
| 계약·지급·원장·예외 | 기존 테이블과 서비스 이용 | 비서용 원장이나 지급 상태 복제 금지 |

DB 도입 시 작업:

- [ ] 기존 사용자·소속·권한·업무 대상 키 구조 확인.
- [ ] 세션·문서에 접근 범위와 소유자 검증 적용.
- [ ] 조회 패턴에 맞는 인덱스·제약·보존 정책 설계.
- [ ] 실제 브랜치의 최신 Flyway 버전을 확인해 새 번호 배정. 기존 마이그레이션 수정 금지.
- [ ] 빈 DB와 기존 데이터가 있는 DB 모두 마이그레이션 검증.

A-1·B 확정 후 C·D를 진행한다. E는 고정 응답 기반 안내가 검증된 다음 연결한다. 각 변경은 기능 단위로 리뷰 가능하게 나눈다. 이 문서는 이슈 생성·PR 작성·배포를 수행했다는 의미가 아니다.

지급 시나리오의 실제 코드 연결을 조사했다. 서버 기동·운영 DB 검증·브라우저 실업무 처리는 수행하지 않았다. 로컬의 기존 `CommissionPaymentServiceImpl.java` 변경을 포함한 현재 작업트리를 읽었으며, 해당 Java 파일은 이번 작업에서 수정하지 않았다. 계약·월 검증 전체의 상세 매핑은 후속 업무 확장 단계에서 진행한다.

### 화면·API·권한

`/app`은 현재 배포 URL 기준이다. 구현 시 하드코딩하지 않고 기존 라우터 basename·월 컨텍스트·이동 헬퍼를 사용한다.

### 실제 상태와 안내 조건

- 지급 enum: `DRAFT`, `CONFIRMED`, `CANCELLED`.
- 미저장·dirty·기준정보 정규화·locked·사전검증 결과는 화면 상태다. `PRECHECKED`라는 지급 상태를 만들었다고 가정하지 않는다.
- 폼은 `DRAFT`만 편집 대상으로 연다. 저장 성공 후 입력을 잠그고 `dirty=false`, 사전검증 결과를 비운다. 기존 폼의 수정 재진입 방식을 따른다.
- `changeForm` 등의 입력 변경은 `invalidatePreview`로 `dirty=true`, `result=null` 처리한다. 귀속 정규화도 `needsSave`에 포함된다.
- 사전검증은 읽기 전용이며 `capCheckId`는 null이다. 200 응답 자체가 통과가 아니다. `confirmable=true`를 확인해야 한다.
- 사전검증은 성공 상태를 DB에 저장하지 않는다. 향후 비서가 재접속·새로고침 후 기존 통과를 기억해 확정 가능으로 단정하지 않게 한다.
- 최종 확정은 서버에서 게이트를 다시 검사한다. 프런트 성공 시 목록으로 이동하므로 가이드는 이동 후에도 해당 paymentId의 완료를 추적해야 한다.
- 일부 차단 사유는 기존 화면에서 사용자가 명시적으로 판정 기록을 요청할 수 있다. 확정 요청이 거부되며 예외가 기록될 수 있으므로 이를 ‘지급 확정 완료’로 표시하지 않는다. 비서가 자동으로 확정 API를 호출해 예외를 생성하지 않는다.

### 0단계에서 확인한 설계 보완점

1. 미저장 금액의 가상 계산을 위한 전용 읽기 전용 계약이 필요하다. 기존 사전검증은 저장된 DRAFT 기준이다.
2. 새 추천의 데이터 버전·유효성 표식을 설계해야 한다. 현재 사전검증 DTO에는 저장본 revision/토큰이 없다. 새 필드를 기존 필드처럼 사용하지 않는다.
3. 현재 SecurityConfig는 COMPLIANCE의 POST를 넓게 차단한다. 조회·계산용 비서 POST를 열 경우 해당 경로의 인증·역할·대상 인가를 명시하고 쓰기 권한을 확대하지 않는다. 1차 처리 가이드는 기존 `canProcess` 범위를 따른다.
4. 조회 컨트롤러의 인증과 대상별 접근 범위는 같은 것이 아니다. 비서 어댑터에서 사용자·대상 범위 검증을 별도 확인해야 하며, 기존에 완성돼 있다고 가정하지 않는다.
5. 계산 API의 같은 결과 재사용과 실제 확정 요청의 멱등성을 구분한다. 계산 질문이 지급 요청을 발생시키지 않게 한다.

## 15. 1단계 상세 — 필수 입력과 분기 규칙

### 15.1 입력 수집·검증 원칙

- 입력 후보의 출처를 `EXPLICIT_MESSAGE`(질문), `SELECTED_CONTEXT`(명시적으로 선택된 화면 대상), `SERVER_RESOLVED`(서버 조회)로 구분한다.
- ‘이 계약’은 화면에서 선택한 계약이 하나일 때만 후보로 해석한다. 지급 목록의 첫 행·최근 계약·기본 금액으로 대체하지 않는다.
- 선택 문맥은 사용 의도의 후보이지 권한·최신 상태의 증거가 아니다. 서버가 존재·접근 범위·현재 상태를 확인한다.
- 질문의 계약·월·금액과 선택 문맥이 다르면 확인 질문을 먼저 한다. 의도적으로 입력한 가상 금액은 실제 저장값과 분리한다.
- 지급 건 ID가 있으면 서버에서 지급단계·정산월·항목·수취인·귀속을 조회한다. 화면이 보낸 값과 충돌하면 어느 대상을 안내할지 확인한다.
- 보험사→GA와 GA→FC를 구분한다. 설계사 수취인이 항상 있다고 가정하지 않는다. 계약 비귀속 지원금 등 예외는 기존 귀속 규칙을 따른다.
- 정산월은 `YYYY-MM`, 실제 귀속일·지급예정일은 `YYYY-MM-DD`로 별도 관리한다. 실제 날짜를 월 첫날로 임의 대체하지 않는다.
- 회차가 복수이면 후보를 제시한다. 월 합계 질문이면 회차 전체를 집계할 수 있지만 ‘특정 회차 금액’으로 설명하지 않는다.

### 15.3 1차 제공 범위

- `payment.amount.review`, `payment.draft`, `payment.confirm`의 화면 가이드를 먼저 제공한다.
- 예상액·귀속 차액·한도·후보 계산은 4단계에서 기존 계산기/조회에 연결한다. 계산 서버 미연결 중에는 합성 고정 응답임을 표시한다.
- 대사 차액 설명은 기존 결과 조회로 제공할 수 있다. 예외·정정의 전체 가이드는 6단계이며, MVP에서 미등록 target을 가진 계획은 시작하지 않는다.
- 4/7년 자동 비교, 보험료 자동 환산, 환수 자동 산정, 자동 배부는 7장의 추가 검증 범위를 유지한다.

## 16. 2단계 결과 — 인터페이스 계약 v1

계약 버전은 `assistant.v1`이다. 이 장의 타입·필드·기본값은 신규 설계이며 실제 API에 아직 존재하지 않는다. 이후 변경은 이 MD를 먼저 갱신한다. 모델 공급자·검색 인덱스·세션 저장 기술 선택은 이 계약과 분리한다.

### 16.1 공통 타입·응답 규약

| 타입 | 계약 |
|---|---|
| `EntityId` | 양의 정수 10진 문자열. 기존 Java Long 범위 검사. 신규 비서 계약에서 JS number로 전달하지 않음. 선행 0 금지 |
| `ResourceId` | 서버 발급 불투명 문자열. 계산·대화·안내 세션 ID. 다른 사용자의 ID 사용 금지 |
| `AmountInput` | 서식 없는 비음수 10진 문자열, 정수 최대 13자리·소수 최대 2자리. 기존 지급 요청 검증을 재사용. 지수·쉼표·원 기호·불필요한 선행 0 금지 |
| `WonAmount` | 반올림 완료한 원 단위 정수 문자열. 차액·잔여액은 음수 허용. 모든 금액은 KRW |
| `DecimalRate` | 단위가 별도 명시된 10진 문자열. 퍼센트는 `unit=PERCENT`. 기존 계산 정밀도를 보존하고 표시와 산술을 구분 |
| `PaymentStage` | 기존 `INSURER_TO_GA` 또는 `GA_TO_FC` |
| `EvidenceKind` | `ACTUAL`, `EXPECTED`, `HYPOTHETICAL`. 합성 고정 응답의 여부는 별도 `synthetic=true` |
| `CalculationStatus` | `CALCULATED`, `REVIEW_REQUIRED`, `INSUFFICIENT_DATA`, `UNSUPPORTED`, `STALE` |
| `InputOrigin` | `EXPLICIT_MESSAGE`, `SELECTED_CONTEXT`, `SERVER_RESOLVED` |
| `GuideState` | 서버 세션은 `GUIDING`, `PAUSED`, `BLOCKED`, `COMPLETED`, `CANCELLED`, `ERROR`. 준비·질문 해석 중 상태는 프런트의 6장 상태를 사용 |

- 기존 `ApiResponse<T>`의 `{data, error, requestId}`를 사용한다. 성공은 `error=null`, 실패는 `data=null`.
- 오류는 기존 `ApiError`의 `code, message, field, params, detail` 형식. 신규 `FGC-ASST-*` 코드는 구현 때 기존 오류 카탈로그에 등록한다. 기존 지급 오류를 새 코드로 잘못 치환하지 않는다.
- 기존 지급 DTO의 숫자 필드와 새 비서의 문자열 금액을 어댑터에서 명시적으로 변환한다. 기존 지급 API 전체의 계약은 변경하지 않는다.
- 신규 객체는 정의한 필드만 허용하며 모르는 workflow·target·계산 ID, 알 수 없는 enum, 범위 밖 금액·ID는 검증 실패다. 사용자 제공 정책 버전·역할·산입 분류를 서버 사실로 채택하지 않는다.
- 존재하지 않음·권한 없음과 달리, 유효한 요청의 자료 부족·미지원은 `200 + data`의 업무 결과다. 모델/서버 장애로 계산하지 못했으면 503이며 자료 부족으로 위장하지 않는다.

### 16.2 업무 카탈로그와 가이드 정의

| 업무 ID | 필수 범위 | 등록 단계 | 완료 정의 |
|---|---|---|---|
| `payment.amount.review` | 단일 계약·월·단계 및 항목/회차 범위 또는 선택 paymentId | scope → amount | 현재 계산 근거를 표시하고 사용자가 명세와 비교. 지급 완료로 표시하지 않음 |
| `payment.draft` | 신규 후보 또는 DRAFT | scope → amount → attributions → evidence → save | 사용자가 저장하고 서버 저장본 확인 |
| `payment.confirm` | DRAFT paymentId | scope → 필요 시 save → precheck → precheck.result → confirm | 기존 API의 확정 성공 및 서버 `CONFIRMED` 확인 |

- 카탈로그 필드: `workflowId, guideVersion, title, description, utterances[], requiredSlots[], capability, roles[], availableCalculationKinds[], steps[], enabled`.
- 단계 필드: `stepId, screenId, targetId, instruction, entryRuleId, completionRuleId, missingTargetBehavior, next[{conditionId, stepId}]`.
- `screenId=TRAN-W02`의 라우트는 등록된 화면 레지스트리에서 찾고, `paymentId`를 query `id`로 전달한다. 모델·서버 응답의 임의 URL로 이동하지 않는다.
- `targetId`는 13장 의미 ID만 허용한다. 확인 모달이 열리면 같은 confirm 단계의 대상을 `payment.confirm.dialog`로 전환한다.
- `entryRuleId`와 `completionRuleId`는 구현된 허용 규칙 ID이며 코드·SpEL·SQL을 문서에서 실행하지 않는다.
- 구체 완료 규칙: `SCOPE_ACKNOWLEDGED`, `AMOUNT_REVIEW_ACKNOWLEDGED`, `ATTRIBUTIONS_REVIEWED`, `EVIDENCE_FIELDS_VALID`, `CURRENT_DRAFT_SAVED`, `CURRENT_PRECHECK_PASSED`, `PRECHECK_RESULT_ACKNOWLEDGED`, `PAYMENT_CONFIRMED`.
- 확인형 단계는 사용자의 확인과 현재 문맥 일치를 요구한다. 저장·사전검증·확정 단계는 사용자 확인만으로 완료하지 않는다.
- 예상액 조회만 원하는 사용자에게 지급 저장·확정을 뒤에 자동 연결하지 않는다. 이전 안내는 되돌려도 지급 상태는 되돌리지 않는다.

### 16.3 대화·문맥 계약

`POST /api/v1/assistant/messages`

| 요청 필드 | 필수 | 의미 |
|---|---|---|
| `contractVersion` | O | `assistant.v1` |
| `conversationId` | 신규 대화는 null | 서버 소유권을 확인하는 대화 ID |
| `clientMessageId` | O | 요청 UUID. 동일 사용자·대화에서 동일 본문 중복은 동일 결과/진행 중 결과를 반환; 신규 conversationId=null도 사용자+clientMessageId로 먼저 중복 판별. 다른 본문으로 재사용하면 409 |
| `text` | O | 공백 제거 후 1~2000자. 사용자 문장은 업무 선택의 입력 |
| `context` | O | `screenId`, 선택 paymentId·contractId·월·단계·회차·항목·수취인, `formDirty`, `clientRevision`. 선택값은 null 허용 |
| `clarificationSelection` | 선택 | 직전 서버 발급 `questionId`와 `optionId`. 임의 선택지·다른 대화 선택지 거절 |

- `context`는 현재 화면에서 실제 선택된 값만 보낸다. 토큰·사용자 역할·소속은 인증에서 확인하며 요청 필드로 받지 않는다.
- 서버 응답 `MessageResult`: `conversationId, messageId, clientMessageId, outcome, text, missingSlots[], clarification, workflowProposal, calculations[], sources[], clientRevision, synthetic`.
- `outcome`은 7장 응답 구분을 따른다. 설명/금액만 준비되면 `ANSWER_READY`, 시작 가능한 가이드 제안이면 `GUIDE_READY`다.
- `clarification`: `questionId, prompt, options[{optionId,label}], requestedSlots[]`; 불필요한 대상 개인정보를 후보에 포함하지 않는다.
- `workflowProposal`: `proposalId, workflowId, guideVersion, resolvedContext, expiresAt`; 서버가 검증한 제안이다. 이것만으로 가이드를 시작하거나 지급을 확정하지 않는다.
- `sources[]`: `sourceId, sourceType(GUIDE|POLICY|SCHEDULE|PAYMENT|RECONCILIATION), title, version, entityId`. 링크는 승인 화면 레지스트리로 만든다. 경로·URL을 모델이 정하지 않는다.
- `clientRevision`은 대상·금액·귀속·근거 등 관련 입력이 달라질 때 증가시키는 프런트 정수이며 서버의 저장본 버전과 다르다. `formDirty`는 화면 안내 힌트이며 서버 상태의 증거가 아니다.
- 오래된 `clientRevision`의 응답은 화면에 새 추천으로 덮어쓰지 않는다. 새 대화·로그아웃은 진행 중 응답을 취소하고 이전 문맥을 제거한다.

### 16.4 계산 도구 계약

`POST /api/v1/assistant/calculations`

요청 공통: `contractVersion, kind, mode, scope, candidate, clientRevision`.

- `mode=EXISTING`: 서버가 현재 자료를 읽는다. `candidate=null`.
- `mode=HYPOTHETICAL`: 완전한 후보를 별도로 평가한다. 실제 지급 상태를 변경하지 않는다.
- `scope`: `paymentId, contractId, settlementMonth, paymentStage, installmentNo, commissionItemId, beneficiaryAgentId, asOfDate`. 종류에 따라 필요한 값만 필수이며 부족하면 구조화된 `missingInputs[]`를 반환한다. 지급단계별 수취인 구조는 서버 원천 기준이다.
- 지급 후보의 `candidate.operation`은 `REPLACE_DRAFT` 또는 `NEW_PAYMENT`. `REPLACE_DRAFT`는 DRAFT paymentId 필수이고 기존 동일 건을 누계에서 제외한 뒤 후보를 한 번 반영한다. 확정 건 대체는 거절한다.
- `candidate.payment`은 기존 `CommissionPaymentCreateRequest`에 대응하는 전체 후보: sourceType, sourceBusinessKey, contractId, agentId, commissionItemId, amount, settlementMonth, cashflowType, scheduledPaymentDate, paymentStage, allocationPolicyVersion, attributions, evidenceRef, note.
- 귀속행은 기존 요청의 contractId, attributionDate, amount, inclusionDecisionStatus, exclusionType, inclusionDecisionReason, allocationBasis, evidenceRef, attributionMethod를 보존한다. ID는 `EntityId`, 금액은 `AmountInput`으로 전송 후 기존 도메인 검증에 연결한다. 명세·날짜·분류·증빙 필드를 모델이 채워 넣지 않는다.
- `settlementMonth`는 신규 비서에서 YYYY-MM이며 기존 지급 요청으로 넘길 때만 월 첫날로 변환한다. `attributionDate`, `scheduledPaymentDate`는 실제 일자를 보존한다.
- `ATTRIBUTION_BALANCE`의 가상 계산은 `candidate.balance={amount, attributionAmounts[]}`만으로 가능하다. 귀속 합계 계산을 지급 가능 판정이라고 표시하지 않는다.

| kind | MVP 모드·필수 자료 | 반환 핵심 |
|---|---|---|
| `EXPECTED_COMMISSION` | EXISTING, 단일 계약·월·단계·명시한 조회 범위 | 스케줄 상세행과 expectedAmount. 활성 스케줄이 없으면 미지원 생성 호출 없이 자료 부족 |
| `ATTRIBUTION_BALANCE` | EXISTING paymentId 또는 HYPOTHETICAL balance | amount, attributedTotal, differenceAmount=지급액−귀속합계 |
| `CAP_STATUS` | EXISTING, 계약·단계·기준일·필요 증빙 | limitAmount, includedAmount, remainingAmount, usagePct, 판정 |
| `PAYMENT_CANDIDATE` | EXISTING DRAFT paymentId 또는 HYPOTHETICAL 전체 후보 | 계약×단계별 capPreview, confirmable, blockers. 가상 계산은 확정용 사전검증 증표를 발급하지 않음 |
| `RECONCILIATION_DIFFERENCE` | EXISTING, 접근 가능한 기존 대사 결과 ID와 연결 원천 | expectedAmount, actualAmount, differenceAmount=실제−예상. 정정액은 확인 전 null |
| `ARBITRAGE_EXCESS`, `JOURNAL_CORRECTION_REVIEW` | ID는 예약하되 후속 업무 어댑터 등록 전 UNSUPPORTED | 지원 범위와 필요한 근거. 임의 실행 없음 |

`scope`의 대사 계산은 추가로 `reconciliationResultId`를 받는다. 범위에 없는 journal/대사 ID를 paymentId로 전달하지 않는다.

계산 응답 `CalculationResult`:

| 필드 | 의미 |
|---|---|
| `calculationId, kind, status, clientRevision, synthetic` | 결과 식별·계산 상태·현재 화면 응답 여부 |
| `mode, evidenceKind, currency` | 실제/예상/가상 구분. currency는 KRW |
| `resolvedScope` | 서버가 확인한 계산 범위와 집계 범위 |
| `amounts` | kind별 허용 금액 이름과 WonAmount. 모르는 값은 null, 0으로 추정 금지 |
| `lines[]` | 행 ID·출처·회차·기준 금액·계산 유형·요율/정액·산출 금액·반올림 근거 |
| `capPreview[]` | 기존 TransactionPrecheckResponse의 게이지 필드 의미를 보존. 금액만 신규 문자열 규약으로 변환 |
| `confirmable` | 후보 검사 결과에서만 boolean, 나머지는 null. 가상 true는 저장/확정 권한·완료 증명이 아님 |
| `blockers[], missingInputs[]` | 도메인 오류 코드·메시지·관련 대상, 부족한 슬롯 |
| `basis` | asOfDate, policyVersionIds, ruleIds, sourceRefs[], rounding={scale:0,mode:HALF_UP,aggregation:ROUND_EACH_LINE_THEN_SUM} |
| `recommendation` | allowed, targetId, suggestedAmount, reason, requiredChecks[]. 규칙상 검토필요·자료부족·오래된 계산이면 allowed=false |
| `validity` | 서버 발급 stateToken, calculatedAt, expiresAt, inputFingerprint, dependencyFingerprint |

- amounts/lines/capPreview와 설명의 숫자가 다르면 서버 숫자를 우선하고 잘못 생성된 설명을 폐기한다. 모델의 추천 금액은 서버 결과에 없는 숫자를 추가할 수 없다.
- 계산 정상과 실행 가능은 다르다. 귀속 차액이 정상 산출돼도 차액이 있으면 입력 보완이 필요하다. 후보 confirmable=true여도 사용자가 직접 저장·검증·확정해야 한다.
- 추천 금액은 원천과 일치 확인 가능한 예상액 등에만 제공한다. 한도 잔여액·대사 차액을 지급 추천값으로 직접 복사하지 않는다.
- 계산 API와 대화 내부 계산은 같은 읽기 전용 어댑터를 사용한다. 실제 지급/원장/예외 기록 또는 스케줄 생성·재생성은 금지한다. 보안·운영 추적 로그와 금융 업무 기록은 구분한다.

### 16.5 유효성·사전검증 증표

- 기본 계산·가이드 제안 유효 시간은 발급 후 5분이다. 안내 세션은 마지막 활동 후 30분이면 만료된다. 구현 기본값이며 설정 변경도 MD에 기록한다.
- 시간 이내라도 금액·귀속·증빙·대상·기준일·정책·활성 스케줄·관련 확정/취소 이력이 바뀌면 즉시 STALE이다.
- `inputFingerprint`는 서버가 검증·정규화한 입력으로 생성한다. `dependencyFingerprint`는 실제 조회한 지급/귀속·규칙·스케줄·증빙·관련 집계 자료의 식별/버전/값을 정규화해 계산한다. 입력 문자열만 해시해 최신성을 주장하지 않는다.
- 서버는 계산에 사용한 일관된 자료 스냅샷에 결과와 fingerprint를 함께 묶는다. 산출 중 자료가 달라졌으면 재시도하거나 STALE로 반환한다.
- `stateToken`은 사용자·접근 범위·종류·대상·fingerprint·만료에 연결된 서버 검증 가능한 불투명 증표다. 클라이언트 hash 자체는 권한·완료 증거가 아니다. 구현 방식과 보존소는 4단계에서 선택하되 이 의미를 지켜야 한다.
- 안내 시작·다음 단계·재개·추천값 사용 시 서버 권한과 의존성을 재확인한다. 최종 지급 확정은 기존 서버 게이트가 다시 판단한다.

**추가 구현이 필요한 실제 사전검증 증표:**

현재 precheck는 결과를 DB에 저장하지 않으므로, 백엔드가 ‘이번 저장본에 대해 사용자가 사전검증을 통과했다’를 확인할 수 있는 표식이 없다. 계약 v1에서는 다음 확장을 계획한다.

1. 사용자가 기존 화면에서 `POST /api/v1/transactions/{id}/precheck`를 실행하고 confirmable=true이면 서버가 응답 헤더 `X-FGC-Precheck-Token`을 추가한다. 기존 JSON 응답은 보존한다.
2. 증표는 사용자·paymentId·현재 저장본/정책/의존성 fingerprint·5분 만료에 연결한다. 기존 `apiClient`에서 이 헤더를 읽어 업무 화면의 완료 이벤트와 함께 보관할 수 있도록 최소 확장한다.
3. 가이드 재검증은 토큰을 확인하고 최신 상태와 대조한다. 클라이언트의 passed=true, 조작된 paymentId, 단순 HTTP 200은 인정하지 않는다.
4. 가상 계산이나 일반 계산 결과에는 이 토큰을 발급하지 않는다. 계산 result의 stateToken과 서로 교환할 수 없다.
5. 페이지 새로고침·토큰 유실·관련 입력 변경·만료 시 사전검증을 다시 요구한다. 다른 브라우저 세션의 옛 통과를 임의로 복원하지 않는다.

이 헤더·증표·클라이언트 확장은 현재 미구현이다. 4단계 완료 전까지 실제 사전검증 완료를 증명했다고 표시하지 않는다. 3단계 고정 응답에서는 synthetic 표식으로만 시연한다.

### 16.6 안내 세션 API·전이

| API | 요청 | 성공 data와 규칙 |
|---|---|---|
| POST `/guide-sessions` | contractVersion, proposalId, context, clientCommandId(UUID) | GuideSession. 권한·대상·현재 상태·제안 버전 재검증. 낡은 제안이면 409 |
| POST `/guide-sessions/{id}/revalidate` | expectedPlanVersion, intent(REFRESH/NEXT/PREVIOUS/REPLAY), currentStepId, context, precheckToken(nullable), clientCommandId | 최신 GuideSession. 서버 조건을 충족한 NEXT만 진행. 미충족이면 200/BLOCKED와 사유 |
| PATCH `/guide-sessions/{id}` | expectedPlanVersion, action(PAUSE/RESUME/CANCEL), clientCommandId | 변경된 GuideSession. RESUME은 최신 권한·상태 확인. 클라이언트 COMPLETED 지정 금지 |

전체 prefix는 `/api/v1/assistant`다.

`GuideSession`: `guideSessionId, workflowId, guideVersion, planVersion, state, resolvedContext, steps[], currentStepId, stepResult, blockers[], validity, synthetic`.

- `steps[]`는 16.2절 단계와 프런트가 표시할 `title, instruction`을 포함한다. 조건은 허용 규칙 ID만 받는다.
- `stepResult`: `status(WAITING|SATISFIED|BLOCKED), reasonCode, message, evidenceKind(USER_ACK|SERVER_SNAPSHOT|PRECHECK_TOKEN|PAYMENT_STATUS)`.
- 완료 조건 불충족은 안내 BLOCKED이며 네트워크 실패와 구분한다. 계획이 바뀌면 planVersion을 증가시키고 폐기한 단계로 진행하지 않는다.
- 명령별 clientCommandId의 동일 본문 재요청은 동일 결과를 반환한다. 다른 본문 재사용·오래된 expectedPlanVersion은 409다. 사용자 ‘다음’ 한 번이 재전송으로 두 단계 이동하지 않는다.
- PREVIOUS는 안내만 이동하며 서버 처리 상태를 취소하지 않는다. REPLAY는 화면·대상을 다시 찾아 강조한다.
- PAUSE→RESUME은 최초 미충족 단계부터 안내한다. 대상 페이지 수동 이동은 프런트가 일시 중지하며 서버 세션도 동기화한다.
- 대화창 닫기는 UI 상태다. 안내를 자동 취소하거나 중지하지 않는다. 안내 종료는 CANCEL, 최종 완료 조건 충족은 서버가 COMPLETED로 반환한다.
- 범위가 바뀌면 기존 추천과 검증 토큰을 폐기하고 재계획한다. `CONFIRMED`이면 재확정 단계를 내보내지 않는다. `CANCELLED`이면 대상 재선택을 요구한다.
- 경로 이동·DOM 준비 실패는 프런트에서 PAUSED와 재시도로 처리한다. 업무 자체가 성공한 것처럼 단계를 넘기지 않는다.

### 16.7 권한·오류·개인정보

| 상황 | HTTP/업무 결과 |
|---|---|
| 인증 없음 | 401, 로그인 후 문맥 재선택 |
| 엔드포인트 역할 또는 대상 접근 불가 | 403. 민감한 대상 내용·계산 결과 반환 금지 |
| 접근 가능한 대상 없음 | 404. 비인가 대상의 존재를 노출하지 않게 조회 정책 통일 |
| 타입·숫자·enum·선택지·필수 기술 필드 오류 | 400, field와 params 제공 |
| 모호한 목적·부족한 업무 슬롯 | 200, CLARIFICATION_REQUIRED 또는 계산 INSUFFICIENT_DATA |
| 아직 미지원 계산·업무 | 200, 계산 UNSUPPORTED 또는 NO_SUPPORTED_WORKFLOW |
| 사전 조건 부족·검토필요·단계 진행 불가 | 200, PRECONDITION_REQUIRED/REVIEW_REQUIRED/BLOCKED. 기존 precheck는 기존 규약 유지 |
| 오래된 제안·명령·토큰·동시 변경 충돌 | 409, FGC-ASST-STALE_CONTEXT 또는 FGC-ASST-VERSION_CONFLICT. 재조회·재계산 |
| 만료된 안내 세션 | 410, 재시작. 이전 대상·대화 권한을 재확인 |
| 사용량 제한 | 429, 서버가 주는 재시도 기준 표시 |
| 모델·검색·계산 인프라 장애 | 503, 기존 업무 화면 사용 가능 |

- 메시지 API는 인증된 기존 역할의 업무 질문을 받아 처리 권한이 없는 의도에 일반적인 PERMISSION_DENIED 설명을 반환할 수 있다. 이 경우 대상 세부 정보는 조회 권한 범위만 사용한다.
- 지급 후보 계산·가이드 시작/진행은 `canProcess` 범위다. COMPLIANCE에 대한 설명/조회 계산 POST만 명시적인 읽기 전용 경로 정책으로 허용하고 기존 지급 POST 권한은 바꾸지 않는다.
- `ATTRIBUTION_BALANCE`, 기존 예상/한도/대사 조회도 각 원천의 조회·대상 인가 후 수행한다. 설명 권한을 근거로 전체 계약 검색을 열지 않는다.
- 세션·대화·계산 ID는 항상 사용자·접근 범위에 묶는다. 로그아웃·사용자 변경 때 프런트 상태를 없애고 서버의 이전 증표를 더 이상 사용할 수 없게 한다.
- 토큰·불필요한 명세·계약자 개인정보를 모델에 보내지 않는다. 출처·검색 문서의 명령은 권한/계산 실행 지시가 아니다.
- 2단계에서는 업무 카탈로그를 버전 관리하는 정적 정의로 시작한다. 대화 장기 보존·새 업무 DB 테이블은 도입하지 않는다. 운영 세션 보존·증표 검증의 구체 기술 선택과 재기동/다중 서버 처리는 4단계에서 별도로 기록한다.

## 23. #733 서버 계산 조회 연결 — 구현 전 범위

- 선행 #740 위에서 저장된 지급의 `ATTRIBUTION_BALANCE`·DRAFT `PAYMENT_CANDIDATE` EXISTING 조회를 먼저 구현한다. 예상 스케줄의 항목/수취인/회차 원천 매핑, 가상 NEW_PAYMENT/REPLACE_DRAFT, 별도 CAP_STATUS·대사 어댑터는 후속이다. 미지원 요청은 UNSUPPORTED를 반환하며 계산·생성을 추정하지 않는다.
- 신규 `POST /api/v1/assistant/calculations`는 입력 contractVersion=assistant.v1, kind/mode/scope/candidate/clientRevision을 따른다. 기존 IF-API-60 질문 API를 바꾸지 않는다. 이번 결과는 `snapshotOnly=true`인 읽기 전용 스냅샷이며 validity=null을 명시적으로 허용한다. 이는 16.4·16.5의 전체 증표 계약에 대한 부분 구현 표시다. validity가 없는 결과의 추천/가이드 실행은 반드시 거절한다.

- 내부 조회 역할은 귀속 차액 조회만 허용한다. 지급 후보는 기존 CAN_PROCESS 역할로 제한한다. 설계사/알 수 없는 역할은 거절한다. 읽기 전용 POST 한 경로만 COMPLIANCE 예외로 허용하고 세션 CSRF를 유지한다.
- 전체 의존성 fingerprint/사용자 바인딩 증표·실제 precheckToken은 이번에 발급하지 않는다. 일관된 REPEATABLE_READ 읽기 결과와 계산 시각만 반환한다. 다음번 조회의 최신 권한·자료를 다시 읽으며 결과에 지급 가능 승인 권한을 부여하지 않는다.
- 프런트는 실제 지급 화면의 현재 저장 paymentId를 명시적으로 선택해 조회한다. 미저장 수정/범위/revision/사용자 변경·로그아웃·새 대화·요청 순서 역전에서 응답을 폐기하거나 다시 조회가 필요하다고 표시한다. 합성 질문과 서버 조회 카드를 구분하고 금액을 입력하지 않는다.
- 조회 버튼은 저장/사전검증/확정 대신 실행하지 않는다. 계산 API로 precheck를 호출해도 사용자 사전검증 완료 이벤트·증표를 만들지 않는다.
- 검증: 반올림·음수 차액·누락/null·비DRAFT·원천 범위·역할/CSRF·기존 precheck 동등성·쓰기로직 미호출·오래된 응답, OpenAPI 생성·서버/프런트 테스트·빌드·Chrome. #733 전체는 닫지 않는다.

2. 질문 원문 의미와 최근 대화 최대 여섯 턴을 활용한다. 대화는 로그인 사용자에 묶인 현재 브라우저 메모리에 보관하고 화면 이동에는 유지, 초기화·로그아웃·계정 변경에는 폐기한다. 서버는 원문을 저장/로그하지 않으며 키·계좌·주민번호·이메일·전화번호 등 민감 패턴을 제거한 텍스트만 모델에 전달한다. 업무 필드·금액·고객 데이터는 자동 수집해 전송하지 않는다. 대화의 처리 완료 주장·권한 주장은 증거로 쓰지 않는다.
3. 승인된 업무 가이드를 단일 버전 지식원으로 관리하고 실제 기능의 단계·입력·선행조건·완료 조건을 명시한다. 단순 안내 확인과 저장·검증·확정 성공을 구분한다. 기존 프로그램의 계산 결과를 연결하고 모델이 금액을 계산·승인하지 않는다.
