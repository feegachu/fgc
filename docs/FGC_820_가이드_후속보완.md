# FUN-087·088 가이드 후속 보완 (#820)

이미 병합된 #743, #759, #814 이후의 보완을 모은 변경이다. 화면정의서 v3.0의 화면별 도움말과 CMN-C04 전체 업무 흐름을 기준으로 한다. 기존 업무 API·권한·저장 버튼이 업무 처리를 담당하고, 가이드는 입력 조건과 실제 서버 결과를 관찰한다.

## 포함한 동작

| 영역 | 완료 판단 및 예외 흐름 |
| --- | --- |
| 지급 도움말 | 정식 마스코트 사용. 증빙 필수 귀속행의 증빙이 없으면 저장 버튼과 저장 핸들러를 차단한다. 다중 계약의 타입·ID를 함께 추적하며 계약 추가·교체 시 안내를 재평가한다. 사전검증과 확정 응답 확인 후 완료를 표시하고 목록으로 이동한다. |
| 화면별 도움말 | 목록·조회 화면에는 설명 확인 단계를 제공한다. 설명을 읽었다는 표시를 실제 업무 완료로 취급하지 않는다. 계약 탭은 등록된 탭만 열며 업무 실행 버튼을 자동으로 누르지 않는다. |
| 계약·정책 저장 / 스케줄 재생성 | 필수 입력을 확인하고 기존 저장 핸들러의 서버 ID 응답을 받았을 때만 다음 단계가 열린다. 완료 안내를 마친 뒤 저장 결과로 이동한다. |
| 검증·대사 실행 | 요청 접수만으로 완료하지 않는다. 현재 대상의 COMPLETED/FINALIZED 결과 조회가 성공해야 한다. 대상·조건 변경, 실패 상태, 결과 조회 실패는 이전 완료를 무효화한다. |
| 예외 처리·원천 정정·최종 확정 | 예외 조치의 처리 순번, 정정의 새 분개 ID, 최종 확정의 서버 결과를 각각 확인한다. 예외 조치 완료와 원천 정정·재검증·재대사 완료를 구분한다. |
| 전체 업무 가이드 | 미저장 입력이 있는 이동은 확인창을 표시하며 기본 선택은 현재 화면 유지다. 같은 경로의 대상·쿼리 변경도 추적한다. 입력 조회·타깃 준비의 무한 대기를 방지한다. 지급 변경 이전의 검증은 새 안내 세션에서도 재사용하지 않는다. |
| 타깃 검사 | 빌드 시 카탈로그의 화면·타깃 누락과 중복, 잘못된 등록을 검사한다. 실행 시에는 실제 DOM의 누락·중복·숨김을 다시 확인하고 안전하게 멈춘다. |

카탈로그: `frontend/src/features/assistant/guide/screen-help.json`.

## 구현 선택과 범위

- 서버 성공 연결은 메모리 내 `SaveGuide`로 공유한다. 별도 업무 저장이나 새 API를 만들지 않고 기존 핸들러의 결과를 사용하기 위함이다. 가이드 진행은 업무 상태의 대체 저장소가 아니다.
- 목록 도움말과 실행 도움말의 완료 문구를 구분한다. 사용자 설명 확인을 검증 통과·예외 해소·최종 확정으로 오인하지 않게 하기 위함이다.
- 최신 develop의 CLAW-W01에는 조회 도움말을 연결한다. 환수 처리 기능 자체를 변경하지 않는다.
- FUN-037의 신규 예정 생성은 아직 별도 작업이므로 이 PR에는 기존 스케줄 재생성 도움말만 포함한다. 예정 생성 전용 타깃과 도움말은 FUN-037과 함께 반영한다.
- AI 통합·추가 업무 시나리오를 다루는 #813과 공통 가이드 변경이 겹칠 수 있으므로 병합 순서에 따라 재검토한다. 이 PR만으로 FUN-087 전체 완료를 선언하지 않는다.
- 백엔드 정책 계산, 테스트 계정·비밀번호·DB 데이터, 개인 로컬 실행 설정은 포함하지 않는다.

## 리뷰·수동 확인 순서

1. 지급 등록에서 신인/제외 귀속행의 필수 증빙을 비운다. 저장이 비활성이고 서버 저장 요청이 발생하지 않는지 확인한 뒤 증빙을 입력한다.
2. 계약을 여러 개 선택한 지급에서 도움말을 연다. 입력 → 초안 저장 → 사전검증 → 확정을 진행하고, 서버 성공 후 완료 안내를 확인한 뒤 목록으로 이동한다. 중간에 계약을 추가·교체했을 때 이전 완료를 재사용하지 않는지 확인한다.
3. 계약·정책 편집 또는 스케줄 새 버전 만들기에서 도움말을 연다. 필수 입력 전에는 다음이 비활성이고, 입력만 완료해도 저장 완료 단계가 열리지 않아야 한다. 실제 저장 뒤 안내 마치기를 눌러 이동한다.
4. 검증·대사 실행 도움말에서 RUNNING 동안 다음이 차단되는지 확인한다. 완료 결과 조회 후 진행하고, 조건 변경·실패·조회 오류 시 이전 성공을 인정하지 않는지 확인한다.
5. 전체 가이드에서 입력을 수정하고 다른 대상으로 이동한다. 확인창의 현재 화면 유지는 입력과 현재 단계를 보존해야 한다. 이동을 선택하면 새 대상에 맞춰 안내가 갱신되어야 한다.
6. 원천 정정 뒤 이전 지급·검증을 다시 선택하거나 안내를 새로 연다. 오래된 결과로 최종 완료할 수 없어야 한다. 새 지급 선택 → 새 월 검증 → 재대사 → 최종 확정 순서로 실제 서버 결과를 확인한다.

## 검증 기록

최종 PR 본문에 검증한 develop 기준 커밋과 테스트 결과를 기록한다. 격리 PostgreSQL과 별도 서버 포트를 사용하며 기존 수동 테스트 DB는 초기화하지 않는다. 실서버 회귀 시나리오는 `frontend/e2e-demo/{payment-guide,settlement-guide,settlement-completion,settlement-normal}.spec.ts`이고, 입력 데이터만 준비한 뒤 결과 상태는 실제 API로 생성한다.
